# Plan 315 — The local edition's first run: a person and a Helmsman who can both see the machine

**Status:** 🌱 design · **Depends on:** the local operating model (delivered through publication; the archive's 313) · **Companion:** the design pass in §5 P2, which decides layout questions this plan records but does not settle

## 0. How this plan is built

From one walkthrough of the local edition as a new user, in a fresh workspace, on the development stack: create a workspace, ask the first question, find This Computer, the Store, Skills, Integrations, Settings, the Workbench, then open a long conversation. Each finding is recorded with the surface it was seen on and the shape of its fix; the phases group the fixes by the surface they change, smallest first. Layout questions the walkthrough raised but cannot answer are recorded for one design pass rather than settled piecemeal.

## 1. Problem

A person installs the appliance, opens a workspace and is met by a hosted product: a rail that names nothing until it is expanded, an empty chat that suggests skills and integrations, a "workspace ready" step that names agents, a Store led by trading and Kaggle, an Integrations page offering repository designations for a lane that is absent here, a connect flow that assumes a source checkout, and credentials buried in a settings tab although most of the product is blocked without them. Nothing says what this computer is, whether it is paired, which coding agent it has, or which folders it reaches. Helmsman is in the same position: it answers the first question well but cannot point at the surface to use, and its own Workbench shows it nothing about the machine.

Memory has the same shape of problem underneath: embeddings need a provider, and today they either ride a platform credential or fail quietly, which leaves memory unsearchable without a word to the operator.

The loop delivered by the local operating model works. Reaching it from a first run takes knowledge the product does not give.

## 2. Decisions

**D1 — The machine is a first-class object on every operator surface, and the same object Helmsman reads.** This Computer, the Workbench and the first-run checklist all render the host inventory the space context already carries (`hostname`, `runtimes`, `harnesses {id, label}`, `observedAt`) and the folders with their posture (`mode`, `allowsExecution`, `branchPrefix`). One reader, three places. When a surface and Helmsman disagree about the machine, that is a bug in the reader, not two facts.

**D2 — First-run guidance is state, not prose, and it lives in the Workbench.** The checklist is derived: credentials present, paired, a folder connected, the local skills installed, GitHub connected, embeddings configured. Each line links to the surface that changes it and disappears when done. The Workbench holds the guidance and the controls; the empty chat only points at the Workbench. Helmsman gets the same state as data in its space context; its prompt gains no sentence.

**D3 — Hosted-only affordances are withheld where their lane is absent, by the derivation the Store already uses.** The Repos tab and the code-repository option in Integrations, hosted-only settings tabs, and any listing whose operations name an uncomposed lane are absent on the local edition, not shown and refused. One rule (`isOperationComposed` / `uncomposedListingReason`) decides.

**D4 — Words.** Operator-facing copy says _coding agent_, never _harness_; _Store_, never _Shop_; _Helmsman_ or _the assistant_, never _cybernetic agent_. Internal identifiers keep their names.

**D5 — The appliance's connect command is the appliance's.** The paired daemon ships a CLI; This Computer prints `aflow connect <code>` on the appliance and the `yarn workspace` form only on a development stack, decided by the same descriptor that decides the edition.

**D6 — A fresh chat says nothing about its connection.** The connection notice speaks only for a session that once was live. The transport's own phase is what a notice reads, not a session subscription that does not yet exist.

**D7 — The coding agent may not touch refs it did not make.** A commission's worktree shares refs with the operator's repository; the executor snapshots refs before the run and refuses a result that changed any ref other than the worktree's own detached HEAD. Local Publish, in turn, takes a branch that already exists and appends to it, so "on the same branch" is a request the skill can honour rather than one the agent works around.

**D8 — Credentials are a rail entry, not a settings tab.** Most of the product is blocked until a model provider key exists, and more will be. Credentials get their own entry in the rail, linked from the model picker beside the composer; the picker keeps the model and reasoning choice and gains a line that says which providers are usable and which need a key. The remaining settings tabs stay where they are: each is optional and situational, and the pass in P2 reviews them for what is dead.

**D9 — The rail expands on hover and pins on click.** Hovering slides the expanded rail over the content, so names appear without a click and nothing moves; clicking pins it open and pushes the content, as today. Names are always in the accessibility tree, expanded or not.

**D10 — The Workbench is open by default on a desktop, and it is cheap to keep open.** Its sections read the same queries the chat already holds; nothing in it polls, and a section that is empty renders one line. Whether it opens by default is a width rule, not a preference.

**D11 — What needs the operator has its own place.** Approvals, questions, gates and proposals gather in one panel that is collapsed when empty and opens when something arrives; the chat inlines the same item where it occurred, as now. One source, two views.

**D12 — Embeddings use the operator's credentials, and their state is visible.** Memory's embedding provider and model are chosen by the operator per space among the providers whose key is present, with a default that follows the chat provider when it offers embeddings. No embedding is ever attempted against a platform credential on the local edition, and none fails silently: a memory written without embeddings is marked as such, memory search says when it is lexical only, and the checklist carries the line. Switching the embedding provider or model re-indexes, and the switch says so and shows progress; a space keeps searching lexically while it re-indexes.

**D13 — A skill run is asynchronous, and its outcome reaches the session as an event, never as an interruption.** `workflow.run.start` returns the run id at once and says how the outcome arrives; the waiter is registered against the session rather than a parked step. Every session has one inbox — operator messages, run wakeup envelopes, approval decisions — that producers append to and nothing polls. Delivery is at the turn boundary: when a turn settles with the inbox non-empty the next turn starts now with the items as data, coalesced; a session idle at its prompt is resumed by a wakeup as a turn with no operator message; a running turn is never interrupted for information (interruption stays what it is, control: cancel, stop, revoke). The envelope is data in the transcript, rendered as a card that says why the agent spoke unprompted, and event-driven turns are bounded by one rate knob per session. This is the session-sized form of the mailbox Plan 299 specifies for the resident mind; the two are one table with different owners, and every measurement taken here — how often the agent speaks unprompted, whether a wake reads as help or as noise, where the rate knob sits — is one the mind needs before it lands.

**D14 — The push asks for a hand only when nothing else has looked.** The approval before a publication's push is a posture on the connected folder, not a step of the skill: `always`, `never`, or `unless-unreviewed`, under which the publication runs Local Code Review itself over `baseSha..commitSha` — the commit it just made, named by two shas so no branch name and no earlier review is involved — and pushes without asking when that review returns `approve`, pausing for the operator otherwise (`comment`, `request_changes`, or a review that could not run). The verdict is tied to the exact commit by construction, and the push sends that sha, not the branch name, so a branch that moved in between carries nothing unreviewed. A review of a head cannot precede the publication that creates the head, and a verdict the reviewing agent writes into its own result cannot clear a gate; both shapes were tried and refused in review. What the gate guarded is already guarded elsewhere: the push can only create or advance a branch under the folder's publish prefix with an argv the skill pins, and nothing reaches the base branch without a pull request, its checks and the operator's review. What the gate never guarded, a secret in the diff leaving the machine, is guarded by a scan over everything the push would add — `origin/<base>..<sha>`, not only the commission's own commits — before the push; a finding fails the publication, a file the scan could not read whole makes it ask, and a line an operator has marked as allowed still makes it ask with the marked lines shown, because the agent that wrote the line can write the marker too. The default becomes `unless-unreviewed` with the scan. The merge stays the operator's.

**D15 — A fix appended to a branch its base has moved past carries the base with it, as one merge commit whose resolution the coding agent made.** Nothing in the loop merges today: a fix commissioned from a branch `main` has moved past carries none of `main`'s changes, and the branch learns it conflicts only from GitHub after the push. A commission therefore takes `mergeFrom`, a `<remote>/<ref>` naming one of the folder's remotes — the publication's `origin/<base>` — fetched and resolved before any checkout is touched, as `base` is, and refused naming it when the remote is not the folder's or the ref cannot be fetched. Once the checkout stands at `base`, the fetched commit, unless the checkout already holds it, is merged in: `--no-ff --no-edit`, under the operator's commit identity, as the publication's commit is, with replace objects, hooks and the operator's global config off and the conflict style and `rerere` pinned, so the merge is a function of its two parents and nothing else. That identity is the one thing a commission with `mergeFrom` needs that a commission without it never did, so where neither the repository's config nor the global one sets it, the commission is refused before any checkout is touched, naming the `user.name` or `user.email` to set. A merge that conflicts is committed, so the agent's turn begins on a tree that shows what needs resolving, and the record of each conflict is what git names, with its kind: `content` where both sides changed a file and `add-add` where both added it differently, each left with markers, and `modify-delete` or `delete-modify` where one side deleted a file the other changed, which leaves no marker at all, so the merge commits it deleted — the base's deletion holds by default, which is the outcome this gate exists to protect. The task names each conflict with its kind and what resolving it means; a deleted one reads "deleted in the merge; restore it with the changes it needs, or leave it deleted". A merge that conflicts in a file both sides hold and git merges as binary leaves no marker to resolve — only one side's bytes — so it is refused before any turn runs, naming the files and saying the merge has to be made by hand. The result reports `merge: { from, conflicts: [{ path, kind }] }`; the diff is taken against the merge commit, so the patch holds the agent's work and its resolution and none of the base's own changes, while `baseSha` stays the branch's head as found, which is what the publication checks the branch against. A continued turn keeps the session's checkout, merge and all. The publication is handed the sha the commission reported as `commit.mergeFrom`: on the branch's head it fetches that sha from `origin` where the folder lacks it, re-makes the identical merge, applies the patch on top and folds both into one commit under the publication's message — parents the old head and `mergeFrom`, tree the agent's. A patch that does not fit the re-made merge is refused as an apply conflict naming the files. The re-made merge records the same conflicts, and the publication refuses a `content` or `add-add` file that still holds the merge's markers, naming the path and the kind, with nothing committed. Only those files are read for markers, so a fixture or a document that holds marker lines of its own and was never in conflict publishes. A `modify-delete` or `delete-modify` file needs nothing of the patch, because no decision about it can be invisible: one the patch leaves alone is published deleted, the deletion accepted, and one the patch brings back is published restored, the file kept — either way it is what the tree becomes. Merging is the commission's decision, made where an agent can resolve it; the publication repeats it and decides nothing. The review reads a branch its base moved past as what the branch adds — the three-dot diff from the merge base of the range's two ends — while its commit list and the scan keep the two-dot range (F64).

## 5. Phases

### P0 — Copy and withholding (one PR, no new surface)

Names in the rail's accessibility tree and the hover-slide (D9, F1); _Store_ everywhere (F4); _coding agent_ and _Helmsman_ in every operator-facing string (F9, F10, F11); Repos tab, code-repository option and hosted-only settings tabs withheld where their lane or edition is absent (F12, F13); the connection notice silent on a fresh chat (F2); the realtime origin in `connect-src` (F5).

### P1 — The machine and the credentials on the surfaces (D1, D8)

A machine card on This Computer: hostname, paired state, executor last seen, the coding agent's label, with pair and unpair (F8). A _This computer_ section in the Workbench: folders with mode, commands and publish prefix, the agent (F14). The connect command per edition (F7, D5). Credentials as a rail entry, linked from the model picker, with the picker saying which providers are usable (D8). One reader in the product package for the machine block; the same block Helmsman reads.

### P2 — The design pass (D2, D10, D11, and the questions below)

One pass over the shell so the rail, the Workbench, the operator panel and the chat's empty state are used as one system rather than four. It decides, with a prototype each: whether there is a home across spaces and agents, with a space's chat as that space's landing; whether the Workbench opens by default at desktop width and what it costs; what the empty chat shows when the Workbench carries the guidance (F3, F6, F15); where the operator panel sits and how it opens when something arrives; which settings tabs are dead or hosted-only. Recorded inputs: the walkthrough findings, the Full Circle round's cards and pauses, and the checklist lines from D2. Exit: a written layout with the questions answered, and P3's tickets cut from it.

### P3 — First run as state (D2, D12)

The checklist derived from the space: credentials, paired, folder, local skills, GitHub, embeddings. Shown in the Workbench and after _Create workspace_ in place of "ready to run agents" (F6), pointed at from the empty chat (F3), and given to Helmsman as data in the machine block so its first answer links the surfaces (F9). The Store's local shelf first (F10). The last conversation offered on opening a space's chat (F15). Embeddings per D12: provider and model chosen from present credentials, the lexical-only state visible, re-index on switch with progress.

### P4 — The coding agent's boundary and the branch it may extend (D7)

Ref snapshot before a commission, refusal of a result that moved any other ref. Local Publish appends to an existing branch when `branch` names one, with the commit's base required to be that branch's head; the skill's description says a fix lands on the branch it reviews.

**Delivered**: a commission takes `base` — a branch, tag or commit — and starts its checkout there, reporting it as `baseSha`; `host.file.patch` takes `commit.baseSha` — a sha, never a branch or tag name — and appends one commit to an existing branch only when that base is the branch's head, refusing a stale base, a branch that moved and a branch some checkout has open, never merging; every run's local branches and tags are read before and after it and reported as `refChanges`, whoever moved them, and no run is refused for them; a `reference-transaction` hook the executor owns (git 2.28 or later, below which a commission is refused) refuses the coding agent's ordinary git when it would create, delete or move one, scoped by identity to the connected folder's repository so the executor's own tests run inside a commission; a call that names its own hooks path or pushes locally is not refused, and what it moved is on `refChanges`; the run's `.aflow/` scratch never enters its diff; a fresh branch is created at the commission's base; Local Publish takes the commission's `baseSha` and binds it to `commit.baseSha`, reads the repository through the space's GitHub binding before its approval so a credential that cannot see it fails the run before anything is pushed, and shows the commit — sha, branch, message and files changed — on that approval; a commission's `base` of the form `<remote>/<ref>` naming one of the folder's remotes is fetched before it is read.

### P4b — The loop runs without a hand on it (F21, F24, F25, F27, F29, F31, F32)

The commission → review → fix → publish loop has been walked end to end on the public repository; what stopped it each time was the operator, not the work. The runner waits for its own shutdown and says when it has stopped, refuses a port another runner still holds, and starts the host lane once an exiting executor has gone (F21, F31, F32). A publication reviews the range it is about to push before it asks for the approval, so a Helmsman waiting on it has nothing to run in parallel (F24); a run started once is one record (F25). A kept coding-agent session lives beside the run rather than in the executor's memory, so a restart does not drop it (F27), and `applies` is judged against the base the commission named (F29).

### P4c — The loop's mechanics, in the order that keeps each step tidy (F24, F25, F27, F29, F34, F35, F37, F38, F40, F41)

Three slices, each commissioned through the loop itself. **Housekeeping first**: a run removes its worktree when it ends, a kept session's worktree lives exactly as long as the session, the executor prunes at boot whatever earlier runs left registered in a bound folder, and `applies` is judged against the base the commission named. **Then the publish skill**: it declares its concurrency so a publication waiting on its approval blocks nothing; it reads the repository through the binding before the approval, so a credential that cannot see it is learned about before the push and named; it takes one `repository` input, a name or a URL, normalized; the commission's sha carries one name at both layers; the approval carries the commit — sha, message, files, diff stat — and the latest review verdict as data, and the card renders the pause prompt. **Delivered so far**: the housekeeping slice (#20); the publish skill's inputs, concurrency, repository read and approval preview (#23); the patch by reference (#26); D13's asynchronous start, session waiters and wakeup events (#33); the run's scratch out of its diff, the fresh branch at the commission's base and the ref guard scoped to the folder (#36) — a restart takes away only its own detached checkouts, waits for the policy, and a continued turn keeps its base. **Then D13**: the asynchronous start, the session inbox, delivery at settle, the wakeup card and the rate knob, with the cybernetic-runtime's existing waiter and `WorkflowRunWakeupEnvelope` as the pieces already built.

### P4d — D13 as it lands (F24, F25, F48)

`wait` on `workflow.run.start` is declared and never read: every start parks the calling step until the child settles, so nothing is asynchronous today, while the inbox already half-exists — a message posted to a running session is read at the next turn boundary by the agent-turn builder, and one posted to an idle session wakes it. The slice completes that shape rather than adding a second one. `wait: 'none'` returns at once with the run id and how the outcome arrives; the waiter it registers is scoped to the session, not to a parked step, and a waiter with no parked step appends a wakeup event to the session's event log — the `WorkflowRunWakeupEnvelope` that already exists — instead of logging and dropping it. The turn builder reads pending wakeups the way it reads new room messages, so a running turn sees them at its next boundary and a burst makes one turn; an idle session (paused at its prompt) is woken by a wakeup as a room message wakes it, under one rate constant, coalesced. The blocking modes keep parking as before, and a session parked on a child cannot be resumed as if it were awaiting an operator. The chat renders the wakeup as a card that says which run spoke and why. `wait` keeps its default until the D10 measure says the asynchronous start is what Helmsman reaches for unprompted; the op's own hints say when it is. The nested-reference collapse (F48) is fixed in the same resolver, with the two call shapes that failed as its tests, and the 32 KB refusal says what does travel — a reference — rather than a path that does not.

### P4e — The card, the scan, and the hand (D14; F49, F54)

After D13 lands: the chat renders a run's wakeup as a card that says which run spoke and why, and the live coding-agent card folds into the transcript when its run settles (F49); the executor never sweeps its own `.aflow/` scratch into a run's diff (F54), and a store error while reading one wakeup neither hides the others nor strands an idle session. Then D14: the folder's push posture, the publication reading the latest review of the head it pushes, and the secret scan before the push.

**Delivered**: the push posture (#41) — `always`, `never` or `unless-unreviewed` on the connected folder's branch policy, set by `connect --push-approval` and changed by `harness push-approval`, carried in the host inventory and the machine block, and read by Local Publish through `host.binding.inspect` (`host.binding:read` in every system profile); under `unless-unreviewed` the publication starts the catalog's Local Code Review, as the Store installed it and named by its catalog id, over its own `baseSha..sha` and waits for it — `approve` or `comment` skips the approval, `request_changes` or a review that failed, paused or never started asks, and a run started by a task may itself start runs only two levels deep; the push sends `<sha>:refs/heads/<branch>`, never the branch by name, and `workflow.run.latest` is gone with the review-of-a-head it served. Then the scan (#42): `host.commit.scan` (`host.commit:read` in every system profile) reads the lines every commit of a `<baseSha>..<sha>` range adds — every commit, not the net diff, since the push carries each — from the repository's objects alone, and matches them against named rules: private key blocks, AWS key ids and the secret keys beside them, GitHub, Slack, Google and Stripe live keys, JWTs, a random-looking value under a secret, token, password or api-key name in any text file — quoted, or bare as YAML (`api_key: …`), `.properties` (`db.password=…`), shell (`export API_TOKEN=…`), compose (`- POSTGRES_PASSWORD=…`) and `.npmrc` (`_authToken=…`) write it — and the same value given to such a key in a file named `.env`, `.env.*` or `*.env`, named there by the `.env` rule. A value is weighed only when it is 16 to 512 characters with Shannon entropy above 3.5 bits, and never when it is all hex (shas and digests), a URL, a path, a template or variable reference, a member access (names of at most 32 characters joined by dots, the first lower-case, as `pricing.promptPer1M`), a placeholder (`example`, `changeme`, `xxx`, `test-`, `dummy`), words joined into a name, a typed sequence, or base64 of printable text; over this repository's own tree the rules find nothing, and a test holds them to that. Every rule is linear in the line — names anchor the assignment pattern, values are bounded, and an unbounded run is entered only at its first character — and a test times each against megabyte lines. The reader holds at most 64 KB of any line, however long; a longer added line is not matched. A file that is binary, has a NUL byte in an added line, adds more than 1 MB in one commit or adds a line over 64 KB is listed in `unscanned` with that reason, its findings so far kept, and `clean` means every file was read whole and nothing found. A file whose added lines are a Git LFS pointer — its `version https://git-lfs.github.com/spec/` first line, or the `oid sha256:` line a changed pointer adds — is listed with reason `lfs`: the commit holds the pointer, and the bytes the operator's git uploads on push are not there to read. Each commit's headers — author, committer, `mergetag`, and any other — and its message in the range are read as texts of their own — from the commit objects, all through one `git cat-file --batch` cut by the size it states for each, since a formatted message stops at a NUL byte and a commit made with `hash-object` can hide text past one — and reported as `<sha> (headers)` and `<sha> (message)` with the line; a NUL in a message makes it `unscanned` with reason `nul-byte`, as in a file; `host.commit.scan` also takes `texts`, named texts that leave with the push, and Local Publish passes the pull request's title and summary as `pull request title` and `pull request summary`. A finding in a message or a text fails the run as one in a file does, and one too long to read is unscanned. Merges are read against their first parent, so lines a merge adds resolving a conflict are read. A line ending in a comment that carries `aflow-scan: allow` — the marker the last thing on the line, after `//`, `#` or `--` set off by a space, or inside `/* … */` or `<!-- … -->` — is listed in `allowed` by file, line and rule instead of `findings`; the same words in a string literal, a URL or anywhere else do not count. That includes a string the line leaves open: the scan tracks quote state along the line (`"`, `'`, `` ` ``, backslash escapes, an apostrophe between two letters or digits read as a word's) and honours the marker only where its comment leader is outside every string, so ``"…" + ` // aflow-scan: allow`` is a finding. The limit is that the state is the line's own — a string opened on an earlier line is not seen. Allowed is never cleared: whoever wrote the line could have written the marker, so `clean` means nothing found, nothing allowed and nothing unscanned, and an allowed line turns a stop into a question for the operator and nothing more. The scan returns at most 50 of each list and counts the rest, refuses a range over 64 MB or 120 seconds rather than clearing part of it, and never returns, logs or stores what matched. Local Publish scans after making its commit and before the review, the approval and the push: a finding fails the run there, naming files, lines and rules and saying the branch stayed on the machine, and nothing is pushed — a commit carrying a secret is never handed to the review's coding agent either. A scan that found nothing but could not read every file, or marked a line allowed, starts no review and asks the operator whatever the posture, `never` included, the approval naming each unscanned file and why and showing each allowed line; only a range the scan cleared may skip the approval under `unless-unreviewed` or `never`. The posture is read only over a cleared range, so wherever the approval asks the push follows the operator's decision alone: a decline pushes nothing under any posture. `unless-unreviewed` is the default with it. The policy file holds only a posture the operator chose — `connect --push-approval`, or `harness push-approval` — and an absent one resolves to the default wherever the posture is read, so nothing that rewrites the file writes the default in and a later change of default reaches every folder that never chose. A folder whose file names `always` because `connect` or a CLI verb wrote the resolved default since #41 keeps it until `harness push-approval` changes it. The push sends `<sha>:refs/heads/<branch>` and so every ancestor `origin` lacks, so the scan and the review read what the push would add rather than the commit alone: `host.file.patch` takes the publication's `base` as `commit.pushBase`, fetches `<base>` from `origin` before anything is made — reading where it is from that fetch's own `FETCH_HEAD`, never from `refs/remotes/origin/<base>`, which a narrowed fetch refspec leaves where it was, and refusing unless `FETCH_HEAD`'s first line names both the branch and the URL of `origin` (`git remote get-url origin` under the operator's transport config, credentials, trailing slashes and one `.git` taken off as git does when it records one), so neither another fetch nor a same-named branch fetched from another remote is read as origin's base — and reports `pushRange`, `<origin base sha>..<sha>`, beside `baseSha` — an operator's local commits not yet on `origin` are scanned and reviewed with the publication's own. `host.commit.scan` returns a receipt for a range it found no secret in — the folder, the range's base and last commit as full shas, whether the scan cleared it or the push has to ask, and when — signed with a key the executor draws at start and never writes down, valid there for a day. Every push `host.process.exec` allows carries `pushBase` and `scan.receipt` beside its argv and is checked in its own step, just before git is spawned: the push must name `origin`, `git remote get-url --push --all origin` must be exactly `origin`'s fetch URL — a `pushurl`, a `pushInsteadOf` rewrite or a second `url` would send it where its base was never read — and the executor fetches `<pushBase>` from `origin` the same way and requires the receipt to be for exactly `<that commit>..<the refspec's source>`, so a receipt over `<tip>..<tip>` or any range the caller chose that starts above `origin` clears nothing the push carries; otherwise the push fails naming both ranges, or the URLs, and the publication has to run again. A base that moved either way since the scan fails it: forward needs a scan of the range as it is now, and a base rewound on `origin` during the review — the usual way a leaked secret is taken back — would have the push send again the commits the scan left out as already there. `origin` moving in the moment between that fetch and git's own push is the one window no check from the machine closes. A range whose scan asked — a line marked allowed, a file not read whole — is pushed only on Plan 253's write-approval grant, and so is every push from a folder whose posture is `always`, whatever its receipt says. The operator's resolve of the `approve-push` human task, the authenticated boundary, mints it from the call the server resolves from the task's `actionPreview` — the push's folder, refspec and receipt — keyed by tenant, run and the hash of exactly that push; an `approvedCall` from the client that differs from that call is refused, naming where, and nothing is approved. A copy test over the product package for the withheld words on local surfaces; edition-gating tests for Repos, code-repository and the hosted-only tabs; a connection-notice test for the fresh-chat case; the machine-card reader tested against a space context with and without a machine; a ref-snapshot test with a planted `git branch -D` inside a commission; a Local Publish test for the existing-branch case; a golden transcript for the first question in a fresh local workspace; memory tests for write-without-provider marking, lexical-only search reporting, and a provider switch re-indexing while search stays available.

## 9. Open questions

- A home across spaces and agents, or straight to a space's chat: decided in P2 with a prototype, not here.
- Whether the appliance CLI is the executor binary itself (`aflow-host connect`) or a thin `aflow` command that fronts it; pairing already writes `~/.aflow`, so the name is the only decision.
- Whether resuming the last conversation on open is the default for every local workspace or only a personal one.
- Whether an embedding model is chosen per provider (each provider offering its own list) or once per space with the provider implied; D12 assumes per space with the provider's models offered, and re-index cost is the argument for keeping the choice rare.
