# Plan 315 — The local edition's first run: a person and a Helmsman who can both see the machine

**Status:** 🌱 design · **Depends on:** the local operating model (delivered through publication; the archive's 313) · **Companion:** the design pass in §5 P2, which decides layout questions this plan records but does not settle

## 0. How this plan is built

From one walkthrough of the local edition as a new user, in a fresh workspace, on the development stack: create a workspace, ask the first question, find This Computer, the Store, Skills, Integrations, Settings, the Workbench, then open a long conversation. Each finding is recorded with the surface it was seen on and the shape of its fix; the phases group the fixes by the surface they change, smallest first. Layout questions the walkthrough raised but cannot answer are recorded for one design pass rather than settled piecemeal.

## 1. Problem

A person installs the appliance, opens a workspace and is met by a hosted product: a rail that names nothing until it is expanded, an empty chat that suggests skills and integrations, a "workspace ready" step that names agents, a Store led by trading and Kaggle, an Integrations page offering repository designations for a lane that is absent here, a connect flow that assumes a source checkout, and credentials buried in a settings tab although most of the product is blocked without them. Nothing says what this computer is, whether it is paired, which coding agent it has, or which folders it reaches. Helmsman is in the same position: it answers the first question well but cannot point at the surface to use, and its own Workbench shows it nothing about the machine.

Memory has the same shape of problem underneath: embeddings need a provider, and today they either ride a platform credential or fail quietly, which leaves memory unsearchable without a word to the operator.

The loop delivered by the local operating model works. Reaching it from a first run takes knowledge the product does not give.

## 2. Decisions

**D1 — The machine is a first-class object on every operator surface, and the same object Helmsman reads.** This Computer, the Workbench and the first-run checklist all render the host inventory the space context already carries (`hostname`, `runtimes`, `harnesses {id, label}`, `observedAt`) and the folders with their posture (`mode`, `allowsExecution`, `branchPrefix`). One reader, three places. When a surface and Helmsman disagree about the machine, that is a bug in the reader, not two facts.

**D2 — First-run guidance is state, not prose, and it lives in the Workbench.** The checklist is derived: credentials present, paired, a folder connected, the local skills installed, GitHub connected, embeddings configured. Each line links to the surface that changes it and disappears when done. The Workbench holds the guidance and the controls; the empty chat only points at the Workbench. Helmsman gets the same state as data in its space context; its prompt gains no sentence.

**D3 — Hosted-only affordances are withheld where their lane is absent, by the derivation the Store already uses.** The Repos tab and the code-repository option in Integrations, hosted-only settings tabs, and any listing whose operations name an uncomposed lane are absent on the local edition, not shown and refused. One rule (`isOperationComposed` / `uncomposedListingReason`) decides.

**D4 — Words.** Operator-facing copy says _coding agent_, never _harness_; _Store_, never _Shop_; _Helmsman_ or _the assistant_, never _cybernetic agent_. Internal identifiers keep their names.

**D5 — The appliance's connect command is the appliance's.** The paired daemon ships a CLI; This Computer prints `aflow connect <code>` on the appliance and the `yarn workspace` form only on a development stack, decided by the same descriptor that decides the edition.

**D6 — A fresh chat says nothing about its connection.** The connection notice speaks only for a session that once was live. The transport's own phase is what a notice reads, not a session subscription that does not yet exist.

**D7 — The coding agent may not touch refs it did not make.** A commission's worktree shares refs with the operator's repository; the executor snapshots refs before the run and refuses a result that changed any ref other than the worktree's own detached HEAD. Local Publish, in turn, takes a branch that already exists and appends to it, so "on the same branch" is a request the skill can honour rather than one the agent works around.

**D8 — Credentials are a rail entry, not a settings tab.** Most of the product is blocked until a model provider key exists, and more will be. Credentials get their own entry in the rail, linked from the model picker beside the composer; the picker keeps the model and reasoning choice and gains a line that says which providers are usable and which need a key. The remaining settings tabs stay where they are: each is optional and situational, and the pass in P2 reviews them for what is dead.

**D9 — The rail expands on hover and pins on click.** Hovering slides the expanded rail over the content, so names appear without a click and nothing moves; clicking pins it open and pushes the content, as today. Names are always in the accessibility tree, expanded or not.

**D10 — The Workbench is open by default on a desktop, and it is cheap to keep open.** Its sections read the same queries the chat already holds; nothing in it polls, and a section that is empty renders one line. Whether it opens by default is a width rule, not a preference.

**D11 — What needs the operator has its own place.** Approvals, questions, gates and proposals gather in one panel that is collapsed when empty and opens when something arrives; the chat inlines the same item where it occurred, as now. One source, two views.

**D12 — Embeddings use the operator's credentials, and their state is visible.** Memory's embedding provider and model are chosen by the operator per space among the providers whose key is present, with a default that follows the chat provider when it offers embeddings. No embedding is ever attempted against a platform credential on the local edition, and none fails silently: a memory written without embeddings is marked as such, memory search says when it is lexical only, and the checklist carries the line. Switching the embedding provider or model re-indexes, and the switch says so and shows progress; a space keeps searching lexically while it re-indexes.

**D13 — A skill run is asynchronous, and its outcome reaches the session as an event, never as an interruption.** `workflow.run.start` returns the run id at once and says how the outcome arrives; the waiter is registered against the session rather than a parked step. Every session has one inbox — operator messages, run wakeup envelopes, approval decisions — that producers append to and nothing polls. Delivery is at the turn boundary: when a turn settles with the inbox non-empty the next turn starts now with the items as data, coalesced; a session idle at its prompt is resumed by a wakeup as a turn with no operator message; a running turn is never interrupted for information (interruption stays what it is, control: cancel, stop, revoke). The envelope is data in the transcript, rendered as a card that says why the agent spoke unprompted, and event-driven turns are bounded by one rate knob per session. This is the session-sized form of the mailbox Plan 299 specifies for the resident mind; the two are one table with different owners, and every measurement taken here — how often the agent speaks unprompted, whether a wake reads as help or as noise, where the rate knob sits — is one the mind needs before it lands.

**D14 — The push asks for a hand only when nothing else has looked.** The approval before a publication's push is a posture on the connected folder, not a step of the skill: `always`, `never`, or `unless-unreviewed`, under which the publication runs Local Code Review itself over `baseSha..commitSha` — the commit it just made, named by two shas so no branch name and no earlier review is involved — and pushes without asking when that review returns `approve`, pausing for the operator otherwise (`comment`, `request_changes`, or a review that could not run). The verdict is tied to the exact commit by construction, and the push sends that sha, not the branch name, so a branch that moved in between carries nothing unreviewed. A review of a head cannot precede the publication that creates the head, and a verdict the reviewing agent writes into its own result cannot clear a gate; both shapes were tried and refused in review. What the gate guarded is already guarded elsewhere: the push can only create or advance a branch under the folder's publish prefix with an argv the skill pins, and nothing reaches the base branch without a pull request, its checks and the operator's review. What the gate never guarded, a secret in the diff leaving the machine, is guarded by a scan over everything the push would add — `origin/<base>..<sha>`, not only the commission's own commits — before the push; a finding fails the publication, a file the scan could not read whole makes it ask, and a line an operator has marked as allowed still makes it ask with the marked lines shown, because the agent that wrote the line can write the marker too. The default becomes `unless-unreviewed` with the scan. The merge stays the operator's.

**D15 — A fix appended to a branch its base has moved past carries the base with it, as one merge commit whose resolution the coding agent made.** Nothing in the loop merges today: a fix commissioned from a branch `main` has moved past carries none of `main`'s changes, and the branch learns it conflicts only from GitHub after the push. A commission therefore takes `mergeFrom`, a `<remote>/<ref>` naming one of the folder's remotes — the publication's `origin/<base>` — fetched and resolved before any checkout is touched, as `base` is, and refused naming it when the remote is not the folder's or the ref cannot be fetched. Once the checkout stands at `base`, the fetched commit, unless the checkout already holds it, is merged in: `--no-ff --no-edit`, under the operator's commit identity, as the publication's commit is, with replace objects, hooks and the operator's global config off and the conflict style and `rerere` pinned, so the merge is a function of its two parents and nothing else. That identity is the one thing a commission with `mergeFrom` needs that a commission without it never did, so where neither the repository's config nor the global one sets it, the commission is refused before any checkout is touched, naming the `user.name` or `user.email` to set. A merge that conflicts is committed, so the agent's turn begins on a tree that shows what needs resolving, and the record of each conflict is what git names, with its kind: `content` where both sides changed a file and `add-add` where both added it differently, each left with markers, and `modify-delete` or `delete-modify` where one side deleted a file the other changed, which leaves no marker at all, so the merge commits it deleted — the base's deletion holds by default, which is the outcome this gate exists to protect. The task names each conflict with its kind and what resolving it means; a deleted one reads "deleted in the merge; restore it with the changes it needs, or leave it deleted". A merge that conflicts in a file both sides hold and git merges as binary leaves no marker to resolve — only one side's bytes — so it is refused before any turn runs, naming the files and saying the merge has to be made by hand. The result reports `merge: { from, conflicts: [{ path, kind }] }`; the diff is taken against the merge commit, so the patch holds the agent's work and its resolution and none of the base's own changes, while `baseSha` stays the branch's head as found, which is what the publication checks the branch against. A continued turn keeps the session's checkout, merge and all. The publication is handed the sha the commission reported as `commit.mergeFrom`: on the branch's head it fetches that sha from `origin` where the folder lacks it, re-makes the identical merge, applies the patch on top and folds both into one commit under the publication's message — parents the old head and `mergeFrom`, tree the agent's. A patch that does not fit the re-made merge is refused as an apply conflict naming the files. The re-made merge records the same conflicts, and the publication refuses a `content` or `add-add` file that still holds the merge's markers, naming the path and the kind, with nothing committed. Only those files are read for markers, so a fixture or a document that holds marker lines of its own and was never in conflict publishes. A `modify-delete` or `delete-modify` file needs nothing of the patch, because no decision about it can be invisible: one the patch leaves alone is published deleted, the deletion accepted, and one the patch brings back is published restored, the file kept — either way it is what the tree becomes. Merging is the commission's decision, made where an agent can resolve it; the publication repeats it and decides nothing. The review reads a branch its base moved past as what the branch adds — the three-dot diff from the merge base of the range's two ends — while its commit list and the scan keep the two-dot range (F64).

**D16 — A publication runs the folder's checks before anything leaves the machine, and the pull request's checks remain the proof.** The review a publication runs reads a diff and runs nothing, so the first autonomous push went out on a reading alone (F63). What a repository counts as passing is the repository's to say and the operator's to choose, so the connected folder's branch policy carries `checks` beside the push posture: one argv, run from the repository root, set on the machine with `aflow harness checks <folder> -- <argv>` and written only when chosen, as the posture is. It is the operator's argv, never the workspace's — no operation takes a command to run as a check, so a run cannot choose what clears its own commit — and it lives on the branch policy because only a folder that publishes has a publication to hold back. `host.commit.check` takes the folder, the commit and the base it is measured against, prepares a detached checkout at the commit as a commission's is prepared — the folder's dependencies linked, so nothing is installed — and runs the argv there under the sandbox a coding agent runs in: egress closed, the folder's own tree not writable, `AFLOW_CHECK_SHA` and `AFLOW_CHECK_BASE` in its environment so the repository's own script knows what changed. Egress stays closed because that is where a check could carry the folder off the machine or pass on an answer from outside it. Loopback is the sandbox's own or closed, never the machine's, because the machine's holds the stack's services and the check runs code a coding agent wrote: on Linux the adapter gives the check a network namespace of its own, so a test binds, accepts and connects to its own server there and finds nothing else; on macOS the adapter's only loopback grant, `allowLocalBinding`, also admits a connection to every localhost port — the stack's Redis, which takes no password and holds write-approval grants and run state, its Postgres and its API — and a sandbox profile can name one port or all, never the command's own, so loopback stays closed and a test that serves itself there fails under the check. This repository's script runs the tests a change can reach, not every test of every workspace that reads it. A test runs when its imports reach a touched file: each import is followed to the module that declares the names it takes, through every re-export on the way, and on through that module's own imports. A namespace, side-effect, dynamic or `require` import takes the whole module; a type-only one is not followed. A touched index reaches a name it passes on only when the change moved where that name comes from. The candidates are the tests of the touched workspaces and of every workspace that reads a touched package, directly or through another. So a contract change still meets its consumers, while a test that cannot observe it does not run. It runs under `checksTimeoutMs`, a knob on the same policy whose default is sized for a type-check and a scoped test run rather than a file read, and a check that outlives it fails naming the knob. Standard output and error are kept in the order they came, the tail where they run long, stored as a payload, and the last few kilobytes are returned inline; the checkout is removed whatever happened. A folder that declares none answers `passed` with `skipped` and says that nothing ran. A check executes code, so its access is `write`. Local Publish runs it after the commit and before the scan, bound to the commit's sha and `pushRange`'s base: a failure fails the run with the tail in the failure message and the output as a payload, and nothing is scanned, reviewed or pushed. That order is the skill's, and it is not what holds the promise: the checks are a receipt the push requires, not a task the skill orders. A copy of the skill without the check, or any workflow that scans and then pushes, would otherwise push unchecked, so the check is closed the way the scan was. Where checks ran, `host.commit.check` returns a check receipt beside its result — signed by the executor process with the scan receipt's key under a distinct kind, over the folder, the commit's sha, the base's sha, a hash of the checks' argv as declared, whether they passed, and when, valid for a day and carrying none of their output — and a push from a folder whose policy declares checks carries it as `check.receipt` beside `scan.receipt`. In the push's own step, before git is spawned, the gate requires a receipt issued by this executor since it started for exactly the refspec's source, the base it measured and the argv the folder declares now, with the checks passed, and refuses any other by name with nothing pushed; a folder that declares none needs none, and a push from it that carries one is refused saying so. A passing check is evidence from this machine about one commit against one base. It is not the CI the pull request runs, which stays the proof and the merge's condition.

**D17 — A restart of the host executor drains instead of killing.** The dev stack restarts the host executor with a signal whenever a source it imports changes, and the executor answered every signal by ending each process it had started and discarding each session's checkout at once, so a merge into the stack's checkout ended every commission, check and review in flight on the machine. Two streams of work share one machine, and the rule that kept them apart — merge only when no harness runs — was kept by a person. The drain is not what SIGTERM means. Every supervisor that stops the executor with SIGTERM or SIGINT sends SIGKILL after a short grace — the dev runner after ten seconds, `tsx watch` after five, launchd after its default — and SIGKILL skips the exit handler and reaches no process in a group of its own, so a drain begun on SIGTERM would leave a harness running unaddressed, holding its provider credential, with its checkout on disk. SIGTERM and SIGINT therefore keep their meaning in full: end every workload, discard every checkout, exit within the supervisor's grace. The drain is SIGUSR2, which only a supervisor that has promised to wait for the exit without a kill sends, and only the dev stack's watcher sends it. On SIGUSR2 the executor stops reading its job stream and lets what it has claimed finish: every in-flight step keeps its heartbeat, the executor keeps its own, and every child process keeps running; it shuts down once the last step has ended. Jobs that a read already under way returns after the signal are run, and the drain waits for them: they were delivered to this consumer, the reclaim skips a consumer's own name, and the host executor's name is the machine's, so left pending they would outlive every restart with nothing to take them back. The executor listens for every signal before either runtime starts, so none lands in a window where it means the default action — which would skip the exit handler and leave a claimed harness's process group running. A step still waiting for its operation's slot is not in flight: the drain gives it back to the job stream unworked, for the next executor, so no coding agent starts here once claiming has stopped and the drain never waits on a queue. The step is already `STARTED`, so the executor keeps its in-flight record alive until it stops, and a restart inside that record's lifetime loses nothing. The drain has a deadline, and it is the started steps' own: the latest instant at which a step's timeout ends it, read again when it falls due, because a step that starts later brings its own — the executor's default stands in from the moment it starts until its own is resolved — and a progress-aware timeout slides its own. A drain that begins with nothing in flight while a read is still under way takes its deadline from the first step that read hands it. Nothing here chooses a length. Past the deadline, on a second SIGUSR2, or on a SIGTERM or SIGINT during the drain, each the word to stop now, the executor does what a signal did before: ends every process it started, discards every session's checkout, and shuts down. What the drain holds open is a harness run, a check and a review; it does not hold a session between its turns, whose checkout the exit discards with every other kept session's, so a merge between the turns of a continued commission still ends it (F74, deferred). The browser runtime stops as the drain begins, so its pages are not held. One line is logged as the drain begins, naming each step in flight and the deadline, and one as it ends, saying how: `finished`, `deadline` or `stopped`. The other executors keep their behaviour, because their steps are short. `tsx watch` does not wait for a drain: it kills five seconds after its signal. So the dev stack runs the host executor under a watcher of its own, which sends SIGUSR2 once per restart, starts the executor again when the drained process exits, and passes on its own SIGTERM or SIGINT as itself. Stopping the stack and `tsx watch` behave as they did before the drain.

**D18 — A commission is a skill, started without waiting, and the machine bounds how many run.** Review and publication are catalog skills and a commission was not: Helmsman called `host.harness.run` itself, a step its conversation waits on for the whole of the coding agent's run — thirty to forty minutes for a slice — so a stream that commissioned did nothing else until the change came back. A commission is therefore a skill, Commission Change, in a bundle of its own beside Local Code Review and Local Publish, started with `wait: 'none'` like any run that takes long: the start returns the run id, the conversation stays free, and the run's end wakes it with the result (D13). The skill is one operation task on `host.harness.run` whose run inputs are everything the operation takes that a brief names — the folder, the task text, `base`, `mergeFrom`, `continueFrom`, `harness`, `model`, `maxTurns`, `timeoutMs` — and its result promotes what the next step takes: `patchRef`, the primary, with `baseSha` and `merge`, which a publication takes as they stand, and `sessionRef`, which a further turn takes as `continueFrom`, beside `applies`, `filesChanged` and `continued`. Its budgets are sized for the work, not guessed: the timeout defaults to the two hours a coding agent may run, because a slice runs thirty to forty minutes and the operation's half-hour default ended one, and the turn budget to several hundred, because every tool call is a turn and a cap sized to a guess ends a run while it is still reading. A run input's `default` is never applied, so the timeout's is made in the task's template. The turn budget's is not, because whether a run can carry a budget is the machine's to know: a harness whose profile has no turn argument — the built-in OpenCode profile has none — refuses any `maxTurns`, so a template that always sent one failed every commission on such a machine and left a brief no way to leave the budget out. The template sends `maxTurns` only when the run names it, and `host.harness.run` gives a run that names none its own default, several hundred turns, on a harness that takes a budget, and no budget on one that does not. `harness` is a run input because a machine offering more than one coding agent refuses a run that names none. The skill runs any number at once and queues none, because each commission has its own checkout. What bounds them is the machine, which runs a coding agent per commission and has only so many cores and so much memory; that limit belongs to the host executor, not to the skill. **D18b — the machine's limit.** The machine's policy holds `maxConcurrentHarnessRuns`, written only when the operator chooses a number (`aflow harness concurrency <n>`, `--clear` for the default), and two otherwise: the machine is usually a laptop that also runs the stack, and two coding agents beside it, each running the project's checks in its own checkout, is what one carries without the stack slowing to a crawl. The host executor admits `host.harness.run` through the executor runtime's concurrency limiter with that number, for that operation alone, and follows a change of the policy without a restart. A run past the limit waits, claimed, for a slot and is never refused; its timeout counts from when it starts. The number is published in the machine's inventory and shown by `host.binding.inspect` beside the folder's push posture and checks. The checks a brief asks for are the folder's own — its tests, type check, linter and formatter, run by the coding agent in its checkout — and the folder's declared checks run again when the patch is published (D16). **D18b's completion** (#62's minor): a run waiting for its slot is scheduled, not started. A step is marked `STARTED`, with `startedAt` and its `StepStarted` event, once it is admitted, so its duration and its timeout count from then and `queueWaitMs` includes the wait; and the stall watchdog reads the live in-flight record of a `SCHEDULED` step as it does a `STARTED` one's, so an executor holding a queued step, or one a drain gave back (D17), vouches for it.

**D19 — The sandbox posture is what the network is, not whether there is a sandbox.** The coding agent and the folder's checks ran under the sandbox a command runs in, and most of the executor's findings in the loop were that sandbox meeting ordinary work: a test that serves itself on loopback (F82), a dependency the agent could not add (F83), a shell whose every command read as failed (F84), a `yarn` Corepack could not fetch (F85), an agent configuration file the agent could not write (F86). Most of it was the network and one temporary file. Taking the sandbox away instead, as this decision first did, also took away what the gates stand on. The ref guard, the scan, the check, the review and the push gate each read their configuration from the machine's host directory (`~/.aflow/`, `hostDir.ts`): push approval, the checks and the posture itself are in `host-policy.json`, and pairing's credential is in `host.env`. An unconfined agent could rewrite that policy, read the credential, write the operator's working tree and its `.git/hooks`, and move a branch by writing `.git/refs` past the ref guard's hook. Gates whose configuration the agent can rewrite protect nothing. So the connected folder's policy gains `sandbox`, `open` or `confined`, set with `aflow harness sandbox <folder> open|confined` (Plan 328 D6 plans its rename to `aflow harness posture`; not done) beside `push-approval` and `checks`. The policy file holds it only when the operator chose it. `host.binding.inspect` shows it, and so does the machine's inventory beside each folder's push posture. A folder that chose none takes `HOST_SANDBOX_POSTURE_DEFAULT` each time it is read. In the local edition that is `open`, with its reason written where it is defined. The posture is held to two reference harnesses, Claude Code and Codex CLI: `open` is no stricter than the one, and `confined` no looser than the other. `open` is the sandbox the operator's own coding tool runs under with every domain allowed — Claude Code's sandbox mode with every domain allowed: the network on, the machine's loopback closed. `confined` is the workspace-write default of the other — Codex CLI's `workspace-write`: the network off. Loopback to the machine is never a job's under `open` or `confined`. `host.harness.run` and `host.commit.check` run inside the sandbox under `open` and `confined`, under one compiled policy, and the posture decides which launcher reads it: under `confined` the adapter's own command line, which refuses every host the policy does not name; under `open` a launcher that admits every host but this machine, so the agent's own search and fetch work and Corepack and the registry are reachable. Nobody enumerates loopback ports. A list of the stack's own services was tried first (F98), and no such list can be complete: the stack's MCP server on 3100 hands the owner's API key to any local session that brings no credential, and `yarn infra:tools` publishes Redis Commander and pgAdmin without a login, so every port the list did not name was a door. Under `open` and `confined` the job's loopback is the sandbox's: on Linux the network namespace's own, where it binds, accepts and connects to its own listeners and the machine's are not there; on macOS none, because the profile's only loopback grant opens every localhost port, so the policy never sets `allowLocalBinding` and a test that serves itself cannot listen there. The `open` launcher's proxy dials from outside the sandbox, so it refuses, on every port, a host that resolves to loopback, the unspecified address or any address of the machine's interfaces, and one that does not resolve. Under `open` and `confined` nothing shared is opened: the system's `/tmp` is writable under neither, because on Linux it is where every job's scratch lives — its checkout, its check worktree, the sandbox settings and status files — and a job able to write it could write into a concurrent job's checkout or a `confined` folder's job. Each job is handed a temporary directory of its own inside its own scratch, as `TMPDIR`, `TMP`, `TEMP` and `CLAUDE_CODE_TMPDIR` (Claude Code writes its shell's working-directory file where that one says, and in `/tmp` otherwise, whatever `TMPDIR` says), and writes it under `open` and `confined`. Everything else is the same under `open` and `confined`. The job writes its checkout and the run's scratch, where its temporary directory is, and nothing else of the system's `/tmp`. The operator's folder is readable, so the checkout can mirror its installation, but it is not writable, and neither is its `.git`. The host directory can be neither read nor written, whatever a harness profile or the machine's tool paths name, and the machine's loopback cannot be reached, so the gates' state is reachable only by the executor. A test runs a command under `open` and under `confined` that tries each of those writes and the credential read, and one under each of the two that reaches for a listener the test holds on the machine's loopback — directly and through the proxy, by address and by name — and is refused, has a loopback server of its own on Linux and none on macOS, and reaches a host off the machine under `open` alone. A test that needs a listener of its own therefore cannot run under the check on macOS: it declares the Vitest tag `listener`, and the check leaves it out there, names it, counts it in the check's receipt and says CI runs it. A check's result and its receipt carry the posture it ran under, signed with the rest. The push gate requires that the receipt's posture equals the posture the check runs under for the folder, which Plan 328 D6 defines as the lesser of the folder's posture and the check's `open` ceiling, as the push runs, and refuses it otherwise as `check_other_posture`, so a receipt from a check run `open` clears no push once the operator has made the folder `confined`; it answers the posture from the receipt, so a push from a folder that declares checks records it as `checkedUnder`. `host.process.exec` stays `confined` under every posture, Plan 328's `trusted` included, because it runs a command an agent wrote, not the operator's tool. The ref guard is still a hook the run's git is told about. A git call that names its own hooks, or a push into the folder, now meets a `.git` it cannot write, so neither moves a branch there; the guard's limits as a hook stay recorded under F56. The lane's boot self-test runs three probes under `open` on the machine: a shell command exits 0, `yarn --version` runs, and a listener the lane holds on the machine's loopback is out of reach. F84 and F85 are retired under `open` by that measurement. F82 is answered rather than retired: a test that serves itself runs under the check on Linux, and on macOS is left out by name and runs in CI. F83 and F86 are not retired: under `open` the registry is reachable, but the installation is still the folder's, which no commission writes, and the sandbox keeps its own protection of agent configuration files. Plan 328 D6 plans a third posture, `trusted`, under which the machine's loopback and Unix sockets are a job's. Under it this paragraph holds in three things only: the compiled filesystem policy, which that plan calls a guardrail and not a boundary; the ceiling `open` of `host.commit.check` and of every harness task, the reviewer's included, except one declaring `posture: folder` in a run an operator message started; and the ceiling `confined` of `host.process.exec`.

**D20 — Every service of the development stack requires a credential, and the sandbox is not the reason.** D19 keeps a job off the machine's loopback, which closes the door F98 found for one caller. It does not close it for any other process on the machine, and the stack's services trusted loopback as a credential: Redis on 6379, which holds the `aflow:write-approval:*` grants the push gate reads, took no password; the MCP server on 3100 gave the owner's API key to any local session that brought none; `yarn infra:tools` published Redis Commander and pgAdmin with no login, Commander holding Redis whole. So each asks for a credential, independently of the sandbox. Redis requires a password, and the password is the machine's, not the checkout's. Every checkout on a machine — each worktree — drives the one Redis container (`container_name: aflow-redis`), so a password minted per checkout is one the running Redis never had: a second worktree's first `yarn start` would fail every service in it with `WRONGPASS`, and its `infra:up` would recreate the container under its own password and break every other checkout. A credential for a shared container lives where the container's other users can all read it and no job can: `~/.aflow/stack.env`, the host directory the sandbox already withholds from jobs, written once by the first `yarn start`, `yarn dev:local` or `yarn redis:password`. `yarn infra:up` hands it to compose, and the Redis service refuses to start without one; the loader every checkout's services read their environment through lays it into that checkout's `REDIS_URL`, which names only where Redis is, so every reader of the URL authenticates without change and no checkout mints its own. The credential reaches every entry point through that one loader — `yarn start`, the dev runner and each root script that starts a service or reaches a datastore, `yarn db:migrate` among them — and it is laid only into a URL naming this machine's Redis, so a checkout pointed at another host never sends it there. A checkout whose `.env` still carries a password of its own is told so by name, and `yarn redis:password` adopts the machine's. The paired machine's identity stays its own, in `~/.aflow/host.env`, where pairing writes it, and pairing hands the machine the address without the stack's password. The MCP server gives the owner's key only to a session that presents the session token `yarn mcp:setup` wrote beside the key, and refuses a session that presents nothing with a message that says how to set it up; the token reaches a client from the operator's environment, never from the repository. The admin tools sit behind the same generated password rather than being documented as open loopback tooling, because the compose file makes that the simpler of the two: Commander needs the Redis password to reach Redis at all, so once the compose file has it a login costs two lines, while an open Commander would be the one page on the machine that hands out everything the password guards. All three publish on `127.0.0.1`. `yarn start` names each service's credential state before it starts anything — authenticating to Redis with the machine's password and naming which of three it found: no password required, the password accepted, the password refused — and stops, by name, on the first and the last, and on a checkout carrying a password of its own. An operator with an existing `.env` or Redis runs one command, `yarn redis:password`. Postgres is the one service left: it publishes on `127.0.0.1` like the rest, and keeps the fixed development credential the compose file has always written. Its generated credential is deferred, not forgotten: `DATABASE_URL` reaches every tool and every Postgres-gated test — migrations, seeds, scripts run outside the dev runner, every `*.pg.test.ts` — so changing it moves all of them and the init script's role setup at once, which is a slice of its own. It holds the API keys a process could add one of its own to, so it is the next slice of this decision, recorded under §9.

**D21 — The appliance survives sleep.** The machine the loop runs on is a laptop, and laptops sleep: one night it went into idle sleep with a commission in flight, briefs were posted in the dark-wake windows macOS opens while it sleeps, and two Helmsman conversations died (F109). Two things failed, and each has its own answer. The first is the machine sleeping under running work, and the answer is **the hold**: while the host executor has a step running it holds a sleep assertion — a child `caffeinate` on macOS, `systemd-inhibit` on Linux — taken when the first step starts and released when the last one settles, never between two that overlap, and ended with the executor. Whether to hold is the operator's, a machine-wide field of the policy beside the harnesses it protects: `on-ac`, the default, holds while the machine is on power, because a laptop held awake on battery is one an operator closed expecting it to stop; `always` holds on battery too; `never` holds nothing. The second is what the platform made of the sleep. Every executor's heartbeat lapses while its machine sleeps, so on waking every executor is missing until its first tick, and a missing executor failed work terminally on every dispatch path — a synthetic FAILED whose classification was dropped on purpose, a session failed outright by a timer, a workflow task given the raw message as its failure reason. The answer is **the wait**: a step or operation task whose executor is missing is parked on its shard timer and dispatched when a look finds the executor back, the looks growing apart up to the heartbeat's own lifetime, as many as span ten minutes on a machine that stays awake, after which it fails as what it is — a transient, retryable outage, its classification kept. A parked step is visible as waiting from the moment it parks, naming the executor it waits for in the run view and the chat, and one whose executor this orchestrator has never seen since it started fails as `configuration`, not retryable, because that executor was never started rather than asleep. The wait is counted in looks rather than in time because a sleeping machine takes none, so a wait it sleeps through is not spent on waking, and a look that comes a heartbeat's lifetime or more late is that wake, counts for nothing and is followed by one more. The classification was dropped to stop one outage entering every step behind it into the retry budget at once; the budget of looks and the growing gap prevent that now, since nothing enters a retry budget while it waits, a lane that returns costs no retry at all, and one that does not costs each step one failure, once its looks are spent. A waiting step is its own completion path, not a stalled pickup: orphan recovery and the stall watchdog leave it alone while its timer lives, however long that is, and arm a timer that went missing again rather than fail the step. The host lane is no exception, though its executor is the operator's to start: a sleeping machine is exactly the case where the executor comes back. **The cold restart** — a sleep long enough that the stack itself comes back cold, its orchestrator restarted and the conversations it held to be recovered — is not in this decision. Whether it happens and what recovery costs are to be measured first, and it is a slice of its own.

**D22 — Local Publish decides by the rounds rule whether a review's findings want a fix round, records the decision, and its push gate follows it. `fix_before_merge` keeps the branch local, `publish_as_is` pushes without asking over findings no more severe than minor and asks the operator over a blocker or a major. No model is asked, and nothing is left undecided.**

The publication push approval must remain resolvable for long decision prompts. Human-task pause builders bound `pausedTaskInputContract.prompt` to the schema's 20,000-character ceiling and retain the full decision text in `resumePrompt`. Operator resume refuses every resolution when no contract surfaces, naming the paused reason; task-backed pauses also refuse `acknowledge` before claiming a resume lease, except for `needs_credentials` and `needs_capability`, whose acknowledge re-executes the blocked task after out-of-band remediation. Tests cover oversized human prompts through contract surfacing, all modes with a missing contract, and generic task-backed acknowledge with and without a contract, and credential/capability acknowledge re-executing the blocked task.

A review with findings woke a Helmsman turn to choose whether a fix round was worth it. That choice is asked many times with the same question, which is what a decision step is for (Plan 316 D2), so the skill asks it through `ai.decision.decide`, with the question written once in `publishLocalChangesDecisions.ts`. The fix round itself is not the publication's: it belongs to the conversation today, and to the shepherd once Plan 321 P1 lands. That model step (`decide-after-review`, at Jev's 0.80) is gone. Measured six times on an approving review with minors, it answered at 0.24–0.46 and never cleared its bar, so every such review paused on the operator for a decision the rounds rule already makes. The rules now make the whole decision, and the question stays in `publishLocalChangesDecisions.ts` for the measurement alone.

**After a failed check, no decision.** The first build also chose what follows a failed check: a rerun, a fix commissioned and republished, or a stop for the operator. That decision was removed pending labelled `operator_install_mismatch` cases (Plan 316 §7), and its fix round (`fix-checks`, `republish-after-checks`) went with it. A check lost only to tests running out of their time is run again by rule (`testTimeouts`, `recheck-commit`). The check step itself breaking — the executor, the checkout of the commit, the fetch of `origin`'s base — fails at `check-commit` saying the checks could not run, with no fix prescribed. Any other failure fails the run at `checks-failed` (`workflow.run.fail`, a step-only primitive that fails its task with the reason it is handed), with the checks' own account. That wakes the conversation as a failed check did before the decision. With the first run no longer failed by its projection, `host.commit.check` stopped reporting `clearedOrRetriableSha`, which nothing read any more; `failingGuard` is read by the check's own summary, which names the step that failed. The failure says what happened — the checks did not pass, nothing was scanned, reviewed or pushed — and prescribes no fix to the change, since a failure on the machine is not the change's.

**After a review with findings, recorded and followed.** `settle-after-review` (`workflow.run.decide`, its rules in `publishLocalChangesAfterReview.ts`) decides every review that finished by the rounds rule, over the verdict, the severities and the publication's `round`, and asks no model. A slice gets one fix round. A verdict short of `approve` — a `comment` (the review could not judge) or a `request_changes` — is `fix_before_merge`, whatever it found. An approving review whose findings are all nits, or that found nothing, is `publish_as_is` with the reason "nits-only review: the rounds rule ends the rounds". An approving review with a minor or worse is `fix_before_merge` on the slice's first publication, and `publish_as_is` once its fix round has run, the findings carried open on the pull request; over a blocker or a major the gate then asks the operator (below). Whether the round ran is never inferred: it is `round`, a declared run input — 1, the default, for the slice's first publication, one more for each publication of a fix round — which the Helmsman passes, and a missing one reads as the first. Asked of a model, approve-plus-one-nit reviews were answered `publish_as_is` at 0.24 (review 53cebf4b) and 0.42 (review 5d02723c), and approve-with-minors never cleared 0.80 in six measurements; the gate paused for the operator every time over an answer the rule already gave. `describe-pr` records the decision with the findings, on the pull request and as the run's `afterReview`: `fix_before_merge` or `publish_as_is`. It is absent where the review did not finish, since there was nothing to decide on. The pull request lists the earlier rounds' findings as the brief passed them, closed and left open, and tells this review by its own summary, which names each of its findings once. What the run hands on as `findings` (`PullRequestFindingsSchema`) is the latest review's open findings: this review's where it finished, replacing the earlier rounds', or else the open ones it was passed. A round's list replaces the last rather than appending to it, so the list the next publication of the branch takes never grows round on round. It is also held within half of the 32 KB that publication's inputs carry together (`HANDED_ON_FINDINGS_MAX_BYTES`): at most `HANDED_ON_FINDINGS_MAX_COUNT` findings, the most severe first, each cut to `HANDED_ON_FINDING_MAX_BYTES`. The cut is measured in serialised bytes, not characters, since one character can serialise to six. A test holds this for the largest review there can be: fifty findings of the longest claims and paths, in the characters that serialise largest. Where the bound leaves any out, describe-pr says how many as `findingsLeftOut`. The list serves the next pull request's record and nothing else: a fix round is briefed from every finding of the review run, which the run names as `reviewRunId`. The pull request's text keeps every finding whole. The first build also judged each finding with a `yes_no` before the round was weighed. The measurement took that step out: no decider reached the target without abstaining on most findings.

**A publication never starts a publication.** The first build ran the fix round inside the publication: a commission, then the fix published as a child publication. That nesting is out, for two reasons. A task-started child that pauses is cancelled: its waiter answers the task with the pause and cancels the child (`waiters.ts`), so a child publication stopping at its own push approval could never be approved. And the chain of task-started runs is bounded (`MAX_WORKFLOW_RUN_DEPTH`), so each nested round used up depth the chain could not spare. Raising the bound to three for two rounds only moved the edge. `MAX_WORKFLOW_RUN_DEPTH` is two again: a publication and the review of its own commit. The skill starts exactly one run, that review, and no skill in the catalog starts a publication; a test over the graph holds both. When `afterReview` is `fix_before_merge`, the conversation — or the shepherd — commissions the fix on the branch (`base: <branch>`), and publishes the branch again as a publication of its own, passing the run's `findings`.

**The push gate reads the decision.** `decide-push` (`workflow.run.decide`, its rules in `publishLocalChangesGate.ts`) runs once `describe-pr` has recorded the answer, and the first rule that holds decides `push`, `ask` or `keep_local`. A range the scan did not clear asks, and so does a folder whose push approval is `always`; `never` pushes. Under `unless-unreviewed` the answer on the findings stands in for the verdict. `fix_before_merge` keeps the branch local: no approval is asked, nothing is pushed and no pull request is opened or rewritten, and the run completes with the decision, its findings and `reviewRunId` in its output, from which the conversation or the shepherd runs the fix round. `publish_as_is` pushes without asking, as an approving verdict does, and the pull request lists the findings it leaves open — under the decision, the override record, the checks and the gaps, so no length of findings pushes those past GitHub's limit, each finding whole as far as the limit leaves room and the rest counted — but only up to the severities it weighed: a blocker or a major among the findings asks the operator whatever was decided, an override's `publish_as_is` included, since the decision stands in for an approving verdict and a review that found a blocker did not approve. `describe-pr` records the most severe finding beside the decision as `severest`, which the gate reads. A review with no findings is settled `publish_as_is` only beside an `approve`, and pushes; one that found nothing and did not approve is `fix_before_merge`, and an override's `publish_as_is` over it still asks, since such a review could not judge the range — as a review that did not finish or start does. A folder with no publish prefix keeps the branch local. The approval asks exactly where the gate decided `ask`, the push goes on an approval or a `push`, and the pull-request tasks never run after `keep_local`. The gate's decision and reason are the run's `pushDecision` and `pushReason`.

**Why `publish_as_is` pushes without asking under a verdict short of approve.** This is the operator's ruling, not an oversight a review should reopen. The decision stands in for an approving verdict for the verdicts and severities it saw: the decision model was handed every finding and the verdict, and weighed them. A blocker or a major among the findings asks, whatever was decided. A `comment` or `request_changes` verdict whose findings are all minor or nits pushes on the decision, because the operator's standing instruction is that minor findings do not hold a push, and asking there would put back the per-review wake-up the decision step removed. Tests pin both sides: `publish_as_is` over a `request_changes` or `comment` verdict with only minor findings pushes, and over a blocker or a major it asks. What stands in there is always the decision model’s answer, never the nits-only constant: nits alone under a verdict short of `approve` are asked, and tests pin that the model is called for `comment` and for `request_changes` over all-nit findings.

**A person's summary heads the body.** A `summary` passed to the publication is a person's words over the composed body, never a replacement for it: the decision, the findings a `publish_as_is` leaves open and any override record render under it as they do with no summary, and where GitHub's limit binds, the account of the commits gives way first, then the summary.

**What no decision passes.** The scan and the posture are read before the answer, so no decision stands in for a range the scan did not clear or for an `always` folder (Plan 316 D9: a decider can be steered by what it reads, so it is never the only gate on what leaves the machine). Where the answer clears a push, it does so over a range the scan read whole, on the receipt of the folder's checks, and the executor's own push gate is unchanged: it sends a range the scan did not clear, or any range from an `always` folder, only on the operator's grant.

**A decision is followed by default, and set aside only by a recorded act.** A follow-up agent — the conversation continuing after a pause, a shepherd pass — follows `afterReview`. Setting it aside is an act with an authority and a reason: the operator's word, the `hands-off` label, or a shepherd `when` rule that holds, such as the attempt budget reached. It is passed to the next publication as `override` (`AfterReviewOverrideSchema`: `by` one of `operator`, `hands_off_label`, `shepherd_rule`, and a `reason`), and no authority is taken on the caller's say: a run input anyone starting the publication can state is not an act. Where the override would set a decision aside — the review returned findings and the answer is not already `publish_as_is` — `claim-override` reads which authority it names and only that authority's check runs (`publishLocalChangesOverride.ts`). The `hands-off` label must be on the branch's open pull request into the base, the loop's own under the folder's prefix, as GitHub returns it (`read-override-pr`, the `loop_pulls` preset). A shepherd rule must be the shepherd's own record on that pull request: its pinned handoff (`read-override-pin`, then `read-override-handoff` by the pinned id, trusted only from the login it was pinned as) holding `abandon`, the decision only the attempt-budget rule makes (`SHEPHERD_BUDGET_SPENT`). The operator's word is the one no read stands in for — no record of it exists that a run can check — so it is taken from the operator: a verified operator override is one the gate asks about, and their approval of the push in this run is that word on record; a decline pushes nothing, and a shepherd-started publication's pause is cancelled by its waiter. `verify-override` decides by rules over those reads; anything it cannot verify is `refused`, and `override-refused` (`workflow.run.fail`) fails the run with the reason naming what it read, before anything is composed or pushed. `describe-pr` runs only where no override was refused, and then records `publish_as_is` and, as `afterReviewOverride`, whose act it was, the reason and the decision it set aside (`fix_before_merge`), on the run and on the pull request. The gate keeps the branch local on a refused override, and on a record whose authority is not the one `verify-override` verified, before it reads anything else; past those, a verified label or shepherd rule is followed as `publish_as_is` is. An override over `publish_as_is`, or where nothing was decided, sets nothing aside, and is neither checked nor recorded. It never stands in for an `always` folder or an uncleared scan. No branch skips silently: every answer ends in a push, a question to the operator, or a completed run whose output names the decision and what follows it.

**The bar.** The fix-or-not bar is Jev's 0.80, measured in Plan 316 §7: it agreed on every case it decided, over seventeen, abstaining on 17.6%. The after-check question rests on two cases, none of them labelled `operator_install_mismatch`, and comes back into the skill only once the measurement has such cases.

**Embeddings (D12, F18).**

- **One resolver.** `resolveSpaceEmbedding` (`@aflow/credential-resolver`) is the only path to an embedding client: the doc embedder, memory search and the settings surface all ask it. It resolves the space's model, then that provider's key through the space chain: space, then tenant, then the space owner's personal keys. Indexing runs with no one signed in, so the owner stands in for the user — on the local edition the only person there is. A platform environment key funds the call only off the local edition; it is read in that one file. A space with no answer is `unconfigured`, with the reason.
- **The model is a column on the space.** `spaces.memory_embedding_model` replaces `memory_embed_config` and its path, agent and global scopes: one space, one vector space, so search never has two models to reconcile. Unset, the default is the first catalog embedding model whose provider resolves, the chat provider's first. The embedder pins the default on its first successful embed, so a key added later never moves a space's index.
- **Dimensions are catalog data.** Each embedding model carries `embeddingDimensions`, sent as `dimensions` on every request: `text-embedding-3-small` 1536, `text-embedding-3-large` 3072, `gemini-embedding-001` 1536 (`outputDimensionality`). No model needs a new vector column. Measured 2026-10-18 through the client: both return 1536 when asked; a paraphrase pair scores 0.743 against 0.433 for an unrelated sentence on Gemini, 0.633 against 0.078 on `text-embedding-3-small`; a batch of 120 texts returns 120 vectors across the adapter's 100-per-call split.
- **A job names the document, not the model.** `MemoryDocEmbedJob` drops `embeddingModel`; the embedder resolves the space's model when it runs the job, so a job queued before a switch embeds with the model chosen after it.
- **Search reads one identity.** `searchVector` matches only chunks whose `embedding_model` is the space's model. During a re-index, search returns re-embedded documents by vector and the rest lexically, never a mix of two models' scores. `memory.query` reports `lexicalOnly` with the reason whenever vector search did not run.
- **States.** A document the embedder cannot serve for want of a provider is `unconfigured`, not `failed`, and is not retried on a cadence. A failure stores its reason in `memory_docs.embedding_error`. Saving a provider key marks the `unconfigured` and `failed` documents in its scope `pending` (a personal key: the spaces its holder owns); choosing a model marks every embeddable document in the space `pending`; both arm the existing backfill pointer.
- **Races.** The embedder takes only `pending` documents, pins a default before calling the provider and embeds with whatever the space then holds, and settles a document with a compare-and-set: still `pending`, and the space still on the model it embedded with. A document re-marked or a space switched mid-embed stays `pending` for the job its re-marking queued.
- **The surface.** Settings → Memory carries the search index: the model, who pays for it, counts by state, the latest error, the models whose provider has a key, and a switch that states the documents and estimated cost of the re-index before it runs. The memory explorer says when search is lexical only, and a document shows its embedding error.
- **Removed.** The entry embedder in the AI executor and its stream, which nothing published to.

## 7. Migration and breaking changes

D20: the first `yarn start`, `yarn dev:local` or `yarn redis:password` on a machine writes `~/.aflow/stack.env`.
