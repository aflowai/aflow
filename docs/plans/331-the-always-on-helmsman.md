# Plan 331 — The always-on Helmsman

**Status:** 🌱 design. Nothing built; the operator's open and place writes it relies on are built by Plan 332 P2 (D2, D5). **Builds on:** Plan 322 (nodes, their kinds, statuses, criteria and notes; `waiting` is on a run, `blocked` on a person, `active` taken in position order; D3 — skills propose, the Helmsman writes nodes; P2b — a stream that wakes itself, `plan.node.next`; P3 — the board and its in-flight/idle activity, #196), Plan 324 (the Helmsman's steering surface and its measured token budget), Plan 328 (a harness is a Runner with a coding agent; D6 — a commission no operator message started runs `open` at most), Plan 329 (`docs/plans/329-planning-is-a-skill.md`; P0 measures how plans are written by hand, P1 builds the planning skill — D1 `PlanProposalSchema`, D2 the planning skill's tasks, D3 accepted proposals written as nodes by the Helmsman, D4 `recalibrate`, D5 the same skill for non-code work), Plan 321 (the Local PR Shepherd and its schedule), Plan 317 (agents propose workflow changes, operators approve them), the loop skills — Commission Change, Local Publish with its review, Local PR Shepherd (`docs/dev/driving-work-through-the-loop.md`) — and two precedents of an agent woken by a schedule: the self-renewing shepherd schedule (#187) and the shepherd's hand-over to a Helmsman through `agent.schedule.create` (#194). **Leaves alone:** the push posture and the space's write policy (a push approval or a merge card the space asks for stays an operator act, and is counted, not removed); Plan 328 D6's posture rule (a wake is not an operator message, so its commissions run `open` at most); Plan 322 D3 (no skill and no Runner writes the plan); the shepherd's rules (Plan 321); the attention block's per-conversation ownership (Plan 322 P1).

## 1. Problem

The operator's direction: "an always-on agent that plans, executes plans, unblocks, makes sure everything is in order and always improves — using the plans as the way to carry context and mission."

The loop already runs without a person between commission and merge. In the operator's space, 21 pull requests merged from 2026-10-23 to 2026-10-26 (#179–#199), every one opened by Local Publish and merged by the scheduled shepherd. The loop skills' lifetime counts are 885 shepherd passes, 256 commissions, 262 publications and 347 reviews. The plan board holds 107 nodes across ten plan roots (315, 318, 320, 321, 322, 324, 328, 329, 330, 331).

What is wrong is that nothing starts without a person. The operator, or an assistant on the operator's side, is the scheduler:

- **Each node is briefed by hand.** The operator reads the board, picks the next node, and starts a fresh Helmsman conversation briefed with it. The node already holds the goal and criteria a brief needs (Plan 322 P1), and a cold conversation told only "continue the stream" can act on it, but someone has to tell it.
- **A node is not marked done until the operator says "folder at `<sha>`".** After every merge the operator confirms that the connected folder holds the merge before the node closes. No operation answers that question: `host.binding.inspect` reads a folder's binding and, when asked, its origin's default branch (`defaultBranch`, `packages/schemas/src/operations/host.ts`), not whether the folder holds a commit.
- **Push approvals and proposal ratifications are the operator's acts**, as they should be. They are also the only signal a waiting node gets, because nothing tells the operator that a node is waiting on them, except the board when they open it.
- **The operator decides what the next wake works on.** Between a merge and the next commission, the space is idle until the operator notices.

The shepherd's hand-over (#194) is the one place where an agent is woken without a person. A pass that meets a case its rules do not cover claims the case once and starts a Helmsman conversation through `agent.schedule.create` (`packages/platform-artifacts/src/skillCatalog/localPrShepherdHandOver.ts`), carrying what the pass read, what it decided and what was tried.

Plan 322 P2b built most of the mechanism a resident agent needs: a schedule whose firing is a Helmsman run that calls `plan.node.next` and acts on a decision made by rule (`packages/cybernetic-runtime/src/plan/stream.ts`). Five things keep it from being the space's scheduler:

1. **It is one schedule per stream root.** Ten roots need ten schedules, each created by the operator. Nothing orders them against each other, so the order the board gives the roots means nothing to them. Each schedule expires after 50 firings unless the operator renews it (`MAX_FIRINGS_CAP`, Plan 322 P2b). The renewal #187 built (`packages/schemas/src/schedules/renewal.ts`, `apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/scheduleRenewal.ts`) is used by the shepherd, not by a stream.
2. **A completed commission with no publication is `wait`** (Plan 322 P2b _Delivered_). The firing that started the commission has ended by the time the commission does, so nothing publishes the change. Whether the conversation should hold the publication is P2b's open question, and the operator is the answer today.
3. **A firing proposes nothing and unblocks nothing.** `stop` marks a node `blocked` and holds the whole stream there "until a person moves the node out of `blocked`". The plan page's write accepts only `done` and `dropped` (`PATCH /v1/spaces/:spaceId/plan/nodes/:nodeId`, Plan 322 P3.2). The operator can therefore unblock a node only by starting a Helmsman conversation.
4. **Overlapping firings each spend a model turn.** The agent schedule's firing path (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts`) records and dispatches every occurrence. It does not ask whether the previous occurrence's run has ended. `OverlapPolicySchema` (`skip`, `allow`, `cancel_previous`) is declared on the flow schedule (`packages/schemas/src/schedules/schedule.ts`), and nothing on the agent schedule's path reads it. P2b's claim (`PLAN_STREAM_CLAIM_TTL_MS`) keeps two firings from both continuing a node, but each still runs a turn to find that out.
5. **Its live exit is open.** The firings P2b names have not been observed on the stack. A schedule the operator would have to create, renew and order by hand is not one the operator has reason to rely on.

## 2. Design constraints

These are settled. Each decision below is checked against them.

- **The resident agent is the space's Helmsman.** It has the same identity, memory and tools, and wakes by a different path. It is not a new kind of agent and not a custom agent. Continuing work is planning, which belongs to the Helmsman alone and is refused to a skill (Plan 322 D3; P2b rejected a step-graph starter for the same reason).
- **It has no long transcript.** Its working context is rebuilt at each wake from durable records: the board (`plan.node.next`, `plan.node.get`), node notes and learnings (`plan.node.learn`), run detail (`workflow.run.detail`) and memory (`memory.store.*`). Memory and node notes are its continuity, not optional. A wake that learned something and wrote it nowhere has lost it.
- **Threads of intention are rows, not processes.** A thread is a plan node. No process, session or timer stands for an intention. The wake only reads them.
- **Long work is a child run** (a skill run, started with `wait: 'none'` and the node's `planNodeId`), and is never awaited inside a wake.
- **The heartbeat is owned by the system.** A heartbeat that arrives while a wake is in flight is dropped. Missed ticks do not overlap and do not build a backlog. An informational wake (a run serving a node ended, a person wrote a node) is never dropped.
- **Silence is the default output of a wake with nothing due.**
- **Nothing is abandoned silently.** Stopping is a recorded decision: a node marked `blocked` or `dropped` with why, as P2b's `stop` already writes it.
- **The agent never approves its own scope.** New work it proposes is a node `blocked` on the operator until the operator approves it.
- **There is no path per scenario.** The agent handles situations with the skills it has, and the rules stay few and deterministic. The model is the shepherd's hand-over (#194): rules decide what they can decide, and hand the rest, with what they read, to an agent with skills.

## 3. Decisions

**D1 — One wake per space: a recurring agent schedule now, the same predicate run by the system later. The default cadence is every fifteen minutes.** The operator creates the resident schedule once per space, in one action: `agent.schedule.create` with `action: 'start_run'`, the Helmsman (`platform-role` `cybernetic-helmsman`) as its target, `cron` `*/15 * * * *`, and a static input naming no root. It renews itself as the shepherd's does (#187): the template carries `{ $schedule: 'id' }`, and a wake within `SCHEDULE_RENEWAL_WINDOW` of the cap creates the successor with `renews`. Pausing the schedule pauses the resident, and a paused schedule is not renewed (`isScheduleRenewalDue`). Fifteen minutes is the longest an approved node can sit idle after something no event announced, such as a person merging on GitHub. It is the P1 default because P1 measures idle time (D7) and the cost of a wake with nothing due, and the cadence is the operator's knob on the schedule. Overlap becomes a rule of the agent schedule's firing path, not of the model. An occurrence whose schedule's previous run has not ended is recorded as skipped, with no catch-up firing, so a heartbeat never queues. P3 moves the due check ahead of the model (§5). _Rejected:_ one schedule per root (P2b as it stands) — ten schedules, no order between them, ten renewals, and the operator is still the one ordering the work. _Rejected:_ a system heartbeat first — it is a background task (Plan 180) with a registration, a candidate rule and budgets, to be built before anything shows the wake is worth it. The schedule path exists, and #187 and #194 have proven it. _Rejected:_ relying on P2b's claim against overlap — it prevents the double write but not the double turn.

**D2 — "Take the next node" is `plan.node.next` without a root: the board's open roots in their position, each walked as P2b walks one.** The wake's first call is `plan.node.next` with no `rootNodeId`. The engine takes the space's open roots in position order, finds each one's active node with `findActiveStreamNode`, and decides each by `decideStreamFiring`. It answers with the decisions that are not `wait`, ordered as D3 orders them, and a tally of the waits by cause. Root order is the operator's priority, and reordering roots on the board reprioritises the resident. That is the place write Plan 332 D6 builds (**Move up** / **Move down**), not a setting of its own. What a wake writes is what P2b's decisions write: the merge record (`plan.node.update` and the `merge` link), a `stop`'s `blocked` with why, and a commission or publication started with `planNodeId`. One line of the node's note records what the wake did, against the revision it read (Plan 322 D6). A cause the next wake should start out knowing is written with `plan.node.learn`. Approved work is an open node a person wrote, or an accepted proposal (D5). A node is taken because it is `active` and first in position, never because a model picked it. _Rejected:_ the model choosing which root to work — the scheduling would move from the operator into a prompt, with nothing to replay a choice from. _Rejected:_ round-robin across roots — it starts everything and finishes nothing.

**D3 — A wake finishes before it starts, starts before it asks, and asks before it proposes.** These are the four things a wake can do, in the order the engine ranks them across the board:

1. **Advance a `waiting` node whose run has finished.** This covers a merge to record, a failed round to re-commission within the attempt budget, and a commission completed with a change and no publication started. For that last case P2b answers `wait`. P1 adds a `publish` decision carrying the commission's run id, so the wake starts Local Publish with the node's `planNodeId`, and the publication takes its commit message from the commission's summary (`docs/dev/driving-work-through-the-loop.md`, _A round_).
2. **Continue an `active` node with no run in flight.** This is P2b's `continue`: commission the node's next step, briefed from its goal, criteria, note and learnings. A node with a run in flight is not continued. Its run's end is an informational wake (D4).
3. **Ask once on a `blocked` node.** The wake states what the node waits on in the note's first line and in the resident thread (D5). A node asked about is not asked about again until its revision moves, so the same question is never posted twice. P2 raises the question as an Action Center item, as a `decide` node's is (Plan 322 D9).
4. **Propose new work** (D5, D6), only when no approved node is actionable.

A wake acts on decisions until the board answers only `wait`, or the wake's budget (D4) is spent. The wake ends with no reply when it acted on nothing. This is the rule, not a courtesy: a wake that answers "nothing to do" every fifteen minutes buries the one that needed reading. _Rejected:_ the model ranking the four — the order is the whole policy, and a rule can be tested where a ranking cannot. _Rejected:_ one action per wake — a merge recorded and the next node commissioned is one step of the work, and splitting it puts fifteen minutes of idle time between them.

**D4 — A wake has a budget, and so does a node. Informational wakes go through the same gate as heartbeats, except that they are never dropped.** _Per wake:_ the context rebuilt at a wake (attention block, the board's decisions, the nodes it opens) is a measured prompt budget, as Plan 324 measures the steering surface. It is added to the context-budget check (`scripts/context-budget/`) with a ceiling, and an excess is reported, never silently trimmed (Plan 324 D5). A wake also caps how many decisions it acts on (three by default) and how many turns it takes. A session's start already carries `budgets` (`maxCostCents`, `maxTokens`, `maxDurationMs`, `maxSteps`, `SessionStartedPayloadSchema`, `packages/schemas/src/runtime/eventEnvelope.ts`). P1 measures which of those an agent run enforces before the resident relies on them. _Per node:_ P2b's attempt budget stands for re-commissions. A node also has a spend ceiling, the sum of `total_cost_cents` over the runs serving it (`workflow_runs.plan_node_id`) and the wake sessions that acted on it. When the ceiling is reached, the node gets a `stop`: `blocked`, with the spend and its runs named. _Informational wakes:_ the end of a run serving a node that a resident wake started, and a person's write to a node, each start a wake. When a wake is already in flight, the event sets the space's pending mark instead. The wake in flight starts one more wake when it ends, if the mark is set. That following wake reads the board, so it sees every event the mark stood for, and none is dropped. _Rejected:_ only a space-wide daily spend cap — one node failing in a loop spends the day and the rest of the board learns nothing. _Rejected:_ waking the session that started the run, as `wait: 'none'` does in a conversation — the wake that started it has ended, which is P2b's open question, and keeping it open would make a transcript of it.

**D5 — The operator's surface is the board, one visible thread, and the schedule's pause.** _The board is the control room._ Up next, In progress and Needs you already say what the resident will do, is doing, and waits on (Plan 322 P3.3). The operator moves a `blocked` node to `active` from the rail with **Approve**, the open write Plan 332 D6 builds (`PATCH …/plan/nodes/:nodeId/open`, through `updatePlanNode`), a person's write only (`planWriteAuthority.ts`), against the revision the rail read. Plan 332 uses one verb on every `blocked` step the rail offers it on, not **Approve** for a proposal and **Resume** for a stop: the record does not distinguish a proposal from a stop, and the write and its effect are the same. A blocked `decide` node is answered by **Decide** instead, and a blocked node under a closed step is stranded and waits for the closed step above it to be reopened. This plan takes that write as built rather than adding a second one. That is how proposals are approved and stops lifted, with no conversation. _Proposals are blocked nodes._ A node the resident writes as new work is created `blocked`, its note's first line saying it is proposed and why, and only a person moves it on. _One visible thread._ Every wake is a session of its own, so no transcript grows. The space shows the wakes' non-silent replies as one thread, newest first, with silent wakes counted and not listed. A message the operator writes there starts a wake whose cause is that message (Plan 328 D6's exchange). _Stop and pause._ Pausing the resident schedule stops heartbeats and informational wakes alike, and leaves runs in flight to finish, report and link to their nodes. Pausing is the operator's write, stamped with who and why. _Rejected:_ approval as a `decide` node answered in the Action Center — the answer is free text that the resident would then interpret as a grant of scope, which is self-approval at one remove. _Rejected:_ one long-lived Helmsman session as the resident — its transcript becomes its context, which the constraints exclude, and one failed turn stops everything queued behind it.

**D6 — Improvement enters as nodes, never as self-edits.** _Carried findings._ A review's findings the publication left `open`, and the `gaps` a commission reported, are linked to the node as `finding` links when the round ends (the rail's _Carried forward_, Plan 322 P3.3). A node that closes with findings still open gets a carrier node proposed under the same parent, `blocked` until approved (D5), with the findings in its goal. The finding is then not lost and not fixed without a person's say. _Recalibration._ When `plan.node.next` answers `recalibrate` (Plan 329 D4: a phase closed, or a node blocked twice), the wake starts the planning skill as a child run (Plan 329 D2) and writes its accepted proposals as nodes (Plan 329 D3), each `blocked` until approved. _Learnings._ A failure's real cause is a `plan.node.learn` on the node or its root, citing the runs, so the next wake starts out knowing it. _Rejected:_ the resident editing its own directives, skills or schedules to improve — a change to how work is done is a proposal an operator approves (Plan 317), and an agent that rewrites its own instructions has no reviewer.

**D7 — Three numbers are measured, from records the platform already writes.** _Operator actions per merged pull request:_ the operator's messages to any Helmsman session in the space, Action Center resolutions (`hitl_action_audit`), plan-page writes (the `plan.node.close` audit row and P1's approve and resume), push approvals, merge cards and schedule writes, divided by the pull requests merged for nodes in the same window. _Idle time between nodes:_ for each approved node, the time from its becoming actionable (approved, or its predecessor closed) to its first commission's start, read from `plan_nodes` and `workflow_runs`. _Cost per node:_ `total_cost_cents` over the runs serving the node, with the resident's wake sessions reported beside it as overhead per merged pull request. One read in the plan engine computes all three for a window, the P1 exit reads it, and P2 shows it on the board. _Rejected:_ counting merges alone — 21 merges in four days already happen with a person as the scheduler, so a merge count cannot show that the person left.

**D8 — A node is done on its merge. The folder's confirmation is not a gate.** P2b's `record_merge` reads the merge from GitHub and judges the node against its criteria with the merged change in hand. The next node's commission is based on `origin/<base>`, not on the connected folder, so nothing the resident does next depends on the folder holding the merge. A node whose criteria need the change running on the stack carries that as a child node of kind `investigate`. The child is `blocked` on the operator until a read of the folder's head exists (P2), and the merged node is not held open waiting for it. _Rejected:_ keeping the confirmation — it costs an operator act on every merge, which is exactly what D7 counts. _Rejected:_ the resident merging `origin/main` into the running stack itself — a merge into `live` restarts the executors and waits for every turn in flight (`docs/dev/driving-work-through-the-loop.md`, _Sharing the machine_), including the resident's own.

## 6. How it is proven

- **Nobody schedules the work.** The P1 exit: D7's read shows zero operator actions across a weekend in which approved nodes landed. A design that still needs a confirmation, a brief or a renewal fails it on the first count.
- **A commission is published without a conversation.** A wake starts a commission. The commission completes after the wake has ended, and the next wake (informational, or a heartbeat) starts Local Publish for that node with the commission's run id. Under P2b as built, that node stays `wait` indefinitely.
- **Root order is the priority.** Two roots each have an actionable node. The wake commissions the first by position, and after the operator swaps the roots, the next wake commissions the other. A model that chose would pass this by chance at best.
- **Overlap is dropped, events are not.** An occurrence while a wake is in flight starts no run and is recorded as skipped. Three runs end during one wake, and exactly one following wake starts and acts on all three.
- **Silence.** A wake whose decisions are all `wait` writes nothing to any node and posts nothing to the thread.
- **No self-approved scope.** A node the resident creates is `blocked`, and no decision commissions a `blocked` node. A test fails if a proposal is created in any other status, or if the engine answers `continue` for a `blocked` node.
- **Stopping is recorded.** A node whose attempts or spend run out is `blocked`, with why and the runs named, and the stream's later siblings are not started until a person moves it.
- **The person's write wins.** The operator approves a node from the rail while a wake is writing it. One write is refused on the revision (Plan 322 D6), and nothing is lost.
- **The resident's commissions stay `open`.** On a `trusted` folder, a commission a wake started compiles the `open` policy (Plan 328 D6). It is a schedule's exchange, not an operator message.

## 7. Open questions

- Whether the resident thread is a session list filtered to the schedule's wakes or a surface of its own. P1 builds the smaller, and the operator's use decides.
- Whether one wake should act on decisions in several roots in parallel up to the machine's harness limit, or one root at a time. P1 caps decisions per wake (D4) and measures idle time before choosing.
- Whether non-code roots (Plan 329 D5) need a decision P2b does not have, or only a different skill behind `continue`. That is decided when the first non-code root is approved.
