# Plan 328 — A harness is a Runner with a coding agent

**Status:** 🌱 design. Nothing built. **Builds on:** Plan 320 D11 (the harness's browser relay), Plan 315 D19/D20 and F101 (the sandbox posture, every service needs a credential), Plan 322 D3 (no Runner reaches `plan.*`), Plan 326 D12 (a value stamped on the job at both dispatch paths). **Feeds:** Plan 329 (the planning skill uses the harness as its investigator).

## 1. Problem

A coding harness on the host lane can read and change the checkout and nothing else the platform holds. A Runner on the same task can call operations — read a memory document, list a workflow's runs — through its capability grant, with every call a step the orchestrator scheduled, gated and recorded. The harness has no such surface:

- **It is handed one MCP server, the browser** (Plan 320 D11), and only when the run asks for one. `host.harness.run` takes no capability input, and the harness's own capability, `host.harness`, says nothing about which operations it may call.
- **The only other road to the platform is the owner's.** The stack's MCP server on 3100 hands the owner's API key to a session that presents its token (Plan 315 F101), and an API key carries its owner's full access — `POST /v1/api-keys` refuses a `scopes` field because nothing in authorization reads one (`packages/server-runtime/src/routes/api-keys.ts`). A harness given that road would act as the owner, unscheduled and unrecorded, with no grant between it and every write the owner can make.
- **That road is closed to it under every posture but `trusted`, and under `trusted` it may be open.** Under `open` and `confined` alike (D6) a harness job never reaches the machine's loopback, so this machine's services are unreachable from it: `allowLocalBinding` is in `FORBIDDEN_SANDBOX_OPTIONS` (`apps/aflow-executor-host/src/sandboxPolicy.ts`), and it is unscoped where it exists — it opens every local port, not one. On Linux the job's loopback is a network namespace of its own, so a port the executor listened on would not be the one the job dials. Under `trusted` (D6) the loopback is reachable, and a credential does not close the road: the connected folder commonly holds the stack's credentials — the aflow checkout holds `mcp.local.json` and `.env` — and the folder is readable under every posture by the operator's grant. Under `trusted` those credentials are usable against the services they open, so in such a folder the harness holds the owner's full access to the stack, unrecorded, exactly as the operator's coding agent does (D6, _Risk accepted_).

So a commission briefs the harness with whatever the Helmsman remembered to paste, a review cannot look up the runs and records it is reviewing against, and the investigator Plan 329 wants — a harness that reads the code _and_ the platform's records — cannot be built. The relay mechanism that would carry such calls already exists and is proven to widen nothing (Plan 320 P3: the compiled policy of a run with a browser is byte-identical apart from its scratch). What is missing is a second server on it, an authority for the calls it carries, and the rule that makes each call the same governed step a Runner's call is.

## 2. Decisions

**D1 — The transport is a second stdio MCP relay server, `aflow`, beside the browser's.** It uses the mechanism of Plan 320 D11 unchanged: a plain-Node relay with nothing outside its standard library, copied into the run's scratch, started by the harness through the profile's `mcpArgs` from the same per-turn `mcp.json`. It answers `initialize`, `ping` and `tools/list` itself and passes each `tools/call` to the executor as one line of JSON over a `mkfifo` pair in `turn-<n>/`, which the executor holds open read-write until the turn's process ends and then removes. The pair is the browser relay's pair in every respect but its names. The `aflow` server gets a request pipe and a response pipe of its own, beside the browser's in the same turn directory, made by the same function at the same moment and closed and removed with them. The two servers are two processes, and the browser's pair cannot serve both: a line written to a FIFO goes to whichever reader reads it first, so two relays reading one response pipe would take each other's answers. Two writers on one request pipe can also interleave any line longer than `PIPE_BUF` (512 bytes on macOS, 4096 on Linux), against a 1 MiB line bound. The pipes are made where the browser's are, in `apps/aflow-executor-host/src/browser/harnessBrowser.ts` — the one module the one-spawn-path guard admits for `mkfifo` — or that function moves to a module both use and the guard's list names it instead; no new `node:child_process` importer appears. The relay exists when the run's surface (D4) is non-empty, with or without a browser. The bounds of Plan 320 P3 apply per server: `MAX_CALLS_IN_FLIGHT_PER_TURN`, `MAX_CALLS_WAITING_PER_TURN`, `MAX_REQUEST_LINE_BYTES`, abandonment at turn end. _Rejected:_ a loopback port, on the executor or anywhere — `allowLocalBinding` is forbidden and unscoped, and on Linux the port is unreachable from the job's namespace. _Rejected:_ a Unix socket — `allowUnixSockets` is forbidden in the same list. _Rejected:_ the MCP server on 3100 — D2.

**D2 — The authority is a token the orchestrator mints for one harness step, and the harness never sees it.** The orchestrator mints it at dispatch, on both paths that dispatch `host.harness.run` — `scheduleStep` for a session and `dispatchClaimedOperationTask` for a workflow task — as Plan 326 D12 stamps `preferredHarness`. The token is random and bound to `(tenantId, runId, harnessStepExecutionId)`. The orchestrator stores only its hash, under a key the host identity has no grant for, and delivers the token on the job message (`StepJobMessage`, beside `callerModel` and `preferredHarness`). The token has no clock of its own. It is minted at dispatch and lives until the harness step reaches a terminal state, where it is revoked: the revocation is written in the same transaction as the step's terminal transition. The host executor applies the step's timeout from the moment the job starts, not from dispatch, so a step queued behind the machine's concurrency limit does not consume its token's life while it waits. A step abandoned before it starts is failed by the orchestrator's stall handling, which is a terminal state, so no token outlives its step. The host executor holds it outside the sandbox and presents it on each relayed call it forwards. The relay and the harness are never given it, so nothing the harness writes into the checkout, its output or its patch can carry it. That is guaranteed under every posture but `trusted`; under `trusted` it is a guardrail a harness can cross (D6). Verification checks two things: the token's hash matches a live binding for that step, AND the step is non-terminal in hot state. A forwarded call failing either is refused before anything is scheduled, so a token whose step has ended verifies nothing, whether or not its revocation was written. The call travels on a road the host identity already holds — its shard results stream — and its answer returns on the `aflow:pubsub:*` channels it already subscribes to. The host executor's Redis ACL gains nothing, and in particular no control stream and no session state (P0 measures this). The owner's API key and the MCP server on 3100 are never used (Plan 315 D19/D20, F101). _Rejected:_ a scoped API key per run — keys have no scopes and the route refuses them; adding scopes means fail-closed scope evaluation everywhere, which is a different plan. _Rejected:_ handing the token to the relay — anything inside the sandbox is the harness's to read. _Rejected:_ a fixed expiry from dispatch — exactly the queued-step refusal: a step that waits behind the machine's concurrency limit would start with its token spent, and every call it relayed would be refused.

**D3 — Every relayed call is a child step the orchestrator schedules, and passes every gate a Runner's call passes.** The orchestrator turns a verified call into a step with `parentStepExecutionId` = the harness step and a `parent:<harnessStepId>` tag, so `callerKindFromStep` (`apps/aflow-orchestrator/src/services/gates/decideStepGating.ts`) reads it as `'agent'`. It goes through `scheduleStep` unchanged: grant renewal, `enforceGrant`, the `opTaskOnly` refusal for an agent caller, and the host-binding gate. A surface check runs before those. It is equivalent to `TOOL_SURFACE_VAR` / `TOOL_NOT_ON_SURFACE`, but keyed by the harness step rather than an agent turn: the surface D4 computes is recorded under the harness step's id when the step is dispatched, and a call naming an operation outside it is refused `TOOL_NOT_ON_SURFACE` with the same teaching text. A call naming a Runner-excluded operation (`isRunnerExcludedOperation`) is refused `GRANT_DENIED` before the surface check, and the refusal names the exclusion, so the harness learns why the operation is out of reach rather than only that it is absent. A refusal is a non-retryable `permission` tool error, returned to the relay as an MCP error result. Nothing pauses, because `GrantEnforcementResult` cannot ask for a pause. `applyStepSucceeded` gains a branch: when the parent of a succeeded child is a `host.harness.run` step, the result is published to the waiting relay call; no agent turn is resumed and the parent is not woken. A failed child takes the same branch from the failure handler. The child is an ordinary step in the run: it appears in the run's steps, its feed and its cost, and the harness's activity feed shows it as a `tool` line, `aflow.<operationId>`, as it shows a browser call. _Rejected:_ the host executor performing the operation itself, as it performs a browser call. A browser call is the executor's own operation on its own machine. A platform operation belongs to its lane and its gates, and a second execution path is the bypass this plan exists to prevent.

**D4 — The surface is the harness operation task's existing `context.capabilities`.** A skill's harness task already carries `context.capabilities` (`operations`, `promotable.operations`), parsed by `TaskCapabilityGrantSchema` (`packages/schemas/src/cybernetic/context.ts`). Today it names only `host.harness.run`, the task's own operation. The surface is those operations minus `host.harness.run` itself, because a harness does not start a harness. A task narrows its surface by naming fewer operations; what the loop's skills name by default is D7. `host.harness.run` gains an optional `capabilities` input of the same shape, parsed by the same schema, for the Helmsman's direct calls. When it is absent the surface is empty and the run has no `aflow` server, as today. Some operations are refused for the whole run at scheduling, before any checkout: those for which `isRunnerExcludedOperation` holds (`plan.*`, `eval.*`, the local model operations) and those that are `opTaskOnly`. This mirrors how `decideHarnessBrowserGating` refuses a run asking for a browser without `browser.page:write`: a non-retryable permission error naming the operation. At validation, `opTaskOnlyValidator` and `capabilityReferencesValidator` scan a harness operation task's capabilities as they scan an agent task's (`collectAgentTaskToolIds` returns nothing for a non-agent task today), so a skill that would be refused at run time is refused when it is saved. `integrations` in the grant is not part of the surface in this plan (§6).

**D5 — The relay's tools are derived from the operation registry for the run's surface, never written by hand.** When the run starts, the executor is handed the surface and builds `aflow`'s `tools.json` from the registry. For each operation it writes a legal MCP tool name mapped one-to-one from the operation id, the description from `semanticDescription` (plus `usage.whenToUse` and `usage.pitfalls` where they are registered), and the input schema from the registered `inputZod` by `toJsonSchemaSync`, the same way the browser relay's tools are built. An operation added to the registry, or a schema tightened, reaches the harness with no edit here. A guard test holds that the relay's tool list for a surface equals what the registry derives for it.

**D6 — Local access is a third posture, `trusted`, beside `open` and `confined`.** Today a folder's posture is `open` or `confined` (Plan 315 D19), and the local edition's default is `open` (`HOST_SANDBOX_POSTURE_DEFAULT`). The two differ ONLY in egress: `open` admits every host but this machine, `confined` only the hosts the profile names. Under both, the compiled policy is otherwise the same: the machine's loopback is never a job's; `~/.aflow`, the host directory and the seeded credential files are denied; and no option `FORBIDDEN_SANDBOX_OPTIONS` names is set. So everything this plan guarantees — D2's token never reaching the harness, the filesystem denials, no machine loopback — holds under every posture but `trusted`, because posture there is egress only.

`trusted` is the compiled policy `open` and `confined` share plus `allowLocalBinding` and `allowUnixSockets`: the two options from `FORBIDDEN_SANDBOX_OPTIONS` that reaching this machine's services needs, and no others.

`trusted` uses the `open` launcher, unchanged. Its proxy dials off-machine hosts from outside the sandbox and refuses, on every port, every address of this machine (`openSandboxLauncher.mjs`), and that stays exactly as it is. What `trusted` adds is the two adapter options in the compiled policy, so the job reaches this machine's loopback and Unix sockets DIRECTLY, inside the sandbox, never through the proxy. Egress to the world is therefore `open`'s — every host but this machine, through the proxy — and the model provider is reachable as under `open`. Loopback is reachable as it never is under `open` or `confined`. So `trusted` is a strict superset of `open`, which is a strict superset of `confined` in egress, and that is the order the lesser-of ceiling rule uses. What a `trusted` run reaches, as D19 says it for the other two:

- _macOS._ The profile's loopback grant admits every localhost port, so the job reaches every listener on the machine's loopback by direct connect — the stack's Redis, Postgres, the MCP server on 3100, the admin tools — each behind only its own credential (Plan 315 D20). The socket grant admits the Unix sockets the operator's user can open. P0 confirms the direct connect under the `open` launcher.
- _Linux._ The job keeps a network namespace of its own. Whether `allowLocalBinding` reaches the machine's loopback from it or only the namespace's is a P0 measurement; until it is measured, `trusted` on Linux reaches local services only through the Unix-socket grant, which is all-or-nothing there, the Docker socket and the SSH agent included.
- _Both._ The filesystem policy is the shared one, and the world beyond this machine is `open`'s, through the proxy.

The command that sets a posture is renamed from `aflow harness sandbox` to `aflow harness posture`, in one pass: the word "sandbox" says there is or is not one, and there always is; "posture" names what varies. `allowAppleEvents`, `enableWeakerNestedSandbox` and `enableWeakerNetworkIsolation` stay forbidden under every posture; none of them is needed to call a local service, and the first removes code-execution isolation. The compiled filesystem policy is untouched by posture: `~/.aflow`, the host directory and the seeded credential files stay in `denyRead` under `trusted` as under `open` and `confined`. Under `trusted` the harness holds the operator's own trust level, as the operator's own Claude Code does — the relay is the RECORDED path and the harness's tool list names only it, but a direct call to this machine's services is possible exactly as it is for the operator, and the record is then as complete as the harness's discipline. `open` remains the default. `trusted` is never the default; it is chosen per folder by the operator on the machine. No run can raise its own posture through the platform; a `trusted` run can rewrite the machine's policy, which is the accepted trade. The guards are in §4: for the same binding, the compiled policy for `trusted` equals `open`'s plus exactly those two options; the `open` launcher's proxy refuses this machine's addresses under every posture it serves; and under `trusted` a listener on the machine's loopback is reachable by direct connect from inside the job, and under `open` and `confined` it is not.

`trusted` is the one posture under which the sandbox is NOT a security boundary. It is a record and a guard against accidents. The compiled filesystem policy still denies `~/.aflow`, the host directory and the seeded credential files, and the relay is still the only tool the harness's tool list names. But the Unix-socket grant reaches the Docker socket where one exists, and access to that socket is host root. So under `trusted` the deny lists, and D2's "the token never reaches the harness", are defeatable by a harness that sets out to defeat them. `trusted` therefore means exactly this: the harness may act as the operator's user on this machine, as the operator's own coding agent does. Everything D2 and the filesystem policy guarantee is guaranteed under every posture but `trusted`. Under `trusted` it is a guardrail the harness is expected to keep but can cross. Unless P0 finds that the socket grant can be scoped by path, this paragraph stands as written.

D6 amends Plan 315 D19. Each sentence of D19 that states a rule for "both postures" or "either" reads "under `open` and `confined`", and D19 ends: "Plan 328 D6 plans a third posture, `trusted`, under which the machine's loopback and Unix sockets are a job's. Under it this paragraph holds in three things only: the compiled filesystem policy, which that plan calls a guardrail and not a boundary; the ceiling `open` of `host.commit.check` and of every harness task, the reviewer's included, except one declaring `posture: folder` in a run an operator message started; and the ceiling `confined` of `host.process.exec`." D19's `host.process.exec` sentence is restated in the amended paragraph: `host.process.exec` stays `confined` under every posture, `trusted` included. The places that state the invariant change with it (§3): `HostSandboxPostureSchema`'s description, the header comments of `sandboxPolicy.ts` and `folderRun.ts`, and `host.harness.run`'s agent-facing text where it states that loopback is never a job's.

A task has a ceiling: the highest posture it may run under. The effective posture of a run is the LESSER of the folder's posture and the task's ceiling, in the order `confined` < `open` < `trusted`, computed by one function beside `sandboxPostureOf` (`apps/aflow-executor-host/src/sandboxPosture.ts`) that every caller uses. The rule is fail-closed: every harness task's ceiling is `open` unless the task declares `posture: folder`, which means "take the folder's posture, `trusted` included", and which takes it only when the run was started from a turn an operator message woke. `HostSandboxPostureSchema` (`packages/schemas/src/operations/host.ts`) gains the value `trusted`. `posture` is not an input of `host.harness.run`. It is a declaration on the skill task, `context.posture`, beside `context.capabilities` as D4's surface is, parsed by `TaskContextSpecSchema` (`packages/schemas/src/cybernetic/context.ts`), and its one value is `folder`; absent, the task's ceiling is `open`. The orchestrator reads it at dispatch, as it reads the surface, resolves the ceiling, and delivers the resolved ceiling on the job message beside the token (D2); the host executor takes the ceiling from there, never from the call's input. The resolution is keyed on what woke the turn that started the run, not on the session's surface. Every agent turn is resumed by exactly one cause, and the orchestrator records it on the turn: an operator message (input arriving through the session's input endpoint under a user or API-key principal), a run's completion, a schedule firing, an event, or a tool result. A workflow run started during a turn carries that turn's cause as `startedBy`. `posture: folder` resolves to the folder's posture only when `startedBy` is an operator message; for a turn woken by a run's end, a schedule, an event or a tool result it resolves to `open`, whatever surface the session uses, and so does a run no turn started. So a Helmsman chat session acting autonomously after a wake runs its commissions `open`; the same session, answering a message its operator just sent, runs them under the folder's posture. The text a run was briefed with never enters the decision — only the cause of the turn that started it, which the orchestrator records and reads at dispatch, a platform fact and not a brief the Helmsman writes. Only Commission Change declares `posture: folder`, because its brief comes from a conversation the operator is in; an unattended Commission Change runs `open` whatever the folder says. Review Local Changes, `host.commit.check`, and every task of the Local PR Shepherd — its fix, bump-dependency and merge-round remedies (`localPrShepherdRemedies.ts`) — declare nothing and so never exceed `open`: an unattended harness whose input is CI logs and pull-request text never runs `trusted`, whatever the folder says. Review Local Changes needs the model's hosts, not this machine: on a `trusted` folder it runs `open`; on an `open` or `confined` folder it runs the folder's. A Helmsman's direct `host.harness.run` call takes `open` and cannot pass `posture: folder`: the schema does not offer it there, because `posture` is not a field of `HostHarnessRunInputSchema` and a direct call has no skill task to declare it. A folder's `trusted` posture is reached only through a skill task that declares it, which today is Commission Change alone, in a run an operator message started. So `trusted` has three conditions: the operator's posture on the folder, the skill task's declaration, and an operator message as the cause of the turn that started the run. A ceiling never raises a run: a task declaring `posture: folder` on a `confined` folder runs `confined`, and so does one whose ceiling is `open`. The reviewer's task has ceiling `open`, so a review runs `trusted` only if a `trusted` run has already rewritten the skill or the policy. _Rejected:_ a per-skill posture on the binding — the binding is per folder and the skill is per space, so the binding has no place to hold it; the lesser-of rule needs no new record. _Rejected:_ the session's trigger or surface (`chat`/`voice`) — it says where the session began, not who steers the turn. _Rejected:_ an approval card per `trusted` run — the operator's own coding agent asks no one, and the operator ruled that the harness should hold what their coding agent holds.

`host.commit.check` has ceiling `open`, always: a check is the folder's verification, not an investigator. So a check runs `trusted` only if a `trusted` run has already rewritten the policy. On an `open` or `confined` folder the check runs the folder's posture, as today; on a `trusted` folder it runs `open` and its receipt signs `open`. The push gate compares the receipt against the CHECK's effective posture for the folder — the lesser of the folder's posture and the check ceiling `open` — computed by the same function the check used, not against the folder's posture. Today `requireCheckedPush` (`apps/aflow-executor-host/src/checkReceipt.ts`) refuses `check_other_posture` when the receipt's posture differs from the folder's, which on a `trusted` folder would refuse every push. With the change, a `trusted` folder's gate expects `open`; on an `open` or `confined` folder nothing changes.

`host.process.exec` keeps ceiling `confined` under every posture, `trusted` included: Plan 315 D19's reason stands — it runs a command an agent wrote, not the operator's tool — and the lesser-of rule gives it `confined` on any folder.

Under `trusted` the sandbox does not protect the stack's own servers; Plan 315 D20 — a credential on every service — is what stands in front of them: the MCP server on 3100 answers only a session presenting its session token, and Redis only its ACL. That holds only while the harness does not hold the credential, and a connected folder often does (_Risk accepted_). ~/.aflow and the profile's seeded credential files stay in every job's compiled `denyRead` under every posture. Under every posture but `trusted` that is a boundary; under `trusted` it is the guardrail described above. D19's kept invariant, that gates whose configuration the agent can rewrite protect nothing, is kept in full under every posture but `trusted`. Rejected: an airgap-only lane — the operator's own coding agent already has this reach, and an agent that cannot read the stack it serves investigates from code alone and misdiagnoses.

_Risk accepted._ The objection to this decision is that under `trusted` two of the options `FORBIDDEN_SANDBOX_OPTIONS` names, `allowLocalBinding` and `allowUnixSockets`, are admitted, so the sandbox no longer keeps the harness off this machine's services. A harness can then reach every loopback listener and every Unix socket the operator's user can — the Docker socket and the SSH agent included, because on Linux the socket grant is all-or-nothing — and nothing records it. On Linux, until P0 measures whether `allowLocalBinding` reaches the machine's loopback or only the job's namespace, that reach is taken to run through the socket grant alone, which is still all-or-nothing there and so still the Docker socket and the SSH agent. What stands between it and the stack's state is each service's own credential (Plan 315 D20), and D20 does not keep a `trusted` harness off the owner's road. The MCP server asks for its session token and Redis for its ACL, but Postgres on the dev stack accepts the credential the repository commits in `.env.example`. And the connected folder commonly holds the stack's credentials: the aflow checkout holds the owner's API key and the MCP session token in `mcp.local.json`, and the Postgres URL and the model-provider keys in `.env`. It does not hold Redis's: that password is the machine's, in `~/.aflow/stack.env`, in the host directory the policy denies. The folder is readable under every posture by the operator's grant, and under `trusted` those credentials are usable against the services they open. Under `trusted` in such a folder the harness therefore holds the owner's full access to the stack — the owner's key through the MCP server and the API, every tenant schema and the API-key table in Postgres, and the model providers on the owner's keys — unrecorded, exactly as the operator's coding agent does. What it reaches through Redis is whatever the running services do with it, not the password. The record of what the harness did to the platform is then complete only as far as the harness keeps to the relay; a call it makes directly to a service on this machine is no child step and is in no run view. The compiled filesystem policy is the same under every posture, but under `trusted` it is a guardrail and not a boundary: a harness holding the Docker socket holds host root, and can read what the deny lists name. The operator chose this trade for the folders they connect, on the grounds that their own coding agent already holds this reach, so `trusted` grants a run nothing the operator has not already given a coding agent. And `trusted` has three conditions: the operator's posture, set on the machine, per folder, and never as the default; the skill author's declaration, `posture: folder` on the task, which only Commission Change makes; and an operator message as the cause of the turn that started the run, which the orchestrator records on the turn and reads at dispatch. The unattended case is why a task's default ceiling is `open`, and why the declaration takes the folder's posture only for a run an operator message started: a harness no operator is watching, whose input is CI logs and pull-request text — the Local PR Shepherd's remedies, Review Local Changes, a Commission Change a schedule, an event or a run's completion starts — would otherwise run `trusted` on a `trusted` folder, steered by text that anyone able to open a pull request or fail a CI job writes, and with the reach above. No run can raise its own posture through the platform; a `trusted` run can rewrite the machine's policy, which is the accepted trade. The reviewer's task has ceiling `open`, so a review runs `trusted` only if a `trusted` run has already rewritten the skill or the policy; `host.commit.check` has ceiling `open` on the same terms. Two mitigations exist, and they are the operator's, not this plan's: keep the stack's credential files out of folders connected `trusted`, or connect those folders `open`. Closing D20 for Postgres is Plan 315's, not this plan's (§6).

**D7 — Commission Change and Review Local Changes declare the Runner's surface for the space as their default capabilities, minus Runner exclusions; a task narrows it; P3 builds exactly that.** D4 is the mechanism by which a task's `context.capabilities` becomes its surface. "The Runner's surface for the space" is the set of operation ids a Runner agent task in the same skill would be granted on this space — `runner_tools` plus `runner_capability_grants`, resolved by the same resolver that fills an agent task's grant — minus every operation for which `isRunnerExcludedOperation` holds and every `opTaskOnly` operation. One shared function derives it for a space, and the P3 guard test compares against that function rather than a list of its own. Because the excluded and `opTaskOnly` operations are stripped when the list is derived, a default surface never names an operation D4 refuses at scheduling: a skill that narrows nothing is never refused for its own default. _Rejected:_ the whole operation registry as the default — far wider than any Runner holds, and refused operation by operation at scheduling, so the default itself would fail.

## 3. What it affects

- `apps/aflow-executor-host`: `browser/harnessBrowser.ts` (the `aflow` server's entry in `mcp.json` and its pipe pair, or the pipe-making moved to a shared module), `browser/harnessRelay.mjs` (or a sibling relay for `aflow`), `handlers/harnessHandlers.ts` (surface, token held, calls forwarded, answers awaited, feed lines), `harnessProfiles.ts` (posture `trusted` in the folder posture enum, machine-set — the enum itself is `HostSandboxPostureSchema` in `packages/schemas/src/operations/host.ts`, read by a binding's `sandbox` in `bindings.ts`), `sandboxPosture.ts` (the one function that computes a run's effective posture, the lesser of the folder's posture and the task's ceiling, beside `sandboxPostureOf`), `sandboxedRun.ts` (`sandboxLauncher` hands `trusted` the `open` launcher, unchanged), `sandboxPolicy.ts` (`allowLocalBinding` and `allowUnixSockets`, and no other forbidden option, admitted only by an effective `trusted` posture, which is otherwise `open`'s policy; its header comment, which says the policy is the same under both postures and the machine's loopback is never a job's, restated as D6 amends D19), and the CLI `harness posture` (today's `harness sandbox <folder> <open|confined>`, renamed in one pass and gaining `trusted`).
- `apps/aflow-executor-host/src/commitCheck.ts`: a check's ceiling is `open`, so its effective posture is the lesser of the folder's and `open`, and its receipt records that posture — `open` on a `trusted` folder, the folder's otherwise (D6).
- `apps/aflow-executor-host/src/folderRun.ts`: where a run's posture is chosen today (`runUnderFolderPosture` hands `sandboxPostureOf(binding)` to `runSandboxed`).
