# Plan 328 — A harness is a Runner with a coding agent

**Status:** 🌱 design. Nothing built. **Builds on:** Plan 320 D11 (the harness's browser relay), Plan 315 D19/D20 and F101 (the sandbox posture, every service needs a credential), Plan 322 D3 (no Runner reaches `plan.*`), Plan 326 D12 (a value stamped on the job at both dispatch paths). **Feeds:** Plan 329 (the planning skill uses the harness as its investigator).

## 1. Problem

A coding harness on the host lane can read and change the checkout and nothing else the platform holds. A Runner on the same task can call operations — read a memory document, list a workflow's runs — through its capability grant, with every call a step the orchestrator scheduled, gated and recorded. The harness has no such surface:

- **It is handed one MCP server, the browser** (Plan 320 D11), and only when the run asks for one. `host.harness.run` takes no capability input, and the harness's own capability, `host.harness`, says nothing about which operations it may call.
- **The only other road to the platform is the owner's.** The stack's MCP server on 3100 hands the owner's API key to a session that presents its token (Plan 315 F101), and an API key carries its owner's full access — `POST /v1/api-keys` refuses a `scopes` field because nothing in authorization reads one (`packages/server-runtime/src/routes/api-keys.ts`). A harness given that road would act as the owner, unscheduled and unrecorded, with no grant between it and every write the owner can make.
- **It cannot reach that road anyway, and must not.** A harness job gets no loopback: `allowLocalBinding` is in `FORBIDDEN_SANDBOX_OPTIONS` (`apps/aflow-executor-host/src/sandboxPolicy.ts`), and it is unscoped where it exists — it opens every local port, not one. On Linux the job's loopback is a network namespace of its own, so a port the executor listened on would not be the one the job dials.

So a commission briefs the harness with whatever the Helmsman remembered to paste, a review cannot look up the runs and records it is reviewing against, and the investigator Plan 329 wants — a harness that reads the code _and_ the platform's records — cannot be built. The relay mechanism that would carry such calls already exists and is proven to widen nothing (Plan 320 P3: the compiled policy of a run with a browser is byte-identical apart from its scratch). What is missing is a second server on it, an authority for the calls it carries, and the rule that makes each call the same governed step a Runner's call is.

## 2. Decisions

**D1 — The transport is a second stdio MCP relay server, `aflow`, beside the browser's.** It uses the mechanism of Plan 320 D11 unchanged: a plain-Node relay with nothing outside its standard library, copied into the run's scratch, started by the harness through the profile's `mcpArgs` from the same per-turn `mcp.json`. It answers `initialize`, `ping` and `tools/list` itself and passes each `tools/call` to the executor as one line of JSON over a `mkfifo` pair in `turn-<n>/`, which the executor holds open read-write until the turn's process ends and then removes. The pair is the browser relay's pair in every respect but its names. The `aflow` server gets a request pipe and a response pipe of its own, beside the browser's in the same turn directory, made by the same function at the same moment and closed and removed with them. The two servers are two processes, and the browser's pair cannot serve both: a line written to a FIFO goes to whichever reader reads it first, so two relays reading one response pipe would take each other's answers. Two writers on one request pipe can also interleave any line longer than `PIPE_BUF` (512 bytes on macOS, 4096 on Linux), against a 1 MiB line bound. The pipes are made where the browser's are, in `apps/aflow-executor-host/src/browser/harnessBrowser.ts` — the one module the one-spawn-path guard admits for `mkfifo` — or that function moves to a module both use and the guard's list names it instead; no new `node:child_process` importer appears. The relay exists when the run's surface (D4) is non-empty, with or without a browser. The bounds of Plan 320 P3 apply per server: `MAX_CALLS_IN_FLIGHT_PER_TURN`, `MAX_CALLS_WAITING_PER_TURN`, `MAX_REQUEST_LINE_BYTES`, abandonment at turn end. _Rejected:_ a loopback port, on the executor or anywhere — `allowLocalBinding` is forbidden and unscoped, and on Linux the port is unreachable from the job's namespace. _Rejected:_ a Unix socket — `allowUnixSockets` is forbidden in the same list. _Rejected:_ the MCP server on 3100 — D2.

**D2 — The authority is a token the orchestrator mints for one harness step, and the harness never sees it.** The orchestrator mints it at dispatch, on both paths that dispatch `host.harness.run` — `scheduleStep` for a session and `dispatchClaimedOperationTask` for a workflow task — as Plan 326 D12 stamps `preferredHarness`. The token is random and bound to `(tenantId, runId, harnessStepExecutionId)`. The orchestrator stores only its hash, under a key the host identity has no grant for, and delivers the token on the job message (`StepJobMessage`, beside `callerModel` and `preferredHarness`). It expires with the step's timeout and is revoked when the harness step reaches any terminal state. The host executor holds it outside the sandbox and presents it on each relayed call it forwards. The relay and the harness are never given it, so nothing the harness writes into the checkout, its output or its patch can carry it. If a forwarded call's token does not hash to a live binding for that step, the call is refused before anything is scheduled. The call travels on a road the host identity already holds — its shard results stream — and its answer returns on the `aflow:pubsub:*` channels it already subscribes to. The host executor's Redis ACL gains nothing, and in particular no control stream and no session state (P0 measures this). The owner's API key and the MCP server on 3100 are never used (Plan 315 D19/D20, F101). _Rejected:_ a scoped API key per run — keys have no scopes and the route refuses them; adding scopes means fail-closed scope evaluation everywhere, which is a different plan. _Rejected:_ handing the token to the relay — anything inside the sandbox is the harness's to read.

**D3 — Every relayed call is a child step the orchestrator schedules, and passes every gate a Runner's call passes.** The orchestrator turns a verified call into a step with `parentStepExecutionId` = the harness step and a `parent:<harnessStepId>` tag, so `callerKindFromStep` (`apps/aflow-orchestrator/src/services/gates/decideStepGating.ts`) reads it as `'agent'`. It goes through `scheduleStep` unchanged: grant renewal, `enforceGrant`, the `opTaskOnly` refusal for an agent caller, and the host-binding gate. A surface check runs before those. It is equivalent to `TOOL_SURFACE_VAR` / `TOOL_NOT_ON_SURFACE`, but keyed by the harness step rather than an agent turn: the surface D4 computes is recorded under the harness step's id when the step is dispatched, and a call naming an operation outside it is refused `TOOL_NOT_ON_SURFACE` with the same teaching text. A call naming a Runner-excluded operation (`isRunnerExcludedOperation`) is refused `GRANT_DENIED` before the surface check, and the refusal names the exclusion, so the harness learns why the operation is out of reach rather than only that it is absent. A refusal is a non-retryable `permission` tool error, returned to the relay as an MCP error result. Nothing pauses, because `GrantEnforcementResult` cannot ask for a pause. `applyStepSucceeded` gains a branch: when the parent of a succeeded child is a `host.harness.run` step, the result is published to the waiting relay call; no agent turn is resumed and the parent is not woken. A failed child takes the same branch from the failure handler. The child is an ordinary step in the run: it appears in the run's steps, its feed and its cost, and the harness's activity feed shows it as a `tool` line, `aflow.<operationId>`, as it shows a browser call. _Rejected:_ the host executor performing the operation itself, as it performs a browser call. A browser call is the executor's own operation on its own machine. A platform operation belongs to its lane and its gates, and a second execution path is the bypass this plan exists to prevent.

**D4 — The surface is the harness operation task's existing `context.capabilities`.** A skill's harness task already carries `context.capabilities` (`operations`, `promotable.operations`), parsed by `TaskCapabilityGrantSchema` (`packages/schemas/src/cybernetic/context.ts`). Today it names only `host.harness.run`, the task's own operation. The surface is those operations minus `host.harness.run` itself, because a harness does not start a harness. A task narrows its surface by naming fewer operations; what the loop's skills name by default is D7. `host.harness.run` gains an optional `capabilities` input of the same shape, parsed by the same schema, for the Helmsman's direct calls. When it is absent the surface is empty and the run has no `aflow` server, as today. Some operations are refused for the whole run at scheduling, before any checkout: those for which `isRunnerExcludedOperation` holds (`plan.*`, `eval.*`, the local model operations) and those that are `opTaskOnly`. This mirrors how `decideHarnessBrowserGating` refuses a run asking for a browser without `browser.page:write`: a non-retryable permission error naming the operation. At validation, `opTaskOnlyValidator` and `capabilityReferencesValidator` scan a harness operation task's capabilities as they scan an agent task's (`collectAgentTaskToolIds` returns nothing for a non-agent task today), so a skill that would be refused at run time is refused when it is saved. `integrations` in the grant is not part of the surface in this plan (§6).

**D5 — The relay's tools are derived from the operation registry for the run's surface, never written by hand.** When the run starts, the executor is handed the surface and builds `aflow`'s `tools.json` from the registry. For each operation it writes a legal MCP tool name mapped one-to-one from the operation id, the description from `semanticDescription` (plus `usage.whenToUse` and `usage.pitfalls` where they are registered), and the input schema from the registered `inputZod` by `toJsonSchemaSync`, the same way the browser relay's tools are built. An operation added to the registry, or a schema tightened, reaches the harness with no edit here. A guard test holds that the relay's tool list for a surface equals what the registry derives for it.

**D6 — Local access.** Under `trusted` the harness holds the operator's own trust level, as the operator's own Claude Code does — the relay is the RECORDED path and the harness's tool list names only it, but a direct call to this machine's services is possible exactly as it is for the operator, and the record is then as complete as the harness's discipline. That is the posture's declared trade, chosen per folder by the operator on the machine, never by a run, and never the default: `confined` stays the default and the reviewer's harness stays `confined`. What protects the stack's own servers under `trusted` is Plan 315 D20 — a credential on every service — not the sandbox: the MCP server on 3100 answers only a session presenting its session token, and Redis only its ACL. ~/.aflow and the profile's seeded credential files stay unreadable to every job under every posture (D19's kept invariant: gates whose configuration the agent can rewrite protect nothing). Rejected: an airgap-only lane — the operator's own coding agent already has this reach, and an agent that cannot read the stack it serves investigates from code alone and misdiagnoses.

_Risk accepted._ The objection to this decision is that under `trusted` the options `FORBIDDEN_SANDBOX_OPTIONS` names — `allowLocalBinding` among them — are admitted, so the sandbox no longer keeps the harness off this machine's services. The record of what the harness did to the platform is then complete only as far as the harness keeps to the relay; a call it makes directly to a service on this machine is no child step and is in no run view. The objection is accepted rather than designed away for three reasons. The operator's own coding agent, run by hand in the same folder, already holds exactly this reach, so `trusted` grants a run nothing the operator has not already given a coding agent. The posture is set on the machine, by the operator, per folder: no run can choose it, it is never the default, and it is never the reviewer's. And the services stay behind their credentials (Plan 315 D20) under every posture.

**D7 — Commission Change and Review Local Changes declare the Runner's surface for the space as their default capabilities, minus Runner exclusions; a task narrows it; P3 builds exactly that.** D4 is the mechanism by which a task's `context.capabilities` becomes its surface.

## 3. What it affects

- `apps/aflow-executor-host`: `browser/harnessBrowser.ts` (the `aflow` server's entry in `mcp.json` and its pipe pair, or the pipe-making moved to a shared module), `browser/harnessRelay.mjs` (or a sibling relay for `aflow`), `handlers/harnessHandlers.ts` (surface, token held, calls forwarded, answers awaited, feed lines), `harnessProfiles.ts` (posture `trusted` in the folder posture enum, machine-set — the enum itself is `HostSandboxPostureSchema` in `packages/schemas/src/operations/host.ts`, read by a binding's `sandbox` in `bindings.ts`), `sandboxPolicy.ts` (the forbidden options admitted only by the machine posture), and the CLI `harness posture` (today's `harness sandbox <folder> <open|confined>`, renamed in one pass and gaining `trusted`).
- `packages/schemas`: `StepJobMessage` gains the token; `HostHarnessRunInputSchema` gains `capabilities` (`packages/schemas/src/operations/host.ts`); a results-stream message for a forwarded call.
- `apps/aflow-orchestrator`: token mint and revoke at both dispatch paths; the forwarded-call consumer that verifies the token and schedules the child; the surface record and check keyed by harness step; the success and failure branches that publish to the relay; the `capabilities` refusal beside `decideHarnessBrowserGating`.
- `packages/cybernetic-runtime`: `opTaskOnlyValidator` and `capabilityReferencesValidator` scan harness operation tasks.
- `packages/platform-artifacts`: Commission Change and Review Local Changes declare their capabilities as D7 states (P3).
- Stored data: the token's hash in Redis, expiring with the step. No table, no migration. The host executor's Redis ACL is unchanged.

## 4. Guard tests that constrain it

Each must stay green, unchanged unless the change says why:

- `apps/aflow-executor-host/src/__tests__/harnessBoundary.test.ts` — _one spawn path_ (no new `node:child_process` importer; the `mkfifo` site stays `browser/harnessBrowser.ts` or moves by name), unchanged. _Never emits an option that voids the contract_ is **restated** (D6): a forbidden option is never emitted for a request, and is admitted only by the machine's `trusted` posture on that folder. It gains the test that a run input cannot name a posture.
- `apps/aflow-executor-host/src/__tests__/sandboxPolicy.test.ts` — **restated** (D6) in the same way: no forbidden option and no loopback for a request or a check's widening, under any posture but the machine's `trusted`.
- `apps/aflow-executor-host/src/__tests__/harnessBrowserRun.test.ts` — the policy of a run with a relay is byte-identical to one without, apart from its scratch. It is extended to a run with the `aflow` server, with and without a browser.
- `apps/aflow-executor-host/src/__tests__/openSandboxLauncher.test.ts` — the `open` launcher refuses this machine on every port and grants no loopback.
- `packages/server-runtime/src/bootstrap/redisAcl.test.ts` — the host identity reaches no other lane, the control stream or session state, and cannot write a write-approval grant.
- The strict body of `POST /v1/api-keys` in `packages/server-runtime/src/routes/api-keys.ts` — it accepts no `scopes`, so no part of this plan may rely on a restricted key.

## 5. Phases

**P0 — Measure.** Three answers, each recorded here before P1 starts:

- _Token path._ A token minted at each dispatch path reaches the host executor on the job. A call forwarded on the results stream is verified and answered over `aflow:pubsub:*`. `redisAcl.test.ts` passes unchanged. This includes whether a workflow task's harness step, which has no session, can parent a child step on the workflow path, and if not, what it needs (§6).
- _Round-trip latency._ Relay → executor → results stream → orchestrator → child step on its lane → result → relay, for a read on the memory lane: p50 and p95, against the harness's MCP tool timeout.
- _The one-spawn-path guard._ The `aflow` server's pipe pair is made without a new spawn site, so the guard's list is unchanged or changes by one named entry. A turn with both servers carries concurrent calls on both, and neither server's answers reach the other.

Exit: the three answers are written down, and none of them requires widening the host ACL or the sandbox policy. If one does, the plan changes before P1.

**P1 — Relay, token and child steps, for reads.** D1, D2, D3, D5, and D4 for operations whose `accessMode` is `read`. A write on the surface is refused at scheduling until P2. Exit, all on the dev stack:

- a harness run in Full Circle calls `memory.store.get` and `workflow.run.list` through the relay and each call appears as a child step of the harness step in the run view; a call to `plan.node.get` is refused `GRANT_DENIED` and the refusal names the exclusion;
- a call naming an operation off the surface is refused `TOOL_NOT_ON_SURFACE`;
- a run whose surface names `plan.node.get` or an `opTaskOnly` operation is refused before any checkout;
- a forwarded call carrying a revoked token, or another step's token, schedules nothing;
- the token appears nowhere in the checkout, the patch, the captured output or the feed;
- the trusted posture, measured on one folder: the same relayed calls appear as the same child steps in the run view, and `plan.node.get` is refused the same way;
- every guard test of §4 passes.

**P2 — Writes and the `capabilities` input.** Write operations on the surface, and `host.harness.run`'s `capabilities` for the Helmsman's direct calls. A relayed write that would park on a write approval (Plan 253) cannot be answered from inside a harness call. It is refused with a code that says so, as `BROWSER_ASK_UNANSWERABLE` is (§6). Exit:

- a Helmsman commission with `capabilities: { operations: ['memory.store.put'] }` writes a document through the harness, and the write is a child step;
- the same call on a space whose write policy asks is refused, not paused;
- a skill whose harness task names an `opTaskOnly` operation fails validation when it is saved.

**P3 — D7, and Plan 329's planning skill uses the harness as its investigator.** Builds D7 as stated. Plan 329's planning skill commissions the harness to investigate the checkout and the platform's records together. Exit:

- each skill's surface, when its task narrows nothing, is what D7 states for the same space, and a task that names fewer operations gets only those;
- a commission from the dev stack reads a memory document and the run list it was briefed about, without the Helmsman pasting either;
- the planning skill's investigation step returns findings that cite both code and records.

## 6. Open questions

- **`plan.node.get` against Plan 322 D3 — decided.** The harness never reads its plan node through the relay. `plan.*` operations are Runner-excluded (D4), so they are in no default surface (D7), and a relayed call to one is refused `GRANT_DENIED` naming the exclusion (D3). The brief carries what the harness needs from the node. Reopening this means amending 322 D3 and its predicate, not this plan.
- **A workflow task's harness has no session.** The workflow-task path dispatches without session state. Whether a child step can be scheduled under it as under a session's step, or needs the workflow run's own scheduling, is for P0 to answer.
- **`promotable.operations` for a harness.** A Runner promotes through `catalog.tool.promote`; a harness reads its tool list once, at start. Default: the relay lists both tiers, since the list costs the harness's context and not the platform's prompt. Whether a harness honours `notifications/tools/list_changed`, which would allow real promotion, is unmeasured.
- **Write approvals.** P2 refuses a relayed write that would ask for approval. The alternative is a harness call that waits on the operator up to the step's timeout, which needs the relay to outlast the harness's own tool timeout.
- **`integrations`.** Bound API endpoints and MCP tools in the grant are outside this plan's surface. Adding them would apply the same child-step rule over a different registry.
- **Codex.** Plan 326 D3's `codex-toml` form carries one `-c` per server. Whether Codex starts two relay servers from one run is unmeasured.
