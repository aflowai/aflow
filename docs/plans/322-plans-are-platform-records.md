# Plan 322 — Plans are platform records

**Status:** 🔨 P0 and P1 built and tested without a live stack; P0's exit — a cold conversation continuing a stream from the node — and P1's — a whole slice with every record on its node — are proven on the live stack after merge. Wake conditions move from deferred into P2b: a recurring schedule starts a Helmsman run that continues the named stream (recording a merged node and advancing to the next active one), waits while its node's work is in flight, re-commissions a failed node within an attempt budget, or stops where its pull request was closed unmerged, its publication was denied or the budget is spent. P2b built and tested without a live stack (§5 P2b _Delivered_); its live exit is open. P3.1 — the operator reads the plan — built and tested without a live stack (§5 P3 _Delivered_); P3.2 — the operator's writes and the `decide` node's Action Center item — built and tested without a live stack (§5 P3 _Delivered_ (P3.2)), the decide answer's record settled in D9; P3's live exit is open. P2 not started.

**Builds on:** Plan 315 (the loop and the stream protocol that drives it), the campaign engine (`packages/cybernetic-runtime/src/campaigns.ts`), the attention block the Helmsman reads each turn (`packages/cybernetic-runtime/src/attentionBuilder.ts`), the `workflow.campaign.*` inline-op family as the template for an operation family with one authority for the agent path and the operator path, and the vocabulary Plan 299 §3.4 fixed for a tree of intentions. It takes from 299 only the tree, and builds it standalone for the on-demand Helmsman.

## 1. Problem

The plan that drives a stream of work lives in a markdown file in the repository, and every stream writes that one file: its decisions, its delivery notes, its findings. In one day `main` moved under one pull request (#72) three times with no content in the conflict, each costing a merge round of the loop; #68 met the same conflict the day before. A Helmsman conversation starts cold: it reads a protocol document to learn what the stream is, and every slice begins with a hand-written brief that restates where the work stands (F103, F107). The shepherd (Plan 321) needs "what is happening to this branch right now" and plans to assemble it from a pull-request comment and a memory-store lease, because nothing on the platform holds it. Three consumers want the same record, and none has it.

What exists is adjacent and not it. A campaign is one goal with one metric for one skill (`campaigns`, `packages/database/src/schema/tenant/campaigns.ts`). A learning is keyed by skill or campaign and cannot point at an arbitrary record (`coach_learnings`, `CoachLearningScopeSchema`). The memory store holds untyped documents under paths, with no join to the runs that did the work. A workflow run carries a `campaign_id` and a `metadata` bag, and no purpose. The attention block the Helmsman reads each turn knows the active runs and the pending proposals, and nothing about why they run.

The earlier plans in this area (88, 99, 215, 234, 299) were design exercises; part of each was built, part was not, and none was driven to a measurable end through the Helmsman. The stream that produced this plan was: forty findings and ten slices landed by briefing the Helmsman, reading reviews and iterating. This plan is sized to that method. The goal is fixed; the design below changes wherever use shows it should.

## 2. Decisions

**D1 — A plan is a tree of nodes in Postgres, per space.** `plan_nodes` carries parent, kind, title, goal, success criteria, status, a bounded working note, and a revision counter. _Rejected:_ a memory-store document — untyped, path-addressed, no join to runs, and a second session's write can lose the first's; a markdown file — the problem. Columns over a JSON bag, because the Helmsman, the attention block and the operator surface all read the same fields and a query on status or parent is the common case.

**D2 — A node's kind is a mode of work, not a classification, and the vocabulary extends Plan 299's.** 299 §3.4 has `execute | investigate` and `active | suspended | waiting | done | dropped | failed`. This plan adds the kind `decide`, because a node whose outcome is the operator's choice is neither work nor inquiry and must raise an Action Center item rather than a run (P3); and the status `blocked`, because a node waiting on a person is a different state from one waiting on a run, and the attention block tells them apart. It drops `suspended` and `failed` until a node can be suspended by a policy or failed by a budget, neither of which exists here. Success criteria may be provisional and are revised with the reason in the note. Breakdown is recursive by adding children; a node is done against its own criteria — the Helmsman marks it, with the outcome recorded, never automatically from its children, because the criteria are the parent's and the children are one attempt at them. _Rejected:_ dependency edges, wake conditions, commitment policies and budgets in P0 — each is a 299 element with a reason, and none is needed to replace the markdown file; dependencies arrive in P2 when the shepherd reads the tree, and the one wake condition this plan builds — a schedule that continues a stream — in P2b.

**D3 — The operations are Helmsman tools, `plan.node.*`, never a skill, and never a Runner's.** Planning is open-ended; a skill's worth is a validatable procedure (Plan 190), and the eval plane's rule holds here: a run may serve a node and may never rewrite the plan it serves. The exclusion is a validation rule, not a test: `isPlanOperation` (fail-closed string prefix, beside `isEvalPlaneOperation`) and `validateSkillPlanSeparation` refuse a skill that references `plan.*`, and a guard test probes the rule with a violation. What reaches a Runner at run time rather than through an authored skill — a delegation's `runner_tools` and capability grant, the promotable tier, the surface a Runner's turn is handed — asks one predicate, `isRunnerExcludedOperation` (the eval plane and the plan), so a plane added to it is excluded from every channel at once. The grant migration 218 gives the system profiles stays: the Helmsman needs it, and the Runner exclusion is what keeps the plan the Helmsman's. The step type is `plan`, group `node`, so the operation reads as what it is; the capability group `plan:node` is added to the system profiles in the same migration, which also drops the `plan.read` / `plan.write` groups migration 020 seeded for a step type that never existed. _Rejected:_ `workflow.plan.*` to save the routing line — a plan is not a workflow, and the agent reads operation names as ontology.

**D4 — The active tree is in the attention block, invalidated by every plan write, and a fresh session reads it before anything else.** `HelmsmanAttentionContext` gains the space's active nodes: title, kind, status, the note's first line, and the in-flight runs under each. The block is cached (`getAttentionCache`) and invalidated by listed entity events (`attentionCacheSubscriber.ts`), so every `plan.node.*` write bumps the attention generation the way a coach or procedure event does; without that the tree goes stale until an unrelated event, and the P0 exit cannot be met. _Rejected:_ a `SpaceContext` section — also cached, invalidated per step type, and projected per role; the attention block is where in-flight state already lives, and the invalidation is one call in either case.

**D5 — A run carries the node it serves.** `workflow.run.start` takes an optional `planNodeId`, stored as `workflow_runs.plan_node_id` with an index, so the attention block renders runs under their nodes and a node's runs are derived, never maintained by hand. A publication or commission started for a node links its pull request and its result to the node when it ends. _Rejected:_ `metadata.planNodeId` — a zero-migration link that nothing can index or join.

**D6 — Writes are compare-and-set on the node's revision.** Two sessions in one space may work the same tree; `update` carries `expectedRevision` and a stale write is refused with the current node, the way `memory.store.put` refuses on `expectedHash`. _Rejected:_ a revision log per write in P0 — the refusal is what prevents loss; the history of a node is its links and its note, and a log is added only if reconciliation across sessions turns out to need it.

**D7 — The operator reads the same authority, when the operator reads it.** The engine functions in `packages/cybernetic-runtime/src/plan/` are the one authority; the inline ops call them in P0, and `GET /v1/spaces/:spaceId/plan` calls them in P3 when a surface renders the tree, as the campaign routes do. Until then the stream is driven from the Helmsman and the Workbench. The operator's writes in P3.2 call the same `updatePlanNode`, so they take D6's compare-and-set like any session's; they are a person's only — an agent's credential is refused whatever its grants, so a Runner's API call cannot reach the plan D3 keeps from it.

**D8 — Campaigns and learnings are left where they are until the record has carried a slice.** A node may link to a campaign; whether a campaign becomes a node kind is decided after P1 with evidence. A learning gains `scope: plan` with a node id in P2, when the record exists to attach to. _Rejected:_ redesigning either now.

**D9 — The operator's `decide` answer is the node's `outcome`, written as the node is marked done.** A `decide` node raises an Action Center item that is derived from the node on every read and stored nowhere — id `plan-decision:<nodeId>`, its CAS token the node's revision — and answering it is a `plan.node.update` to `done` with the answer as `outcome`, compare-and-set on that revision, through the same engine the Helmsman and the plan page write through. Who answered and when is the `hitl_action_audit` row the Action Center writes for every resolution, keyed by the item id and stamped from the session, never from the request. The outcome is where every reader of the plan already looks — the attention block, the plan page, `plan.node.get`, a stream's walk — and D2 already says a node is done against its criteria with its outcome; for a `decide` node, the choice is that statement. Answering on the plan page (**Decide**, a close to `done` with an outcome) is the same write, so the two surfaces cannot record a decision in two places. _Rejected:_ a link from the node to the Action Center item — the item has no record of its own once answered, so the link would name nothing a reader can open; the node would read as closed with no statement of how; and every reader would need a second hop to learn what was chosen. A link kind for the decision as well as the outcome — two records of one fact, which drift the first time one is corrected.

## 3. Design

### 3.1 Records

`plan_nodes` (per space): `id`, `space_id`, `parent_id`, `kind`, `title`, `goal`, `criteria`, `status`, `outcome`, `note`, `revision`, `position`, `created_by`, `created_at`, `updated_at`, `closed_at`. In P1, `plan_node_links`: `node_id`, `space_id`, `kind` (`run | session | pull_request | document | finding | campaign`), `ref`, `label`, `created_at`; and `workflow_runs.plan_node_id`. Zod in a `plan.ts` beside `campaign.ts` under `packages/schemas/src/cybernetic/`; the length caps on `goal`, `criteria`, `outcome` and `note` are storage ceilings in the thousands, since they hold model-authored prose a person reads. The rule that a node is done against its criteria lives in the schema: `update` with `status: done` requires `outcome`, the statement of how the criteria were met, and is refused without it.

### 3.2 Operations

| Operation          | Phase | Does                                                                                                            |
| ------------------ | ----- | --------------------------------------------------------------------------------------------------------------- |
| `plan.node.create` | P0    | a node under a parent (or a root), with kind, title, goal, criteria                                             |
| `plan.node.update` | P0    | status, note, criteria, title, parent, position — compare-and-set on `expectedRevision`; `done` needs `outcome` |
| `plan.node.get`    | P0    | one node with its children and, from P1, its links and in-flight runs                                           |
| `plan.node.list`   | P0    | the space's tree, filtered by status or root, bounded                                                           |
| `plan.node.link`   | P1    | a typed reference from a node to a run, session, pull request, document, finding or campaign                    |

Engine functions in `packages/cybernetic-runtime/src/plan/`, called by the inline handlers under `handlers/inlineOps/plan/`. Registered in `packages/schemas/src/catalog/registry.ts` with `usage.whenToUse` carrying what the schema cannot (open the node before briefing a round; a round's brief is the node's goal and criteria), pinned for the Helmsman in `catalog.coreOperations`.

### 3.3 What a fresh session sees

The attention block renders, for each active root: `[execute] 315 · Local first-run ergonomics — active — next: F114 findings out of the plan file` with its active children indented, and from P1 the in-flight runs under each by slug and status. The Helmsman's first move in a stream is `plan.node.get` on the node named, and its briefs are the node's goal and criteria plus what the operator adds.

Neither skill declares `planNodeId` as a run input of its own: the start's field is the one place a run's node is named, so a run cannot carry two, and the review takes the publication's from the harness; Local Publish's description, at the catalog's 5,000-character ceiling, is unchanged. `docs/dev/driving-work-through-the-loop.md` has a round read its node first and name it on the commission and the publication. **Open**: the exit, measured in Full Circle after merge.

**P2 — Learnings and dependencies.** `coach_learnings` gains `scope: plan`; dependency edges with a condition on the dependency's outcome, validated for cycles. _Exit:_ a learning written on a node is read by the next session that opens it; the shepherd's `read-in-flight` task reads the branch's node and writes no pull-request comment.

**P2b — The stream wakes itself.** A recurring schedule (`agent.schedule.create`, `action: 'start_run'`, `cron`) whose target is the Helmsman (`platform-role` `cybernetic-helmsman`) starts a run told only to continue the named stream: its template is static JSON naming the stream's root node and the attempt budget and nothing else, as a firing can carry no live value (Plan 321 §5 P0.1). Before it acts, that run reads the active node's linked runs — `plan.node.get` on the stream's active node, its links and the runs in flight for it and every node under it, whoever drove them — and the space's attention items (`workflow.run.list_attention`, `scope: 'space'`), and decides `wait`, `stop` or `continue`. The firing is the writer of a merge, and it records one before it decides anything. The stream's active node is found by walking down from the root, by `position`, into the first child that is not closed (`done` or `dropped`), and on from there. The walk stops at the first node that has no open child, or at the first node that is not `active` — a `blocked` node ends it even where it has open children or open siblings after it: that node is the active one. So a parent whose children are all closed is its own active node again, and a `stop` holds the stream, not just its node: the node it marked `blocked` stays the active node, rule 1 decides `wait` on every later firing, and no sibling after it, nor its parent, is started until a person moves it out of `blocked` (or drops it, which closes it and lets the walk pass). The merge is read from the pull request itself, not from the node's timestamps: the active node's newest pull request is merged — GitHub's `merged` on the `pull_request` link's pull request, read through the space's binding — and no commission of the node (D5) started after its `merged_at`. That pair is the merge nobody has acted on yet, whoever has written the node since, and the firing records it with `plan.node.update`, carrying `expectedRevision` (D6): the Helmsman judges the node against its criteria with the merged change in hand — met, the node is `done`, its `outcome` naming the pull request and its merge commit; not met, the node stays `active`, its note's first line names the merge and the next step, and the decision below — no commission since that write — commissions the next step. Either way the merge is acted on once: a `done` node is closed and the walk passes it, and an `active` one has a commission started after the merge, so the next firing reads it by its runs alone. A firing that recorded the merge but did not get its commission started leaves the pair true, and the next firing judges the same merge again and rewrites the same note line — the record is idempotent, and only a started commission retires it. A write refused on the revision means another firing or a person's conversation wrote first, and the firing ends as `wait`, writing nothing more. Having written, the firing walks the stream again and decides on the active node it finds, so marking a node `done` advances the stream in the same firing, to the next active sibling, or to the parent. A root that is `done` or `dropped` has no active node, and every firing on it is `wait`, writing nothing, until the operator removes the schedule. The decision is read from the active node's own runs (D5) and links, in this order, the first that holds deciding:

1. `wait` — the node is `blocked`, which the walk above stops at; a commission or a publication of the node is in flight, running or paused (a publication paused at its push approval, which is where a `request_changes` review lands under the push posture, is in flight); the node's pull request — the `pull_request` link its publication wrote — is open, as GitHub answers through the space's binding; or any of these reads failed, since a firing that cannot see the node's work must not add to it.
2. `stop` — the node's pull request was closed without being merged: a person closed the work, the shepherd never does (Plan 321 D6), and the next step would build on a change that will not land. Or the node's newest publication ended at the operator's word against it — its push approval denied: re-commissioning would ask the operator the question they just answered. Or the node's attempt budget is spent (below).
3. `continue` — the node has no commission since its last write, so its next step is the work; or its newest commission failed or was cancelled, or its newest publication failed or ended at `fix_before_merge` with nothing pushed, and the budget is not spent — a re-commission, briefed with the failed run's error or the review's findings by the run's id, as Local Publish's own `afterReview` hands a fix round on.

The attempt budget bounds the third case: a firing re-commissions a node at most `attempts` times — a static value of the schedule's template beside the root node, two by default — counted as the node's commissions that ended without the node gaining a pull request, among those started after the node's last write (`updated_at`). A `continue` firing writes nothing to the node beyond the merge it records, so its attempts accumulate; the `stop` that spends the budget writes the node, and a person who moves the node on or writes to it starts a fresh count. Nothing else re-commissions: a node in a state none of the three names — a run of a kind the firing does not know, a link it cannot read — is `wait`. A `wait` firing commissions nothing, cancels nothing, writes nothing to the node and ends; its run in the ledger is its whole record. A `stop` firing commissions nothing and cancels nothing; it marks the node `blocked`, its note naming why — the closed pull request, the denied publication, or the attempts spent with the last run's id — so the attention block shows the stream waiting on a person, and the walk holds the whole stream there. `blocked` alone decides `wait`, whatever the pull request's state, so every later firing waits until a person moves the node out of `blocked` — reopening the pull request does not, and is not meant to: the node stays the person's until they say what the work is now. A person who reopens the work sets the node `active` again, and from then the reopened pull request, open, holds the firings at `wait` until it merges; a person who drops the work drops the node, or marks it `done` with an outcome, either of which closes it, and the next firing's walk passes on to the next open node. A `continue` firing is the cold conversation of P1: it takes the node's next step and its criteria as the brief and starts a commission with `planNodeId`. The firing reads `plan.node.get` rather than its own attention block because the block shows another live conversation's runs only as a count (P1), and the work in flight that should hold a firing back is usually a previous firing's or a person's conversation. The interval and the stream the schedule names are operator knobs: both are set when the schedule is created and changed on it, and the plan picks no default for either. A recurring schedule's `maxFirings` is finite, and the schedule is renewed by the operator, as Plan 321 D2's renewal is the shepherd's own task. _Rejected:_ a step-graph custom agent, the shape of the shepherd's starter (Plan 321 D1) — continuing a stream is planning, which is the Helmsman's alone and refused to a skill (D3); a wake condition stored on the node and evaluated by an engine of its own — the schedule and the in-flight read already exist, and the condition is the two records the firing reads. _Exit:_ two firings observed on the live stack — one after the node's pull request merged that commissions the next node with that node's id in the commission's inputs, and one while that commission is in flight that decides `wait` and starts, cancels and writes nothing; and a firing after the node's pull request was closed unmerged that decides `stop` and marks the node `blocked`. In tests: a failed commission is re-commissioned up to the budget and the firing after it decides `stop`; a denied publication decides `stop` with no commission; a publication ended at `fix_before_merge` is re-commissioned with the review's run id in the brief; a write to the node restores the budget; a firing after a merge marks the node `done` with the pull request in its outcome and commissions the next active node, and the firing after it records nothing again; a merge followed by a person's write to the node is still recorded, and the node is not re-commissioned as though nothing had merged; a node marked `blocked` by a `stop` stays the active node, every later firing is `wait`, and its next sibling is not commissioned until a person moves it; a merge that does not meet the node's criteria leaves it `active` with the merge in its note and its next step commissioned; two firings racing to record one merge leave one write, the other refused on the revision and `wait`.

**Delivered** (P2b): `plan.node.next` (`plan`/`node`, read, no write to the plan) is the firing's first call and the one authority over its decision, by rule in `packages/cybernetic-runtime/src/plan/stream.ts`: `findActiveStreamNode` is the walk above; `decideStreamFiring` the rules, in the order the decision reads them — `blocked`, then in flight (a run of the node or any under it running or paused, or a pending `workflow_run_paused` attention item about one), so no merge is judged while the node's own work runs — read over one walk of every node under the active one, whatever its status, and where that walk stops at its depth or node bound the runs below are unread, so the firing is `wait` (`read_failed`) rather than deciding on fewer runs — then the merge, then the pull request open or closed unmerged, then the newest commission or publication started since the node's last write. The pull request is GitHub's to answer and the orchestrator holds no GitHub credential, so a node with a `pull_request` link — its newest, read by kind, and the `merge` record by its key, never from the page of links `plan.node.get` returns — is answered `read_pull_request` — owner, repo, number — and the firing reads it through the space's GitHub binding and asks again with `pullRequest` (`state`, `merged`, `merged_at`, `closed_at`, `merge_commit_sha`, or `read: "failed"`, which is `wait`); an answer for another URL is asked again. A merge is acted on when a commission started after `merged_at`, or when the node holds a `merge` link to the pull request — a link kind P2b adds, its ref the pull request's URL — which `record_merge` hands the firing to write with `plan.node.link` once its update is written; a note that only mentions the URL is not one, and a person's write after the merge does not hide it. A pull request closed unmerged stops the stream only where it closed after the node's last write, so a person who sets the node `active` again has said what the work is now. A declined push is a completed publication with `pushDecision: ask` and no `prUrl`; `fix_before_merge` with no `prUrl` is a re-commission carrying `reviewRunId`. Attempts are the commissions that ended since the later of the node's last write and its newest pull request link, counting the first, so a firing re-commissions while they number at most `attempts` and stops past it; `stop` carries the `plan.node.update` that marks the node `blocked` with why. A completed commission with no publication started, a cancelled publication, or an outcome that cannot be read is `wait`. A `continue` claims the state it was decided on — the node's revision, its newest round and its newest pull request link — with a Redis `SET NX` held by the firing's session for `PLAN_STREAM_CLAIM_TTL_MS` (thirty minutes), so of two firings that read alike one continues and the other is `wait` with cause `claimed`; the commission it starts changes the state, and from then the in-flight rule holds firings back. The decision's other reads are `createPlanStreamReads` (`streamReads.ts`): the node's commissions and publications by slug (`PLAN_STREAM_COMMISSION_SLUG`, `PLAN_STREAM_PUBLICATION_SLUG`, pinned to the catalog skills by a test), a completed publication's promoted outcome through `buildWorkflowRunResult`, and the pending pauses. The schedule's message is `planStreamScheduleInput(rootNodeId, attempts)`, `attempts` two by default and at most ten. `plan.node.next` is in `HELMSMAN_DISCOVERY_PRESET`, not pinned: no turn but a firing's calls it, and pinned it cost every turn about 800 tokens. `docs/dev/driving-work-through-the-loop.md` has the schedule and the decisions; the help article on this computer has the stream for the operator. **Open**: the live exit — the two firings and the `stop` above, observed on the stack after merge — and whether a firing whose Helmsman run ends before its commission does leaves the slice's publication to the conversation (`awaiting_publication` waits for it).

**P3 — Seen by the operator.** `GET /v1/spaces/:spaceId/plan`, the tree in the space, a `decide` node raising an Action Center item, done nodes with their outcome. _Exit:_ the operator marks a node done or drops a branch without the Helmsman. Built in two slices: P3.1 the read — the route and the page — and P3.2 the operator's writes through the same engine and the `decide` node's Action Center item.

**Delivered** (P3.1): `readPlanTrees` in `packages/cybernetic-runtime/src/plan/operations.ts` is the operator's read, beside the operations' reads in the one engine (D7). It walks the whole space, every status, with the bounds every read of the plan takes (`PLAN_TREE_WALK_BOUNDS`: 64 levels, 2,000 nodes), orders it by `orderPlanTree` and nests it by `nestPlanTree` (`tree.ts`), so roots and siblings read by position and then id. Each node is its summary with, where it has them, its `outcome` and `closedAt` (`PlanNodeStore.closingsOf`, read for the walked nodes only, so a summary still carries no outcome into the attention block), its newest `PLAN_TREE_NODE_LINKS_LIMIT` (20) links with `linksTotal` (`listLinksOfEach`, one query ranking each node's links by a window over them), and the runs in flight serving it — the space's newest `PLAN_TREE_RUNS_LIMIT` (200) across every node read, each placed under the node it serves, with `runsTotal`. A walk cut short names its bound in `truncated`, as `plan.node.list` does. `PlanTreeOutputSchema` (`operations/plan/schemas.ts`, recursive through `PlanTreeNodeSchema`) is the response. `GET /v1/spaces/:spaceId/plan` (`packages/server-runtime/src/routes/plan.ts`, surface `plan`, core) is authorised as a read of the space named in the URL and calls the engine through the tenant's plan store. The page is `SpacePlanPage` (`packages/web-product/src/ui/screens/space-plan.tsx`) over the shared `PlanTree` component, at `s/[space]/plan` in both editions and **Plan** in the sidebar: nodes nested by parent, each with its status, kind and title, a closed node's outcome (or why it was dropped), an open node's working line, its runs in flight opening their run pages and its links as references — a run and a conversation open their pages, a pull request or merge its URL as `repo#number`, a document its memory path or URL; a finding and a campaign have no page and read as text (`lib/plan-links.ts`). What a bound left out is said on the page: older links per node, runs past those placed, nodes past the walk. The page reads once, under `['space', spaceId, 'plan']`; it is not live. **Open**: the store's new SQL is covered by `planStore.pg.test.ts`, which skips without `DATABASE_URL` and was not run against a database in this slice.

**Delivered** (P3.2): `PATCH /v1/spaces/:spaceId/plan/nodes/:nodeId` (`routes/plan.ts`, beside the read) closes a node: `PlanNodeCloseSchema` — `expectedRevision`, `status` `done` or `dropped`, and `outcome`, which `done` requires with the same message as `plan.node.update`; nothing else is accepted. It is authorised as a write of the space in the URL, so a viewer is refused, and it is a person's only: `requireOperatorPrincipal` refuses an agent's credential whatever its grants (D7), and the person it returns is the write's stamp — `createdBy` on the engine's context and a `plan.node.close` row in the audit log with the node, its new revision and its status, taken from the session and never the body. It calls `updatePlanNode`, so the operator's write is judged by every rule the Helmsman's is: a stale revision is `409 PLAN_NODE_STALE` with `current` — the node's id, revision, status, `updatedAt` and the fields that differ (`PlanNodeRefusalDetailsSchema`) — in words for the operator rather than the agent's; a write that changes nothing is `422 PLAN_NODE_UNCHANGED` with the same `current`; a node not in the space is `404`; a server without Redis answers `503` rather than writing a node whose attention generation it cannot bump. Dropping a node closes the branch under it without writing the nodes below: an open list, the attention block and a stream's walk do not descend through a closed node already, and the branch's statuses stand if the node is reopened. The plan page's open nodes carry **Mark done** (asks how the criteria were met; confirm stays disabled until it is said), **Drop** — **Drop branch** where open steps sit under it, saying they leave with it — and, for a `decide` node, **Decide** in place of **Mark done** (`components/plan/PlanTree.tsx`). The write goes through `useApiMutation` (PATCH, the node's id in the path, the plan's query invalidated); a refusal shows in the node's own form, and a `409` reads the plan again so the operator chooses against the node as it now stands. A `decide` node raises an Action Center item (`planDecisionSource`, space-scoped, beside the others in `buildSpaceAggregator`): every open `decide` node whose ancestors are all open — `listOpenDecisions`, over the walk every read of the plan takes, at most `PLAN_OPEN_DECISIONS_LIMIT` (50) in tree order — is a `human_input` item `plan-decision:<nodeId>` with origin `plan_decision` (`nodeId`, `revision`), titled **Decide: …**, its summary the goal and then the criteria, `high` priority while the node is `blocked`, answered in the free-text box as **Decide** by anyone who may act in the space and reassignable like any input. Its marker and the resolve route's CAS compare the revision, so a question the Helmsman rewrites is a changed item to every viewer and an answer to the old one is refused with the item as it now stands; one whose node closed meanwhile is refused without one. The answer is recorded per D9: `updatePlanNode` to `done` with the trimmed answer as `outcome`, on the revision the item was shown at; an answer that is not text, or blank, writes nothing. Every node write — create or update, not a link — wakes the space's Action Center topic after it commits (`publishActionCenterWake`, source `plan_node_write`), so an item appears, changes or goes as the node does, the residual audit repairing a lost wake. D2's rule that a `decide` node raises an item rather than a run now holds for a stream too: `decideStreamFiring` answers an active `decide` node `wait`, cause `awaiting_decision`, before anything else of the node is read, so no firing commissions a decision; the walk still descends into a decision's open children first, so the inquiries under it run, and it waits on the decision once they close. The help articles say where a decision is answered and what the plan page's controls do; `docs/dev/driving-work-through-the-loop.md` has the write and the decision. ## 6. How it is proven

- **A cold session continues**: the P0 exit, measured twice with different conversations, the node id and criteria read from the commission run's inputs.
- **No lost update**: two sessions update one node; the second is refused with the first's revision.
- **A Runner cannot plan**: `validateSkillPlanSeparation` refuses a skill referencing `plan.node.update`; the guard test fails when the rule admits it. A delegation naming `plan.node.update` in `runner_tools` starts no Runner, and a Runner's turn whose state carries it is handed a surface without it.
- **No loop**: two sessions move A under B and B under A at once; one is refused as a cycle and the tree keeps its root — against the engine, and against Postgres where a database is configured.
- **Done needs an outcome**: `update` to `done` without `outcome` is refused by the schema.
- **Stale never**: a plan write followed by a turn in another session shows the new node in that turn's attention block.
- **Deleted with its space**: a sentinel per table in the cascade test.
- **The operator acts without the Helmsman**: on the live stack, the operator marks a node done and drops a branch from the plan page with no Helmsman turn, and the next turn's attention block and the next firing read the change; a write against a revision the Helmsman has moved past is refused with the current one and writes nothing; a `decide` node shows in the Action Center, the answer given there is the node's outcome, and no firing commissions it.
- **It wakes, and waits while work is in flight**: a scheduled firing after the node's pull request merged records the merge on the node — `done` with the pull request in its outcome, or the merge in its note — and commissions the stream's next active node, its id in the commission's inputs, and the next firing does not record that merge again, nor does a person's write after the merge hide it; a `stop` holds the stream at the `blocked` node, its later siblings unstarted; a firing while a commission or publication of the node is in flight, or its pull request is open, decides `wait` and starts, cancels and writes nothing; a firing after its pull request was closed without merging decides `stop`, starts nothing and leaves the node `blocked` with the pull request named; a node whose commission failed is re-commissioned at most `attempts` times before a firing decides `stop`, and one whose publication the operator denied is never re-commissioned.
- **Nothing in the file**: after P1, the plan document's findings table has no new rows and the slice's record is complete on its node.
