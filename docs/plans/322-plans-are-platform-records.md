# Plan 322 — Plans are platform records

**Status:** 🔨 P0 and P1 built and tested without a live stack; P0's exit — a cold conversation continuing a stream from the node — and P1's — a whole slice with every record on its node — are proven on the live stack after merge. P2–P3 not started.

**Builds on:** Plan 315 (the loop and the stream protocol that drives it), the campaign engine (`packages/cybernetic-runtime/src/campaigns.ts`), the attention block the Helmsman reads each turn (`packages/cybernetic-runtime/src/attentionBuilder.ts`), the `workflow.campaign.*` inline-op family as the template for an operation family with one authority for the agent path and the operator path, and the vocabulary Plan 299 §3.4 fixed for a tree of intentions. It takes from 299 only the tree, and builds it standalone for the on-demand Helmsman.

## 1. Problem

The plan that drives a stream of work lives in a markdown file in the repository, and every stream writes that one file: its decisions, its delivery notes, its findings. In one day `main` moved under one pull request (#72) three times with no content in the conflict, each costing a merge round of the loop; #68 met the same conflict the day before. A Helmsman conversation starts cold: it reads a protocol document to learn what the stream is, and every slice begins with a hand-written brief that restates where the work stands (F103, F107). The shepherd (Plan 321) needs "what is happening to this branch right now" and plans to assemble it from a pull-request comment and a memory-store lease, because nothing on the platform holds it. Three consumers want the same record, and none has it.

What exists is adjacent and not it. A campaign is one goal with one metric for one skill (`campaigns`, `packages/database/src/schema/tenant/campaigns.ts`). A learning is keyed by skill or campaign and cannot point at an arbitrary record (`coach_learnings`, `CoachLearningScopeSchema`). The memory store holds untyped documents under paths, with no join to the runs that did the work. A workflow run carries a `campaign_id` and a `metadata` bag, and no purpose. The attention block the Helmsman reads each turn knows the active runs and the pending proposals, and nothing about why they run.

The earlier plans in this area (88, 99, 215, 234, 299) were design exercises; part of each was built, part was not, and none was driven to a measurable end through the Helmsman. The stream that produced this plan was: forty findings and ten slices landed by briefing the Helmsman, reading reviews and iterating. This plan is sized to that method. The goal is fixed; the design below changes wherever use shows it should.

## 2. Decisions

**D1 — A plan is a tree of nodes in Postgres, per space.** `plan_nodes` carries parent, kind, title, goal, success criteria, status, a bounded working note, and a revision counter. _Rejected:_ a memory-store document — untyped, path-addressed, no join to runs, and a second session's write can lose the first's; a markdown file — the problem. Columns over a JSON bag, because the Helmsman, the attention block and the operator surface all read the same fields and a query on status or parent is the common case.

**D2 — A node's kind is a mode of work, not a classification, and the vocabulary extends Plan 299's.** 299 §3.4 has `execute | investigate` and `active | suspended | waiting | done | dropped | failed`. This plan adds the kind `decide`, because a node whose outcome is the operator's choice is neither work nor inquiry and must raise an Action Center item rather than a run (P3); and the status `blocked`, because a node waiting on a person is a different state from one waiting on a run, and the attention block tells them apart. It drops `suspended` and `failed` until a node can be suspended by a policy or failed by a budget, neither of which exists here. Success criteria may be provisional and are revised with the reason in the note. Breakdown is recursive by adding children; a node is done against its own criteria — the Helmsman marks it, with the outcome recorded, never automatically from its children, because the criteria are the parent's and the children are one attempt at them. _Rejected:_ dependency edges, wake conditions, commitment policies and budgets in P0 — each is a 299 element with a reason, and none is needed to replace the markdown file; dependencies arrive in P2 when the shepherd reads the tree.

**D3 — The operations are Helmsman tools, `plan.node.*`, never a skill, and never a Runner's.** Planning is open-ended; a skill's worth is a validatable procedure (Plan 190), and the eval plane's rule holds here: a run may serve a node and may never rewrite the plan it serves. The exclusion is a validation rule, not a test: `isPlanOperation` (fail-closed string prefix, beside `isEvalPlaneOperation`) and `validateSkillPlanSeparation` refuse a skill that references `plan.*`, and a guard test probes the rule with a violation. What reaches a Runner at run time rather than through an authored skill — a delegation's `runner_tools` and capability grant, the promotable tier, the surface a Runner's turn is handed — asks one predicate, `isRunnerExcludedOperation` (the eval plane and the plan), so a plane added to it is excluded from every channel at once. The grant migration 218 gives the system profiles stays: the Helmsman needs it, and the Runner exclusion is what keeps the plan the Helmsman's. The step type is `plan`, group `node`, so the operation reads as what it is; the capability group `plan:node` is added to the system profiles in the same migration, which also drops the `plan.read` / `plan.write` groups migration 020 seeded for a step type that never existed. _Rejected:_ `workflow.plan.*` to save the routing line — a plan is not a workflow, and the agent reads operation names as ontology.

**D4 — The active tree is in the attention block, invalidated by every plan write, and a fresh session reads it before anything else.** `HelmsmanAttentionContext` gains the space's active nodes: title, kind, status, the note's first line, and the in-flight runs under each. The block is cached (`getAttentionCache`) and invalidated by listed entity events (`attentionCacheSubscriber.ts`), so every `plan.node.*` write bumps the attention generation the way a coach or procedure event does; without that the tree goes stale until an unrelated event, and the P0 exit cannot be met. _Rejected:_ a `SpaceContext` section — also cached, invalidated per step type, and projected per role; the attention block is where in-flight state already lives, and the invalidation is one call in either case.

**D5 — A run carries the node it serves.** `workflow.run.start` takes an optional `planNodeId`, stored as `workflow_runs.plan_node_id` with an index, so the attention block renders runs under their nodes and a node's runs are derived, never maintained by hand. A publication or commission started for a node links its pull request and its result to the node when it ends. _Rejected:_ `metadata.planNodeId` — a zero-migration link that nothing can index or join.

**D6 — Writes are compare-and-set on the node's revision.** Two sessions in one space may work the same tree; `update` carries `expectedRevision` and a stale write is refused with the current node, the way `memory.store.put` refuses on `expectedHash`. _Rejected:_ a revision log per write in P0 — the refusal is what prevents loss; the history of a node is its links and its note, and a log is added only if reconciliation across sessions turns out to need it.

**D7 — The operator reads the same authority, when the operator reads it.** The engine functions in `packages/cybernetic-runtime/src/plan/` are the one authority; the inline ops call them in P0, and `GET /v1/spaces/:spaceId/plan` calls them in P3 when a surface renders the tree, as the campaign routes do. Until then the stream is driven from the Helmsman and the Workbench.

**D8 — Campaigns and learnings are left where they are until the record has carried a slice.** A node may link to a campaign; whether a campaign becomes a node kind is decided after P1 with evidence. A learning gains `scope: plan` with a node id in P2, when the record exists to attach to. _Rejected:_ redesigning either now.

## 3. Design

### 3.1 Records

`plan_nodes` (per space): `id`, `space_id`, `parent_id`, `kind`, `title`, `goal`, `criteria`, `status`, `outcome`, `note`, `revision`, `position`, `created_by`, `created_at`, `updated_at`, `closed_at`. In P1, `plan_node_links`: `node_id`, `space_id`, `kind` (`run | session | pull_request | document | finding | campaign`), `ref`, `label`, `created_at`; and `workflow_runs.plan_node_id`. Zod in a `plan.ts` beside `campaign.ts` under `packages/schemas/src/cybernetic/`; the length caps on `goal`, `criteria`, `outcome` and `note` are storage ceilings in the thousands, since they hold model-authored prose a person reads. The rule that a node is done against its criteria lives in the schema: `update` with `status: done` requires `outcome`, the statement of how the criteria were met, and is refused without it.

### 3.2 Operations

| Operation          | Phase | Does                                                                                                            |
| ------------------ | ----- | --------------------------------------------------------------------------------------------------------------- |
| `plan.node.create` | P0    | a node under a parent (or a root), with kind, title, goal, criteria                                             |
| `plan.node.update` | P0    | status, note, criteria, title, parent, position — compare-and-set on `expectedRevision`; `done` needs `outcome` |
| `plan.node.get`    | P0    | one node with its children and, from P1, its links and in-flight runs                                           |
| `plan.node.list`   | P0    | the space's tree, filtered by status or root, bounded                                                           |
| `plan.node.link`   | P1    | a typed reference from a node to a run, session, pull request, document, finding or campaign                    |

Engine functions in `packages/cybernetic-runtime/src/plan/`, called by the inline handlers under `handlers/inlineOps/plan/`. Registered in `packages/schemas/src/catalog/registry.ts` with `usage.whenToUse` carrying what the schema cannot (open the node before briefing a round; a round's brief is the node's goal and criteria), pinned for the Helmsman in `catalog.coreOperations`.

### 3.3 What a fresh session sees

The attention block renders, for each active root: `[execute] 315 · Local first-run ergonomics — active — next: F114 findings out of the plan file` with its active children indented, and from P1 the in-flight runs under each by slug and status. The Helmsman's first move in a stream is `plan.node.get` on the node named, and its briefs are the node's goal and criteria plus what the operator adds.

## 5. Phases

**P0 — The record, the tools, the block.** _Built (#79, 2026-10-05)._ The exit was measured the same morning and **not met**: a cold conversation told only "continue the Plan 315 stream" read the tree in its attention block and still acted on the loudest item beside it, another stream's `request_changes` review, cancelling that stream's paused publication and commissioning its fix on that stream's branch. The block gives a cold session two answers to "what now" — the tree's next step and the attention items of every run in the space — and nothing binds the conversation to a node or marks another root's items as not its own. That is P1's first job, ahead of the links: a conversation is bound to the node it continues, attention items are grouped under the node whose run produced them, and an item under another root renders as other work with no call to act.

`plan_nodes`, the four P0 operations, the attention section with its invalidation, the capability group, the separation rule. _Exit:_ in Full Circle, a Helmsman conversation that is told only "continue the Plan 315 stream" reads the active node from the attention block, names its next step, and starts a commission whose task carries that node's id, goal and criteria — checked in the run's inputs — with no hand-written brief; a second conversation's stale `update` is refused with the current revision and loses nothing. ✅ Built.

**Delivered**: migration 218 creates `plan_nodes` with an index on `(space_id, status)` and one on `(space_id, parent_id)`, a parent a foreign key into the same table; it grants `plan.node` read and write to Full Access, Standard and Personal Safe — `Standard` less the execution lanes, which a plan is not, and the profile migration 217 found local spaces holding — and read to Read Only, and removes `plan.read` / `plan.write` from every profile's allowed and denied lists. `plan_nodes` is in `DIRECT_SPACE_ID_TABLES` with its sentinel. `PlanNodeKindSchema`, `PlanNodeStatusSchema`, the node and its summary are in `cybernetic/plan.ts`; goal, criteria, outcome and note hold 8,000 characters and a title 500; `update` refuses `done` without `outcome`, and an update naming nothing to change, each with a message that says how to meet it. `plan.node.create / update / get / list` are registered and pinned on the Helmsman, and the `plan` bundle, loaded, owns `plan.node`. The engine in `packages/cybernetic-runtime/src/plan/` is the one authority: `update` compares and sets on `revision` and refuses a stale write with `PLAN_NODE_STALE` and what a retry needs — the node's id, revision, status and `updatedAt`, and the fields the update names whose value differs from it — never the node itself, since a refusal travels inline on the results stream and `plan.node.get` reads the node; a move under the node itself or a descendant is `PLAN_NODE_CYCLE`, checked in the transaction that writes the move, which locks the rows from the new parent up to its root (`SELECT … FOR UPDATE`) as it walks them by key — two moves that would close a loop between them deadlock, and the one Postgres ends is refused as a cycle on its next attempt — and no node sits more than 64 levels below its root (a root is depth 0): a create under a node at depth 64, or a move whose new parent's depth plus the height of the subtree it carries would pass 64, is `PLAN_NODE_TOO_DEEP` with the depths named, checked in the write's transaction, which for a move holds the moved node's row first so a create below it waits for the measurement — a create and a move whose walks cross deadlock and retry as two moves do; reopening a `done` or `dropped` node clears its outcome and keeps it as the note's first line, and a reopen that would carry the note past its 8,000 characters is `PLAN_NODE_NOTE_TOO_LONG` with the ceiling and the length it would reach, so the caller trims the note (or the outcome) first, and `update` refuses an `outcome` beside an open status — the schema in one request, and the engine against the node, so an `outcome` alone on a node that is or stays open is `PLAN_NODE_OPEN_HAS_NO_OUTCOME`, judged on the revision the write is pinned to; an update whose fields equal the node's is `PLAN_NODE_UNCHANGED` with the same details as a stale write, and moves neither its revision nor the attention generation, so a repeated no-op reaches the agent's failure accounting as one decision repeated; a position is bounded by its `INTEGER` column (`PLAN_NODE_POSITION_MAX`), and a node placed after a sibling at that ceiling shares it; `get` returns the node and up to 100 children, `list` the space's nodes parents first, open by default — a list of open statuses walks through open nodes only, so closed history does not count toward its ceiling and a node under a closed one is reached by naming the closed status — at most 200, read by walking down from the roots or from `rootId` (found by key) at most 64 levels and 2,000 nodes, and when a bound cuts it short the result names it — `limit`, `depth` or `nodes` — with its value; siblings read by position and then id, a rule stated once in `tree.ts` that the store's `ORDER BY` is built from; every write bumps the space's attention generation. The attention block opens with the open tree — open roots, their open children indented, at most 30 lines and a pointer to `plan.node.list`, which says "more than" the count it read when the walk stopped at a bound — each line `[kind] title — status — the note's first line [nodeId: …]`; a node under a closed parent is left out. `isPlanOperation` (prefix, fail closed) sits beside `isEvalPlaneOperation`; `validateSkillPlanSeparation` beside its eval sibling, in the same write- and read-side validity, as `skill_references_plan_op`. At run time `isRunnerExcludedOperation` holds both planes off a Runner: a delegation naming either in `runner_tools` or its capability grant is refused and starts no Runner, and the promotable tier and the `runner_tools` a Runner's turn merges drop them. The inline handlers parse their input with the schema, so the refinement holds there too, and surface the engine's refusals as validation errors with their details. **Open**: the exit, measured twice in Full Circle after merge.

**P1 — Work flows through the node.** `plan_node_links` and `plan.node.link`; `planNodeId` on `workflow.run.start`; commissions and publications started for a node link their pull request and result; Plan 315's remaining items are the first tree, and its findings become nodes of kind `investigate` so the markdown table stops growing. Its first job came from P0's exit, measured and not met: a cold conversation told only "continue the Plan 315 stream" read the tree and still acted on the loudest item beside it, another stream's `request_changes` review — cancelling that stream's paused publication and commissioning on its branch. The block gave a cold session two answers to "what now", and nothing marked another root's work as not its own; P1 removes the second answer. _Exit:_ one whole slice — brief, commission, review, publish, merge — runs with every record on the node and the plan document untouched. ✅ Built.

**Delivered**: migration 219 adds `workflow_runs.plan_node_id` (UUID, nullable, no foreign key as with `campaign_id`), indexed where it is set, and `plan_node_links` — `node_id`, `space_id`, `kind`, `ref`, `label`, `created_at` — keyed by `(node_id, kind, ref)`, which is the index a node's links are read by and makes one record linked to a node once, with `(space_id, node_id)` for the space's delete; `node_id` references `plan_nodes` on delete cascade. `plan_node_links` is in `DIRECT_SPACE_ID_TABLES` ahead of `plan_nodes`, whose delete would otherwise take the links uncounted, with its sentinel in the cascade test. `workflow.run.start` takes `planNodeId`: a named node not in the space is `PLAN_NODE_NOT_FOUND` and nothing starts; a run a task starts serves its parent run's node unless it names one, so a publication's review carries the publication's. `plan.node.link` (kind `run | session | pull_request | document | finding | campaign`; a run, session or campaign by its UUID, a pull request by its URL) is registered and pinned on the Helmsman beside the four; a node that is not in the space is `PLAN_NODE_NOT_FOUND`, and a record already linked is `PLAN_NODE_LINK_EXISTS` with the link held, so a repeat reaches the agent's failure accounting. A node title is one line (`PLAN_NODE_TITLE_ONE_LINE_MESSAGE`, a `pattern` in the catalog's schema too). `plan.node.get` adds the node's links (newest first, 100) and the runs in flight — running or paused — for it and every node under it, whatever their status (50, with totals). `plan.node.list` under a `rootId` reads the root whatever its status, so a closed root lists the open work under it and is itself listed only when its status is named. When a run serving a node ends — completed, failed or cancelled — `completeRun` links it to the node (`<slug> <status>`) and, where its promoted output holds `prUrl` (`RUN_PULL_REQUEST_URL_OUTPUT`, which Local Publish's `find-pr` and `open-pr` promote, pinned by its test), the pull request; a link already held — a second publication appended to the same branch — is left as it stands. The attention block is rendered per conversation over the space's cached data: a conversation's roots are those of every node a run it drove serves (`workflow_runs.session_id`, which a run a task starts inherits), read each turn. Active runs, and pending attention items with their run's slug and node, are placed by walking each node up to its root. An item is a conversation's own when that conversation drove the item's run (`workflow_runs.session_id`) or, for a run serving a node, has taken up the same root. A run serving no node belongs to the session that drove it (`workflow_runs.session_id`, inherited by a run a task starts) while that session is a Helmsman conversation that has not ended: that conversation's block lists it, with its paused-run items, and every other conversation counts it among the other work, with no slug, run id or status. A run serving no node that no live conversation owns — started from the web UI, through `run_operation`, or by a conversation that has ended — is the operator's, and every conversation's block lists it in full; the active-run read carries whether the driving session is such a conversation (`drivenByLiveConversation`, joined from `sessions`), so the space's cached block serves every conversation. The cached block holds the newest ten items under each root and each conversation's ten newest serving no node — read as each node's newest ten, and each driving session's, so one stream's items cannot push another's out — and every root's and every conversation's exact count from the store; this conversation's runs and its ten newest items sit indented under their node in the tree, its work on a node the tree does not show is listed with that node's id, items of its own past the ten are one line naming `workflow.run.list_attention`, every run under another root, every run serving no node that another live conversation drove, and every item not its own is the one line `other work in this space, not this conversation's: N runs, M items`, its items counted rather than sampled, naming `workflow.run.list_attention` for those items and `workflow.run.detail` for a run whose id the operator gives so the count is never a dead end, and the runs serving no node it lists — its own and the operator's — and its own items serving none follow the tree in their own lists, headed "outside the plan" when some do serve one, the items with how many more there are. The block is the state as it stands: writing an attention item and consuming one bump the space's attention generation once committed, as does every run transition (`emitRunUpdated`: start, pause, resume, terminal), after the transaction that writes the transition and its attention item together. An attention item is a wake-up, read once, by a turn the model has answered: the block shows a conversation only its own items, and the agent turn's step hot state records the ids it showed (`attentionItemIds`); the turn's step-succeeded path consumes them by its session (`consumeAttentionReadByTurn`), so the next turn no longer shows them, while a turn that fails or is retried shows them again, and no conversation consumes another's. A run's next item — a pause after a resume, or its end — consumes the run's earlier `workflow_run_paused` in the same write; counts are of pending items, and `workflow.run.list_attention` with `includeConsumed` lists the consumed ones with their `consumedAt`. A conversation that has started nothing for the plan reads every run in it as another's until it starts one; `plan.node.get` on its node is where it finds its stream's work in flight. Commission Change (version 3, bundle `local-commission` 3) tells the Helmsman to start a commission with `planNodeId` beside its inputs, the node read first, and its publication with the same. Neither skill declares `planNodeId` as a run input of its own: the start's field is the one place a run's node is named, so a run cannot carry two, and the review takes the publication's from the harness; Local Publish's description, at the catalog's 5,000-character ceiling, is unchanged. `docs/dev/driving-work-through-the-loop.md` has a round read its node first and name it on the commission and the publication. **Open**: the exit, measured in Full Circle after merge; `workflow.run.list_attention` still lists every stream's items unplaced.

**P2 — Learnings and dependencies.** `coach_learnings` gains `scope: plan`; dependency edges with a condition on the dependency's outcome, validated for cycles. _Exit:_ a learning written on a node is read by the next session that opens it; the shepherd's `read-in-flight` task reads the branch's node and writes no pull-request comment.

**P3 — Seen by the operator.** `GET /v1/spaces/:spaceId/plan`, the tree in the space, a `decide` node raising an Action Center item, done nodes with their outcome. _Exit:_ the operator marks a node done or drops a branch without the Helmsman.

Deferred, not planned here: budgets and metabolism (299 §3.9), commitment policies and wake conditions, a revision log, campaigns as a node kind, importing the earlier plan archive. Only the work a stream picks up becomes nodes.

## 6. How it is proven

- **A cold session continues**: the P0 exit, measured twice with different conversations, the node id and criteria read from the commission run's inputs.
- **No lost update**: two sessions update one node; the second is refused with the first's revision.
- **A Runner cannot plan**: `validateSkillPlanSeparation` refuses a skill referencing `plan.node.update`; the guard test fails when the rule admits it. A delegation naming `plan.node.update` in `runner_tools` starts no Runner, and a Runner's turn whose state carries it is handed a surface without it.
- **No loop**: two sessions move A under B and B under A at once; one is refused as a cycle and the tree keeps its root — against the engine, and against Postgres where a database is configured.
- **Done needs an outcome**: `update` to `done` without `outcome` is refused by the schema.
- **Stale never**: a plan write followed by a turn in another session shows the new node in that turn's attention block.
- **Deleted with its space**: a sentinel per table in the cascade test.
- **Nothing in the file**: after P1, the plan document's findings table has no new rows and the slice's record is complete on its node.
