# Plan 321 — The loop recovers from CI

**Status:** 🔨 P0 measured (§5); P1 built — the skill, its bundle and agent, the endpoints and their tests (§5 P1 _Delivered_); its live-fire exit runs on the node

**Builds on:** Plan 315 (the loop: commission → review → publish; `mergeFrom`; the push posture), the catalog's `pr-shepherd` skill (the hosted code lane's shape of the same job), the scheduler (`agent.schedule.create`), and the `github` connector.

## 1. Problem

The loop ends at the push. Local Publish commits, scans, reviews and pushes, and opens the pull request; what happens to that pull request afterwards is read by a person. In the first week of running the loop on this repository, three pull requests failed CI after an autonomous push — a flaky timing test, a dependency advisory that arrived between two pushes, a merge conflict with `main` that the PR workflow refused to run on — and each was found by the operator, diagnosed by hand, and fixed by a brief written by hand. The always-on target of Plan 315 has a hole exactly there: nothing on the platform notices a red check, and nothing turns it into a commission.

A shepherd that does this starts cold every time. A scheduled run is a new session with no memory of the last one, in a space where other work is in flight: a publication of the same branch may be paused at its approval, a commission for the same pull request may be running under another operator's conversation, a review may be about to return. A shepherd that reads only the pull request will commission a fix for a failure another run is already fixing, re-fix the same failure on every firing, or push onto a branch while a person is working on it. The platform has the pieces — `workflow.run.list_attention`, the handoff comment the hosted `pr-shepherd` leaves on a pull request, the memory store — and no skill that composes them into "what is happening to this pull request right now".

What the hosted `pr-shepherd` already settles: one invocation is describe → rehydrate → decide → fix / merge / abandon / wait → handoff; the handoff comment on the pull request is the durable record the next invocation reads; the fix runs on the existing branch; review and learning happen outside the skill. What it cannot do here: it runs on the hosted code lane (`code.agent.run`, `code.repo.push`), which the local edition does not have, and its idea of "in flight" is the handoff alone.

## 2. Decisions

**D1 — The shepherd is a skill, run by the Runner, started by an agent that decides nothing, and every decision it makes is read from data.** A schedule does not start a skill: it starts an agent run, and the skill runs because that agent calls `workflow.run.start` (§5 P0.1). A schedule carries only a persistent target, `platform-role` or `custom-agent`, never an inline agent (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/scheduleCrud.ts:388`), and the platform agent that holds `workflow.run.start`, the Helmsman (`cybernetic-helmsman`), is a model acting on a template — the prompt rejected below. The agent that decides nothing is therefore a custom agent (`custom-agent`, `packages/schemas/src/runtime/agentTarget.ts`): a step-graph agent, of the kind `agent.manage.create` writes, whose definition is one operation step — `workflow.run.start` of `local-pr-shepherd`, with the skill's slug and the folder binding, `bindingId`, as literal values — and no model turn at all: no `ai.agent.turn`, no prompt, nothing to drift. The step's inputs are fixed when the agent is installed — no `$memoryRef`, which fails the firing, and nothing derived at fire time, which a template cannot carry. The Local PR Shepherd bundle installs the agent beside the skill, under its slug, so the operator creates nothing by hand, and the schedule targets that agent by its slug: the target it stores is `{ kind: 'custom-agent', agentId }`, the id of the agent the slug names. `local-pr-shepherd` is a catalog skill on the host lane: it finds the pull requests the loop opened, reads each one's live state, decides `fix | wait | abandon | leave`, and for `fix` commissions the coding agent on the pull request's branch with `base: <branch>` and `mergeFrom: origin/<base>` and publishes the result appended, through Local Publish, under the folder's posture. No step of the skill is a Helmsman conversation, and the agent's run that starts it reads nothing about pull requests. _Rejected:_ a Helmsman prompt that says "check the pull requests" — a cold session with prose instructions is the shape that commissions duplicate work; what a cold run needs is the state as inputs to its tasks (D3), not a paragraph about being careful.

**D2 — The trigger is a schedule on the local edition, and a webhook later where there is a public address.** A recurring schedule (`agent.schedule.create`, `action: 'start_run'`, `cron`) starts a run of the shepherd's custom agent every five minutes while the executor is paired, and that agent's one operation step starts the skill (D1); the interval is an operator knob whose default, `*/5 * * * *`, is derived from GitHub's rate budget in §5 P0.2. The schedule's target is the custom agent the Local PR Shepherd bundle installs, named by its slug; its template is static JSON, checked at creation only for non-emptiness, and the step reads none of it — the skill's slug and `bindingId` are literals in the agent's definition. The firing carries nothing else: the skill discovers its pull requests itself, because a template carries no live value and no cursor across firings. The appliance's own webhook ingest is the hosted edition's trigger, where `api.aflow.ai` can receive GitHub's `check_suite` events; a laptop cannot, so it polls. A recurring schedule's `maxFirings` is finite by design; the skill's last task renews the schedule when it is near its cap, with the same target and template, so the shepherd does not expire silently.

**D3 — A cold run reads four things before it acts, and acts on none it did not read.**

1. **The pull requests that are its to tend**: open pull requests whose head branch is under the folder's publish prefix and whose body carries Local Publish's marker. A pull request a person opened, or one labelled `hands-off`, is left alone.
2. **The head's checks**: `listCheckRuns` on the head sha. The decision reads the conclusions, not the names.
3. **The handoff**: one comment per pull request, `<!-- aflow:shepherd -->`, carrying `attemptCount`, the `checkRunId` of the last failure acted on, the head sha it acted on, and the run id of the fix it commissioned. Written by the shepherd alone.
4. **The space's in-flight work on that branch**: a lease in the memory store, `shepherd/<owner>/<repo>/<branch>`, taken for the duration of a fix and released at its end, holding the run id and the time; and a bounded read of the space's runs by workflow and input field — `workflow.run.list`, space-wide and one page at most, for the non-terminal runs, paused included, of `publish-local-changes` whose `branch` input is the branch and of `commission-change` whose `base` input is the branch. The attention list cannot answer this: its items name a run, never a branch (§5 P0.4). A branch with a live lease or a non-terminal run on it is `wait`, whoever started that run — a person's conversation included.

The four reads are tasks with typed outputs, and the deciding step receives them as its inputs. A read that fails ends the run as `wait` with the reason, never as a guess.

**D4 — Same failure, same answer: a check run is acted on once.** A failing check whose `checkRunId` equals the handoff's is `wait` — CI has not re-run since the last fix, or the fix is still being published. A new failing check run on a head the shepherd already pushed increments `attemptCount`; at the budget (three, an operator knob) the shepherd posts why it stopped and raises one Action Center item, and leaves the pull request alone until a person moves it.

**D5 — The fix brief is assembled, not written.** The commission's task is built from data: the pull request's title and body, the failing jobs' names and the last part of each failing job's log (`listWorkflowRunJobs` and `getJobLogs` join the `github` connector; the excerpt is bounded and stored as a payload the task references), the handoff's record of earlier attempts, and the standing rules every commission carries (the checks to run, no process started, nothing under `.aflow/`). A conflict with `main` is not a fix the shepherd writes: with `mergeFrom`, the commission starts on the merged tree and resolves it (Plan 315 D15), and the publication folds it into one merge commit.

**D6 — The shepherd never approves, merges or closes.** It pushes only through Local Publish, under the folder's posture, so an unclean scan or a `request_changes` still asks the operator; it holds no grant and cannot mint one (Plan 253). Merge-on-policy is the next plan, not this one; `abandon` is a comment and an Action Center item, not a closed pull request. _Rejected:_ the hosted skill's `merge` branch with an HITL gate — the local loop's rule is that the merge is the operator's until a policy says otherwise, and that policy is not written.

**D7 — What a person asks Helmsman is answered from the same records.** "What is the shepherd doing" is `workflow.run.list_attention` plus the handoff comments, surfaced in the space context as the shepherd's recent decisions per pull request. Helmsman gets no prose about the shepherd; it gets the records.

**D8 — Which remedy a red check wants is a decision task; whether to act stays a rule.** The rules of D3 and D4 are `when`-style comparisons on data with no model — the same `checkRunId` is `wait`, the budget is `abandon`, the `hands-off` label is `wait` — evaluated by one rule step, `workflow.run.decide`, whose first rule that holds is the decision and its reason, and whose default is `fix`. Only once a pass has decided `fix` does a decision task (Plan 316 D4, stored as routes, Plan 318) read what no rule can: its state is the failing jobs' names and log excerpts, the pull request's title and body and the handoff's record, and its one `choice` — `flaky_or_timeout`, `code_defect`, `dependency_advisory`, `base_conflict`, `ci_outage` — routes a confident answer to re-running the failed jobs, the fix commission, a commission that bumps the dependency through `resolutions`, a merge round with `mergeFrom`, or nothing (`wait` on CI). `minConfidence` is set and `onUndecided` is the fix commission, which is what a pass did with every failure before the question was asked, so abstaining costs nothing new; a decision that could not be made at all routes nowhere, and the lease is still released and the record written. The step names no model: the space's decision model answers. The decider never gates a push or a merge (316 D9) — the publication's own posture clears the push, and the guard of the publish task reads only whether a commission returned a change. This replaces §3.1's "the remedy is not a decision task in P1": the measurement there (1 of 5) is why abstention, not a guessed label, carries every case the decider is unsure of.

**D9 — One pass tends one pull request, and every read is a task the rules read whole.** A workflow task is one operation, and the graph runs no task per item, so a pass reads the loop's pull requests and tends the first: those not labelled `hands-off` first, then the most recently updated; `pullNumber` aims a manual pass at one, which must still be one the loop opened. The reads are GitHub's answers shaped by the API executor into typed records before anything is cut to fit inline (`response.transformPresetId`: `loop_pulls`, `loop_pull`, `loop_checks`, `loop_handoff`, `loop_failing_jobs`; `getJobLogs` carries `job_log_tail` itself): a rule compares one field of a record, never a field of GitHub's whole object, and a body that does not shape fails the read. A read GitHub refused is `wait`, by rule. The lease is read with `memory.store.query` over the branch's directory — `memory.store.get` refuses a path with no document, which is the normal case — and taken with `memory.store.put` `writeMode: 'create'`, so the second of two passes on one branch fails there with nothing commissioned and nothing released. The excerpt bound of D5 holds as the excerpt is carried, escaped as JSON with colour codes taken out, so a log task's output stays one inline payload the classifying and commissioning tasks bind to by reference to that task. A publication the shepherd starts waits through its approval: a task waiting on a run it started now waits through that run's operator approval (`pauseCause: 'needs_decision'`) instead of cancelling it, and the chain of task-started runs goes three deep, so the shepherd's publication reviews and asks exactly where one started by hand would. The handoff is written by template, its record `key: value` lines inside `<!-- aflow:shepherd … -->` that `parseShepherdHandoff` reads back; a template has no arithmetic, so the handoff read carries the next attempt count, and `$text` writes a count or an id as text and is absent on null, so a part falls through `$firstOf` to its default. Everything after the lease is optional, and a binding to an optional task that failed reads as absent, as a skipped one does — which is what lets the release and the handoff run whichever way a commission or a publication ended. The pass is twenty-three tasks; a stored workflow holds thirty-two (`WORKFLOW_TASKS_MAX`), and compose-skill's drafts keep their own bound.

## 3. Design

### 3.1 Tasks

| Task             | Operation                                                                | Reads / does                                                                           |
| ---------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| `read-folder`    | `host.binding.inspect`                                                   | the branch prefix, the posture, `origin`                                               |
| `list-prs`       | `api.http.call` `listPullRequests`                                       | open pull requests, filtered to the prefix and the marker, `hands-off` last            |
| `read-pr`        | per pull request: `getPullRequest`, `listCheckRuns`, `listIssueComments` | head sha, checks, the handoff                                                          |
| `read-in-flight` | `memory.store.query`, `workflow.run.list`                                | the lease and the non-terminal runs, paused included, whose branch input is the branch |
| `decide`         | `when` rules only (`workflow.run.decide`)                                | `fix \| wait \| abandon \| leave`, with the reason; `fix` where no rule names another  |
| `read-failure`   | `listWorkflowRunJobs`, `getJobLogs`; then the remedy decision (D8)       | failing jobs and bounded log excerpts, as a payload                                    |
| `lease`          | `memory.store.put`                                                       | the lease, written before the commission                                               |
| `fix`            | `host.harness.run`                                                       | `base: <branch>`, `mergeFrom: origin/<base>`, the assembled task                       |
| `publish`        | `workflow.run.start` Local Publish                                       | appended onto the branch, `wait: 'until_complete'`                                     |
| `handoff`        | `createIssueComment` / edit                                              | the updated record, every pass                                                         |
| `release`        | `memory.store.delete`                                                    | the lease, on every terminal path                                                      |
| `renew`          | `agent.schedule.create`                                                  | the next schedule when this one nears `maxFirings`                                     |

`decide` is a rule. The four reads of D3 decide `fix`, `wait`, `abandon` and `leave` without a model, and a failure no rule names is `fix`. The remedy for a `fix` is a decision task (D8), routed, whose abstention is the fix commission — a commission briefed with the log excerpt, which reads what a rule cannot. Measured on this stream's own CI failures (Plan 316 §7), Jev, gpt-6-luna and claude-opus-5-5 each named the remedy actually taken — re-run, code fix, resolutions bump or merge round — for 1 of 5 (20%), so the bar is set high and abstaining costs only that default; it is measured again once the labelled set holds enough failures to say more.

As built (P1), one task is one operation, so the rows above are these tasks: `read-folder`; `list-prs`; `read-pr`, `read-pr-checks`, `read-pr-handoff`; `read-in-flight-lease` (`memory.store.query`, D9), `read-in-flight-publications`, `read-in-flight-commissions`; `decide` (`workflow.run.decide`); `lease` (create-only); `read-failure` and `read-failure-log-1` to `-3`; `classify-failure` (`ai.decision.decide`, routed, D8); `rerun-jobs` (`reRunFailedJobs`), `fix`, `bump-dependency`, `merge-round`; `publish`; `release`; `handoff` and `handoff-edit`. `renew` is P2.

### 3.2 What is recorded

Every pass leaves the handoff current and one run in the ledger. A `fix` also leaves the commission's and the publication's runs, linked from the handoff by id. A pass that found nothing to do leaves only its run.

## 5. Phases

**P0 — Measure.** How a fired schedule starts a skill run and what input reaches it (`scheduleCrud`); GitHub's rate budget against the polling interval; the size of a failing job's log and the excerpt that carries the failure; whether `workflow.run.list_attention` can name a branch. _Exit:_ each answer in this plan with the command that produced it — met.

1. **The schedule-to-skill-input path.** _Command:_ a code read of the scheduler path (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts`, `packages/schemas/src/schedules/inputResolution.ts`, `apps/aflow-orchestrator/src/services/SessionOrchestrator/lifecycle/startRun.ts` and their callers) by the coding agent at base `a7939a74`. _Answer:_ a schedule never calls `workflow.run.start`; it starts an agent run, and a skill runs only if that agent then calls `workflow.run.start` with inputs it picks itself. The template is stored verbatim, checked at creation only for non-emptiness (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/scheduleCrud.ts:152-160`, `:499`; `packages/schemas/src/schedules/operations.ts:145-153` — no skill-slug field exists). Firing resolves it with ctx `{now}` (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts:513`); `on_completion` adds `{sourceRun, now}` where `sourceRun.output` is a `PayloadRef` string, not the dereferenced output, and `input` is never set (`:889-892`, `:937-940`). Substitutions are `$now`, `$sourceRef`, `$memoryRef` (`packages/schemas/src/schedules/inputResolution.ts:68-129`); no caller supplies a memory resolver, so any `$memoryRef` fails the firing (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts:514-522`). Dispatch is inline base64 JSON on a `start_run` control message (`:737-757`, `:1090-1093`), trigger `'schedule'`, unattended turn (`packages/schemas/src/runtime/agentPolicies.ts:23-25`). The agent's input contract is checked only at run start (`apps/aflow-orchestrator/src/services/SessionOrchestrator/lifecycle/startRun.ts:117-139`). A scheduled run can carry: static JSON (a branch name, an owner/repo, a SHA range as literal text), `$now` timestamps, and for `on_completion` the source `runId`/`status`/`outputRef`. It cannot carry: live or derived values, any cross-firing cursor (only `firing_count` advances), a skill slug or typed skill inputs as first-class fields, or a repo coordinate — a coding skill's repo is campaign config (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/workflowCrud/run/start.ts:446`) and `pr-shepherd`'s only run input is `prNumber` (`packages/platform-artifacts/src/skillCatalog/prShepherd.ts:136-141`, `:158-165`).
2. **GitHub's rate budget.** _Command:_ `gh api rate_limit` (live probe of the binding's token; `x-ratelimit-*` headers read off a bound `GET /repos/aflowai/aflow`). _Answer:_ core limit 5,000 requests/hour; 5 used at probe, window reset ~38 minutes out. `x-ratelimit-*` and `Retry-After` reach the calling agent unparsed (`apps/aflow-executor-api/src/lib/header-redaction.ts:9-20`). In code there is no GitHub-specific handling: only the generic retry — 2 retries, exponential backoff 1s→30s, on 429/502/503/504, idempotent methods only (`apps/aflow-executor-api/src/handlers/api/execution.ts:74-163`, `apps/aflow-executor-api/src/handlers/api/config.ts:26-40`); it never reads `Retry-After` or `x-ratelimit-*`; the exhausted-limit 403 is not retried; POST/PATCH calls are never retried on 429; `API_RATE_LIMITED` is declared but never raised (`apps/aflow-executor-api/src/lib/api-errors.ts:92`, `:157`). _The interval it gives:_ one pass costs one `listPullRequests` read, then for each pull request the requests of the §3.1 tasks: `read-pr`'s three reads (`getPullRequest`, `listCheckRuns`, `listIssueComments`), `read-failure`'s jobs read for the failing run and log read for the failing job, and `handoff`'s one write — five reads and one write, 6 requests, for a pull request red on one failing job; each further failing job adds one log read. A pass over N such pull requests is 1 + 6N requests. With N = 10: 1 + 60 = 61 requests a pass. One pass every five minutes is 12 an hour: 12 × 61 = 732 requests an hour, 732 / 5,000 ≈ 15% of the budget. With every GET retried twice, the generic retry's ceiling, and the write not retried: 3 × (1 + 50) + 10 = 163 a pass, 12 × 163 = 1,956 an hour, ≈ 39%. Five minutes spends the whole budget at 5,000 / 12 ≈ 416 requests a pass: 1 + 6N ≤ 416 gives N = 69 (12 × 415 = 4,980), and at the retry ceiling 3 × (1 + 5N) + N = 3 + 16N ≤ 416 gives N = 25 (12 × 403 = 4,836). The default interval is five minutes, `*/5 * * * *`, and the rest of the hour's budget stays with the commission, Local Publish and the operator's own use of the same token.
3. **The size of a failing job's log.** _Commands:_ `gh api repos/aflowai/aflow/actions/runs/37460214524/attempts/1/jobs` to name the failing jobs, then `gh api repos/aflowai/aflow/actions/jobs/<job_id>/logs` — GitHub's `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`, which answers with a redirect to a signed URL — for CI run 37460214524 on `aflowai/aflow` (PR #94's first run). _Answer:_ the Test job (112257622723) is 5,955 lines, 923,330 bytes; Vitest's "Failed Tests" block begins at line 5,676, so the last 280 lines carry the failure and its assertion. The Dependency audit job (112257622741) is 421 lines, 32,310 bytes; the advisories first appear at line 232 and the final attempt's block begins at line 387, so the last 35 lines carry every advisory once. An excerpt bounded at the last 300 lines, under 60 KB, carried the failure for both job kinds observed; a bound needs no endpoint binding to hold, and the D5 endpoints are P1's.
4. **Whether the attention list can name a branch.** _Command:_ `workflow.run.list_attention` (pending and consumed items). _Answer:_ no. Items carry `id`, `kind`, `relatedRunId`, `relatedResource` (`workflow_run:<id>`), `payload.terminalStatus`, `priority`, `createdAt`, `consumedAt`, `own` — no branch, no PR, no repo field; learning what a run produced costs a follow-up run-detail read per item.

**P1 — One pass, by hand.** The skill with `read-*`, `decide` (on `when` rules, a fix commission the default), `handoff` and `release`, fired manually against a pull request with a planted failing test; `fix` and `publish` land it. _Exit:_ the planted failure is fixed and pushed within one pass without a hand; a second pass on the same check run is `wait`.

## 6. How it is proven

- **It fixes what CI failed**: a planted failing test is fixed and pushed within one pass, with no hand.
- **Once per failure**: the same `checkRunId` twice is `wait`; the handoff shows one attempt.
- **Never two at once**: two firings in the same minute on one pull request leave one lease, one commission, one publication.
- **It yields to people**: a paused publication, a running commission or a `hands-off` label on the branch is `wait`, by one test parameterised over the three.
- **It approves nothing**: the publication it starts asks exactly where Local Publish asks on its own; a planted allowed-line secret still pauses for the operator.
- **It stops**: the budget reached is a comment, an Action Center item and no further commission.

## 7. Open questions

- Whether the lease belongs in the memory store or on the pull request itself, as a label the shepherd sets and clears; the store is private to the space, the label is visible to a person on GitHub.
- Whether a person's `request_changes` review on the pull request should feed the same `fix` path, with the review comments as the brief's data. The hosted `pr-shepherd` says yes; this plan starts with CI alone.
