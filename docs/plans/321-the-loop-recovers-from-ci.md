# Plan 321 — The loop recovers from CI

**Status:** 🔨 P0 measured (§5); P1 built — the skill, its bundle and agent, the endpoints and their tests (§5 P1 _Delivered_); its live-fire exit runs on the node. D6 revised: the shepherd merges by squash where the connected folder's merge posture allows — `mergePosture`, `never` or `when-green`, beside the push posture, `never` by default — each merge on the operator's write approval (§5 P2b, not started)

**Builds on:** Plan 315 (the loop: commission → review → publish; `mergeFrom`; the push posture, beside which the merge posture sits), the catalog's `pr-shepherd` skill (the hosted code lane's shape of the same job), the scheduler (`agent.schedule.create`), and the `github` connector.

## 1. Problem

The loop ends at the push. Local Publish commits, scans, reviews and pushes, and opens the pull request; what happens to that pull request afterwards is read by a person. In the first week of running the loop on this repository, three pull requests failed CI after an autonomous push — a flaky timing test, a dependency advisory that arrived between two pushes, a merge conflict with `main` that the PR workflow refused to run on — and each was found by the operator, diagnosed by hand, and fixed by a brief written by hand. The always-on target of Plan 315 has a hole exactly there: nothing on the platform notices a red check, and nothing turns it into a commission.

A shepherd that does this starts cold every time. A scheduled run is a new session with no memory of the last one, in a space where other work is in flight: a publication of the same branch may be paused at its approval, a commission for the same pull request may be running under another operator's conversation, a review may be about to return. A shepherd that reads only the pull request will commission a fix for a failure another run is already fixing, re-fix the same failure on every firing, or push onto a branch while a person is working on it. The platform has the pieces — `workflow.run.list_attention`, the handoff comment the hosted `pr-shepherd` leaves on a pull request, the memory store — and no skill that composes them into "what is happening to this pull request right now".

What the hosted `pr-shepherd` already settles: one invocation is describe → rehydrate → decide → fix / merge / abandon / wait → handoff; the handoff comment on the pull request is the durable record the next invocation reads; the fix runs on the existing branch; review and learning happen outside the skill. What it cannot do here: it runs on the hosted code lane (`code.agent.run`, `code.repo.push`), which the local edition does not have, and its idea of "in flight" is the handoff alone.

## 2. Decisions

**D1 — The shepherd is a skill, run by the Runner, started by an agent that decides nothing, and every decision it makes is read from data.** A schedule does not start a skill: it starts an agent run, and the skill runs because that agent calls `workflow.run.start` (§5 P0.1). A schedule carries only a persistent target, `platform-role` or `custom-agent`, never an inline agent (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/scheduleCrud.ts:388`), and the platform agent that holds `workflow.run.start`, the Helmsman (`cybernetic-helmsman`), is a model acting on a template — the prompt rejected below. The agent that decides nothing is therefore a custom agent (`custom-agent`, `packages/schemas/src/runtime/agentTarget.ts`): a step-graph agent, of the kind `agent.manage.create` writes, whose definition is one operation step — `workflow.run.start` of `local-pr-shepherd`, with the skill's slug and the folder binding, `bindingId`, as literal values — and no model turn at all: no `ai.agent.turn`, no prompt, nothing to drift. The step's inputs are fixed when the agent is installed — no `$memoryRef`, which fails the firing, and nothing derived at fire time, which a template cannot carry. The Local PR Shepherd bundle installs the agent beside the skill, under its slug, so the operator creates nothing by hand, and the schedule targets that agent by its slug: the target it stores is `{ kind: 'custom-agent', agentId }`, the id of the agent the slug names. `local-pr-shepherd` is a catalog skill on the host lane: it finds the pull requests the loop opened, reads each one's live state, decides `fix | merge | wait | abandon | leave`, and for `fix` commissions the coding agent on the pull request's branch with `base: <branch>` and `mergeFrom: origin/<base>` and publishes the result appended, through Local Publish, under the folder's posture. No step of the skill is a Helmsman conversation, and the agent's run that starts it reads nothing about pull requests. _Rejected:_ a Helmsman prompt that says "check the pull requests" — a cold session with prose instructions is the shape that commissions duplicate work; what a cold run needs is the state as inputs to its tasks (D3), not a paragraph about being careful.

**D2 — The trigger is a schedule on the local edition, and a webhook later where there is a public address.** A recurring schedule (`agent.schedule.create`, `action: 'start_run'`, `cron`) starts a run of the shepherd's custom agent every five minutes while the executor is paired, and that agent's one operation step starts the skill (D1); the interval is an operator knob whose default, `*/5 * * * *`, is derived from GitHub's rate budget in §5 P0.2. The schedule's target is the custom agent the Local PR Shepherd bundle installs, named by its slug; its template is static JSON, checked at creation only for non-emptiness, and the step reads none of it — the skill's slug and `bindingId` are literals in the agent's definition. The firing carries nothing else: the skill discovers its pull requests itself, because a template carries no live value and no cursor across firings. The appliance's own webhook ingest is the hosted edition's trigger, where `api.aflow.ai` can receive GitHub's `check_suite` events; a laptop cannot, so it polls. A recurring schedule's `maxFirings` is finite by design; the skill's last task renews the schedule when it is near its cap, with the same target and template, so the shepherd does not expire silently.

**D3 — A cold run reads four things before it acts, and acts on none it did not read.**

1. **The pull requests that are its to tend**: open pull requests whose head branch is under the folder's publish prefix and whose body carries Local Publish's marker. A pull request a person opened, or one labelled `hands-off`, is left alone.
2. **The head's checks**: `listCheckRuns` on the head sha. The decision reads the conclusions, not the names.
3. **The handoff**: one comment per pull request, `<!-- aflow:shepherd -->`, carrying `attemptCount`, the `checkRunId` of the last failure acted on, the head sha it acted on, and the run id of the fix it commissioned. Written by the shepherd alone.
4. **The space's in-flight work on that branch**: a lease in the memory store, `shepherd/<owner>/<repo>/<branch>`, taken for the duration of a fix and released at its end, holding the run id and the time; and a bounded read of the space's runs by workflow and input field — `workflow.run.list`, space-wide and one page at most, for the non-terminal runs, paused included, of `publish-local-changes` whose `branch` input is the branch and of `commission-change` whose `base` input is the branch. The attention list cannot answer this: its items name a run, never a branch (§5 P0.4). A branch with a live lease or a non-terminal run on it is `wait`, whoever started that run — a person's conversation included.

The four reads are tasks with typed outputs, and the deciding step receives them as its inputs. A read that fails ends the run as `wait` with the reason, never as a guess.

**D4 — Same failure, same answer: a check run is acted on once.** A failing check whose `checkRunId` equals the handoff's is `wait` — CI has not re-run since the last fix, or the fix is still being published. A new failing check run on a head the shepherd already pushed increments `attemptCount`; at the budget (three, an operator knob) the shepherd posts why it stopped and raises one Action Center item, and leaves the pull request alone until a person moves it.

**D5 — The fix brief is assembled, not written.** The commission's task is built from data: the pull request's title and body, the failing jobs' names and the last part of each failing job's log (`listWorkflowRunJobs` and `getJobLogs` join the `github` connector; the excerpt is bounded and stored as a payload the task references), the handoff's record of earlier attempts, and the standing rules every commission carries (the checks to run, no process started, nothing under `.aflow/`). A conflict with `main` is not a fix the shepherd writes: with `mergeFrom`, the commission starts on the merged tree and resolves it (Plan 315 D15), and the publication folds it into one merge commit.

**D6 — The shepherd merges by squash what the folder's merge posture allows, and never approves or closes.** It pushes only through Local Publish, under the folder's push posture, so an unclean scan or a `request_changes` still asks the operator; it holds no grant and cannot mint one (Plan 253). Whether the shepherd merges a pull request the loop opened is a posture of the connected folder, beside the push posture on its branch policy: `mergePosture`, one of `never` and `when-green`, `never` by default. It is set and changed where the push posture is, by one valued flag named as its sibling is — `connect --merge-posture <never|when-green>` and `aflow harness merge-posture <folder> <never|when-green>` — written to the policy file only when the operator chose it, an absent one resolving to the default wherever it is read, carried in the host inventory and the machine block, and read by the pass through `host.binding.inspect` beside the push posture. `when-green` needs the push posture `unless-unreviewed`: only under it does a publication run Local Code Review (Plan 315 D14), so only under it is there a verdict for condition 2 to read, and under `always` or `never` every pass is `leave`, "the push posture runs no review". The commands refuse that combination rather than store a posture that does nothing: `connect --merge-posture when-green` with a push posture other than `unless-unreviewed`, and `harness merge-posture <folder> when-green` on a folder whose push posture is another, each refuse and name the push posture to set first; `harness push-approval <folder> always|never` on a folder whose merge posture is `when-green` refuses likewise, naming `harness merge-posture <folder> never`. A policy file edited by hand into the combination is read as it stands, and the host inventory and the machine block show the merge posture with that reason beside it. Under `when-green` the shepherd decides `merge` when three things hold, each read on the pull request's current head sha:

1. **Every required check passed on the head.** The required checks are the base branch's, from both places GitHub keeps them: the `required_status_checks` rules of the repository rulesets that apply to the branch (`getBranchRules`, which returns ruleset rules only) and the classic branch protection's required checks (`getBranch`, whose `protection.required_status_checks` a token with read access sees, where the protection endpoint itself wants an administrator). The set is the union of the two; each must have a check run on the head concluded `success`. A required check pending, skipped, neutral or absent from the head has not passed. Only check runs are read (`listCheckRuns`): a required context reported through the commit Statuses API — the older surface an external CI or a bot may still post to — is not a check run, so it is absent from the head and never passes, and `when-green` never merges on a base that requires one. That is this plan's limitation, not an oversight: the pull request is `leave`, its reason naming the required context with no check run, so the operator sees why. Reading the head's combined status (`GET /repos/{owner}/{repo}/commits/{ref}/status`) beside its check runs is deferred (§5). An empty set is not a pass: a base branch that requires no check has not said what green is, so the pull request is `leave` with that as its reason, and an operator who wants such a branch merged by the shepherd names a required check on it first.
2. **The publication's review verdict for that head was `approve`.** The verdict is the one Local Publish's own Local Code Review returned over the range ending at that head, read from the publication's run in the ledger and never from the pull request: the body is prose any collaborator can edit, and a verdict is trusted only from a record the loop alone writes, as D9 trusts the handoff only from its pinned author. Local Publish's `review-commit` output names, beside `verdict`, the `sha` it reviewed — the `at` it bound, which is the commit the push carries. The pass finds the branch's newest finished publication (`workflow.run.list`: Local Publish, input `branch` equal to the head ref, the finished statuses, `limit: 1`, newest first) and reads that task's output (`workflow.run.detail` with `taskOutput: 'review-commit'`); the verdict counts only where its `sha` is the head, so a verdict for an earlier head, a publication that ran no review, or a head another hand pushed counts as none. `publish_as_is` (Plan 316) clears a push and stands in for no verdict here: a head pushed past findings is the operator's to merge.
3. **No person's review on the pull request requests changes.** The reviews are read in one page of a hundred, GitHub's most (`listPullRequestReviews`, which gains `per_page` and `page`; as built it takes neither, and GitHub answers its first thirty). A pass reads one page because a task is one operation and the graph runs no task per page, and GitHub returns reviews oldest first with no count to aim at the newest page by, as D9 aims at the newest comments. So the cap is planned with its consequence: the reviews' transform says whether the page held them all — fewer than a hundred — and a full page is `leave`, "more reviews than one page holds", since a `CHANGES_REQUESTED` past it would not be seen. A pull request with a hundred reviews is the operator's to merge; the loop's own pull requests carry a handful. Of each reviewer who is a person (`user.type: User`), only the reviews that carry a verdict count — `APPROVED`, `CHANGES_REQUESTED` and `DISMISSED` — and the latest of those is what that reviewer says; a `COMMENTED` review carries no verdict, as GitHub itself counts it, and never clears an earlier change request. A reviewer whose standing verdict is `CHANGES_REQUESTED` holds the merge until that review is dismissed or the same reviewer approves.

The merge is the shepherd's `merge` decision in its pass, not a task of Local Publish, because the checks take longer than a publication run should wait: a publication ends at the push and the pull request, CI on the pull request runs for tens of minutes after it, and every pass of the shepherd already reads the head's checks. `merge` is a rule in `decide`, never the decision task (316 D9). It takes the place of the rule that leaves a green pull request to the operator, and every rule that decides `wait` — `hands-off`, a live lease, a publication or commission in flight on the branch, a read that failed — is evaluated before it, so a pull request with a push on its way is not merged. A `merge` pass takes the lease, as a `fix` does. The merge is `mergePullRequest` with `merge_method: squash` and `sha` the head the pass read, so GitHub refuses it if the head moved since the read. A refused merge is `leave`, and its record is in the handoff: `mergeRefusedSha`, the sha the refused request was pinned to, with GitHub's status and message in the handoff's prose. A rule evaluated before `merge` decides `leave` where `mergeRefusedSha` is the head, "GitHub refused to merge this head", so a refusal that persists — a protection rule the reads do not see, a conflict, a merge method the repository forbids — raises one card per head, not one per pass. A refusal because the head moved records the old sha, which is no longer the head, so the next pass reads the new head and may ask again, as it should. A refusal a person resolves without a push — say, by changing the branch's rules — leaves that head to the operator to merge. A merge that succeeds records `mergeCommitSha`, GitHub's answer's `sha`, beside `headSha`, the head merged. `mergeDeclinedSha` (below), `mergeRefusedSha` and `mergeCommitSha` join `SHEPHERD_HANDOFF_FIELDS`. Under `never`, or where any of the three does not hold, the pull request is `leave`, with the condition that did not hold as its reason. `abandon` stays a comment and an Action Center item, never a closed pull request.

The posture's cost is one approval per merge. `mergePullRequest` is a `medium` write, gated by default (Plan 253), and the posture changes neither its tier nor the gate: the `merge` task parks as a `write_approval` pause, an Action Center card showing the exact request — the pull request, `squash`, the pinned sha — and the merge happens when the operator approves it. What `when-green` takes off the operator is the judgment, not the click: no card is raised until the required checks, the publication's verdict for the head and every person's standing review all say merge, so approving confirms one sha-pinned request instead of reading three states. While the card is open the pass is paused and its lease is live, so every later pass on the pull request is `wait` and no second card is raised — for as long as the card is open, not only for D9's twelve hours: a lease whose holder `workflow.run.detail` reports paused at its own `merge` task's write approval is live whatever its age, because that pass is waiting on its operator, not stuck, and D9's bound exists to free a lease from a pass that will not finish. The pause ends only by the operator's answer or the run's cancellation; a cancelled holder has ended, and its lease is stale as D9 says. One duplicate card remains possible — a holder whose run could not be read is stale under D9, and the pass that takes the lease over may ask again — and it cannot merge twice: both requests are pinned to the same sha, and GitHub refuses the second merge of a merged pull request. An approval given after the head moved is refused by GitHub on the pinned sha, and is recorded as any refusal is. A denial fails the `merge` task with the operator's reason, a `permission` error that is not retried; the task is optional, so the pass still writes the handoff and releases its lease. The denial's record is in the handoff: a field `mergeDeclinedSha`, beside `headSha`, holding the head whose merge was denied, with the operator's reason in the handoff's prose; the pass writes it only on a denial, and every later handoff carries it forward until the head moves. `decide` reads it as it reads `checkRunId` (D4): a rule evaluated before `merge` decides `leave` where `mergeDeclinedSha` is the head, with "the operator declined to merge this head" as its reason, so the next pass on that head raises no card, and a new head — a push that moved it — clears it. Because the record is only as good as the handoff's read, `merge` also requires a handoff record read through its pin (D9): a read that was `undecided`, with no pinned author to trust a record from, cannot see a denial, so that pass is `leave` — the pass that writes the first handoff and its pin does not merge, and the next pass does. A space whose operator lowered the `medium` gate in its write policy (`spaces.write_policy`) merges with no card; that is the operator's choice for every medium write in the space, and this plan neither makes it nor asks for it. _Rejected:_ a merge task in Local Publish that waits for the checks — it holds a publication run open for the length of CI on every push; GitHub's auto-merge — it reads the checks and the required reviews but not the publication's verdict for the head, which is the loop's own word on the change; lowering `mergePullRequest`'s tier — the tier is the endpoint's for every space and every caller, the hosted `pr-shepherd`'s gated merge among them, and a posture on one folder cannot answer for them; a posture that pre-approves the merge — an approval is minted only at the authenticated resolve boundary, keyed by the hash of the exact request (Plan 253), and no request exists until the pass has read the sha it pins.

**D7 — What a person asks Helmsman is answered from the same records.** "What is the shepherd doing" is `workflow.run.list_attention` plus the handoff comments, surfaced in the space context as the shepherd's recent decisions per pull request. Helmsman gets no prose about the shepherd; it gets the records.

**D8 — Which remedy a red check wants is a decision task; whether to act stays a rule.** The rules of D3 and D4 are `when`-style comparisons on data with no model — the same `checkRunId` is `wait`, the budget is `abandon`, the `hands-off` label is `wait` — evaluated by one rule step, `workflow.run.decide`, whose first rule that holds is the decision and its reason, and whose default is `fix`. Only once a pass has decided `fix` does a decision task (Plan 316 D4, stored as routes, Plan 318) read what no rule can: its state is the failing jobs' names and log excerpts, the pull request's title and body and the handoff's record, and its one `choice` — `flaky_or_timeout`, `code_defect`, `dependency_advisory`, `base_conflict`, `ci_outage` — routes a confident answer to re-running the failed jobs, the fix commission, a commission that bumps the dependency through `resolutions`, a merge round with `mergeFrom`, or nothing (`wait` on CI). `minConfidence` is set and `onUndecided` is the fix commission, which is what a pass did with every failure before the question was asked, so abstaining costs nothing new; a decision that could not be made at all routes nowhere, and the lease is still released and the record written. The step names no model: the space's decision model answers. The decider never gates a push or a merge (316 D9) — the publication's own posture clears the push, and the guard of the publish task reads only whether a commission returned a change. This replaces §3.1's "the remedy is not a decision task in P1": the measurement there (1 of 5) is why abstention, not a guessed label, carries every case the decider is unsure of.

**D9 — One pass tends one pull request, and every read is a task the rules read whole.** A workflow task is one operation, and the graph runs no task per item, so a pass reads the loop's pull requests and tends the first: those not labelled `hands-off` first, then the most recently updated; `pullNumber` aims a manual pass at one, which must still be one the loop opened. An aimed pass reads its pull request by number (`getPullRequest`) and lists none, so it finds one that would sit past the first hundred open pull requests; a guard reads task outputs, never run inputs, so a rule step (`aim`) says whether the pass is aimed, and only a pass aimed at none lists them. The reads are GitHub's answers shaped by the API executor into typed records before anything is cut to fit inline (`response.transformPresetId`: `loop_pulls`, `loop_pull`, `loop_checks`, `loop_handoff`, `loop_failing_jobs`; `getJobLogs` carries `job_log_tail` itself): a rule compares one field of a record, never a field of GitHub's whole object, and a body that does not shape fails the read. A read GitHub refused is `wait`, by rule. The lease holds the run that took it (a `run_id` binding) and when (a `clock` binding), and is read with `memory.store.get` as an optional read — no lease is the usual case, and the read only advises. It is live while its run is running or paused (`workflow.run.detail`) and younger than `SHEPHERD_LEASE_STALE_AFTER_MS` (twelve hours: a commission's two and a publication waiting at its approval besides); a live lease is `wait`. Where there is none it is taken with `writeMode: 'create'`, and a stale one — its run ended or unreadable, or past the bound unless its run is paused at its own merge card (D6) — is taken over with `writeMode: 'overwrite'` and the `expectedHash` of the lease that was read, so of two passes on one branch, by either way, the second fails there with nothing commissioned and nothing released. The release deletes the lease only as the pass wrote it — `memory.store.delete` with the `expectedHash` its own write answered, which covers its run id and when it was taken — so a pass whose lease was taken over leaves the new holder's standing. A pull request is the loop's only from a branch of the repository itself — a fork's pull request is never the loop's, marker and prefix notwithstanding — and the handoff record is trusted only from the author it was posted as: the record is an HTML comment nobody sees, so from any other author it would lift the budget or hold the pull request at `wait`. No pass asks GitHub who the connection is — `GET /user` refuses a GitHub App's installation token — so the pass that writes the handoff, posted or rewritten, pins it per pull request (`shepherd/<owner>/<repo>/pulls/<number>`) with the comment's id and the author login GitHub's answer to the write gave, and the next pass reads it by id (`getIssueComment`) and takes its record only where the comment's author is the pinned login and the comment sits on the pull request being tended (`loop_handoff:<login>:<number>`). Only where none is pinned, or the pinned comment is gone — it answered 404, and nothing else — is the newest page read (`page` = the comment count over 100, rounded up), for the pinned author's handoff on that pull request; with no pin there is no author to tell a record from a forgery by, the read is `undecided`, and the pass decides as on a pull request with no record — the `fix` default, never a `wait`. "No pin" is only a pin read that succeeded and found none: the pin is read with `ifMissing: 'absent'`, so a pin that is not there answers `found: false`, and a read that fails is not its absence — the record may exist and could not be read. That pass is `wait`, by rule, before anything reads the record; the newest page is not read, so no handoff is posted or re-pinned over the record it could not see, and the already-acted guard and the attempt count stand for the next pass. A pinned comment that could not be read — any answer but 200 or 404, or a call that failed outright — is the same: past one page of conversation the newest holds no handoff rewritten in place, so that pass is `wait`, by rule, and the newest page is not read. A second pull request on the same branch has its own pin and so neither reads nor rewrites the first's handoff. The record keeps the earlier rounds — the attempt count, the last classification and the remedy the routes took (`record-remedy`, a rule step over the remedy question's answer that names the same remedy the routes enable) — and the fix commission and the remedy question are briefed with it whichever read found it. The excerpt bound of D5 holds as the excerpt is carried, escaped as JSON with colour codes taken out, and the log is read from its end — the executor streams the body past all but its last 960 KB, counting the lines it passes, so a log over the 10 MB inline budget still yields its last 300 lines — so a log task's output stays one inline payload the classifying and commissioning tasks bind to by reference to that task. A publication the shepherd starts waits through its approval: a task waiting on a run it started now waits through that run's operator approval (`pauseCause: 'needs_decision'`) instead of cancelling it, and the chain of task-started runs goes three deep, so the shepherd's publication reviews and asks exactly where one started by hand would. The handoff is written by template, its record `key: value` lines inside `<!-- aflow:shepherd … -->` that `parseShepherdHandoff` reads back; a template has no arithmetic, so the handoff read carries the next attempt count, and `$text` writes a count or an id as text and is absent on null, so a part falls through `$firstOf` to its default. Everything after the lease is optional, and a binding to an optional task that failed reads as absent, as a skipped one does — which is what lets the release and the handoff run whichever way a commission or a publication ended. The pass is thirty tasks; a stored workflow holds thirty-two (`WORKFLOW_TASKS_MAX`), and so does a compose-skill draft (`ComposedWorkflowSchema`), which is bounded by the same constant.

## 3. Design

### 3.1 Tasks

| Task             | Operation                                                                | Reads / does                                                                                     |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| `read-folder`    | `host.binding.inspect`                                                   | the branch prefix, the posture, `origin`                                                         |
| `list-prs`       | `api.http.call` `listPullRequests`                                       | open pull requests, filtered to the prefix and the marker, `hands-off` last                      |
| `read-pr`        | per pull request: `getPullRequest`, `listCheckRuns`, `listIssueComments` | head sha, checks, the handoff                                                                    |
| `read-in-flight` | `memory.store.query`, `workflow.run.list`                                | the lease and the non-terminal runs, paused included, whose branch input is the branch           |
| `decide`         | `when` rules only (`workflow.run.decide`)                                | `fix \| merge \| wait \| abandon \| leave`, with the reason; `fix` where no rule names another   |
| `read-failure`   | `listWorkflowRunJobs`, `getJobLogs`; then the remedy decision (D8)       | failing jobs and bounded log excerpts, as a payload                                              |
| `lease`          | `memory.store.put`                                                       | the lease, written before the commission                                                         |
| `fix`            | `host.harness.run`                                                       | `base: <branch>`, `mergeFrom: origin/<base>`, the assembled task                                 |
| `publish`        | `workflow.run.start` Local Publish                                       | appended onto the branch, `wait: 'until_complete'`                                               |
| `merge`          | `api.http.call` `mergePullRequest`                                       | by squash, pinned to the head sha read, under `when-green` only, on the operator's approval (D6) |
| `handoff`        | `createIssueComment` / edit                                              | the updated record, every pass                                                                   |
| `release`        | `memory.store.delete`                                                    | the lease, on every terminal path                                                                |
| `renew`          | `agent.schedule.create`                                                  | the next schedule when this one nears `maxFirings`                                               |

`decide` is a rule. The reads decide `fix`, `merge`, `wait`, `abandon` and `leave` without a model — `merge` only under `when-green`, on D6's reads besides D3's four — and a failure no rule names is `fix`. The remedy for a `fix` is a decision task (D8), routed, whose abstention is the fix commission — a commission briefed with the log excerpt, which reads what a rule cannot. Measured on this stream's own CI failures (Plan 316 §7), Jev, gpt-6-luna and claude-opus-5-5 each named the remedy actually taken — re-run, code fix, resolutions bump or merge round — for 1 of 5 (20%), so the bar is set high and abstaining costs only that default; it is measured again once the labelled set holds enough failures to say more.

### 3.2 What is recorded

Every pass leaves the handoff current and one run in the ledger. A `fix` also leaves the commission's and the publication's runs, linked from the handoff by id. A pass that found nothing to do leaves only its run.

## 5. Phases

**P0 — Measure.** How a fired schedule starts a skill run and what input reaches it (`scheduleCrud`); GitHub's rate budget against the polling interval; the size of a failing job's log and the excerpt that carries the failure; whether `workflow.run.list_attention` can name a branch. _Exit:_ each answer in this plan with the command that produced it — met.

1. **The schedule-to-skill-input path.** _Command:_ a code read of the scheduler path (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts`, `packages/schemas/src/schedules/inputResolution.ts`, `apps/aflow-orchestrator/src/services/SessionOrchestrator/lifecycle/startRun.ts` and their callers) by the coding agent at base `a7939a74`. _Answer:_ a schedule never calls `workflow.run.start`; it starts an agent run, and a skill runs only if that agent then calls `workflow.run.start` with inputs it picks itself. The template is stored verbatim, checked at creation only for non-emptiness (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/scheduleCrud.ts:152-160`, `:499`; `packages/schemas/src/schedules/operations.ts:145-153` — no skill-slug field exists). Firing resolves it with ctx `{now}` (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts:513`); `on_completion` adds `{sourceRun, now}` where `sourceRun.output` is a `PayloadRef` string, not the dereferenced output, and `input` is never set (`:889-892`, `:937-940`). Substitutions are `$now`, `$sourceRef`, `$memoryRef` (`packages/schemas/src/schedules/inputResolution.ts:68-129`); no caller supplies a memory resolver, so any `$memoryRef` fails the firing (`apps/aflow-orchestrator/src/services/ScheduleEvaluator.ts:514-522`). Dispatch is inline base64 JSON on a `start_run` control message (`:737-757`, `:1090-1093`), trigger `'schedule'`, unattended turn (`packages/schemas/src/runtime/agentPolicies.ts:23-25`). The agent's input contract is checked only at run start (`apps/aflow-orchestrator/src/services/SessionOrchestrator/lifecycle/startRun.ts:117-139`). A scheduled run can carry: static JSON (a branch name, an owner/repo, a SHA range as literal text), `$now` timestamps, and for `on_completion` the source `runId`/`status`/`outputRef`. It cannot carry: live or derived values, any cross-firing cursor (only `firing_count` advances), a skill slug or typed skill inputs as first-class fields, or a repo coordinate — a coding skill's repo is campaign config (`apps/aflow-orchestrator/src/services/SessionOrchestrator/handlers/inlineOps/workflowCrud/run/start.ts:446`) and `pr-shepherd`'s only run input is `prNumber` (`packages/platform-artifacts/src/skillCatalog/prShepherd.ts:136-141`, `:158-165`).
2. **GitHub's rate budget.** _Command:_ `gh api rate_limit` (live probe of the binding's token; `x-ratelimit-*` headers read off a bound `GET /repos/aflowai/aflow`). _Answer:_ core limit 5,000 requests/hour; 5 used at probe, window reset ~38 minutes out. `x-ratelimit-*` and `Retry-After` reach the calling agent unparsed (`apps/aflow-executor-api/src/lib/header-redaction.ts:9-20`). In code there is no GitHub-specific handling: only the generic retry — 2 retries, exponential backoff 1s→30s, on 429/502/503/504, idempotent methods only (`apps/aflow-executor-api/src/handlers/api/execution.ts:74-163`, `apps/aflow-executor-api/src/handlers/api/config.ts:26-40`); it never reads `Retry-After` or `x-ratelimit-*`; the exhausted-limit 403 is not retried; POST/PATCH calls are never retried on 429; `API_RATE_LIMITED` is declared but never raised (`apps/aflow-executor-api/src/lib/api-errors.ts:92`, `:157`). _The interval it gives:_ one pass costs one `listPullRequests` read, then for each pull request the requests of the §3.1 tasks: `read-pr`'s three reads (`getPullRequest`, `listCheckRuns`, `listIssueComments`), `read-failure`'s jobs read for the failing run and log read for the failing job, and `handoff`'s one write — five reads and one write, 6 requests, for a pull request red on one failing job; each further failing job adds one log read. A pass over N such pull requests is 1 + 6N requests. With N = 10: 1 + 60 = 61 requests a pass. One pass every five minutes is 12 an hour: 12 × 61 = 732 requests an hour, 732 / 5,000 ≈ 15% of the budget. With every GET retried twice, the generic retry's ceiling, and the write not retried: 3 × (1 + 50) + 10 = 163 a pass, 12 × 163 = 1,956 an hour, ≈ 39%. Five minutes spends the whole budget at 5,000 / 12 ≈ 416 requests a pass: 1 + 6N ≤ 416 gives N = 69 (12 × 415 = 4,980), and at the retry ceiling 3 × (1 + 5N) + N = 3 + 16N ≤ 416 gives N = 25 (12 × 403 = 4,836). The default interval is five minutes, `*/5 * * * *`, and the rest of the hour's budget stays with the commission, Local Publish and the operator's own use of the same token.

## 6. How it is proven

- **It fixes what CI failed**: a planted failing test is fixed and pushed within one pass, with no hand.
- **Once per failure**: the same `checkRunId` twice is `wait`; the handoff shows one attempt.
- **Never two at once**: two firings in the same minute on one pull request leave one lease, one commission, one publication.
- **It yields to people**: a paused publication, a running commission or a `hands-off` label on the branch is `wait`, by one test parameterised over the three.
- **It approves nothing**: the publication it starts asks exactly where Local Publish asks on its own; a planted allowed-line secret still pauses for the operator.
- **It stops**: the budget reached is a comment, an Action Center item and no further commission.
- **It merges only what the posture allows**: under `when-green`, a pull request green on every required check, approved by the publication's review for its head and with no person requesting changes raises one write approval and, approved, is squash-merged on the head that was read; three planted refusals — a red required check, a base requiring no check, and a person's `request_changes` that a later `COMMENTED` review of theirs does not clear — each leave it unmerged with the reason in the handoff and no card raised; a denied card is `leave` with the operator's reason, and no later pass asks again for that head — only for a new one; an approved merge GitHub refuses is `leave`, and no later pass asks again for that head; a merged pull request's handoff names the merge commit; a lease held by a pass paused at its merge card past D9's bound is not taken over; a full page of reviews is `leave`; a required context with no check run is `leave`; the commands refuse `when-green` beside a push posture that runs no review, in either order; a verdict edited into the pull request's body counts for nothing; under `never`, nothing merges.
